# Changes to ergo.rego

This file is about `ergo.rego` only. The Rust engine's changes are in [engines/rust/CHANGELOG.md](engines/rust/CHANGELOG.md), and the spec's in [spec/CHANGELOG.md](spec/CHANGELOG.md). Each release names the version of the spec it follows.

## 0.7.0

### Changed

- A number in the policy with more than 15 significant digits is written wrong, as spec 0.7 says ([sentence.value.scalar](spec/syntax.md#values)). `l equals 1234567890.1209567890` fails `$well_formed` with `number with more than 15 significant digits: 1234567890.1209567890`, and the requirement gets no other row, where it passed with `l` holding `1234567890.1209567990`. A number in `from`, `meta` or `min_subjects` is written wrong the same way. Digits are counted on the value, so `1.50` has 2 and `1e20` has 1. The limits of the range, `2.2250738585072014e-308` and `1.7976931348623157e308`, have 17, so a policy can't write them any more. Changes the report of every policy that writes such a number.

### Fixed

- Numbers in the input and the params are compared on every digit, as spec 0.7 says ([value.number](spec/semantics.md#values)), where OPA could count two decimals as equal when they differed only after the 15th significant digit. With `{"rows": [{"id": "b", "l": 1234567890.1209567990}]}` and `limit` `1234567890.1209567890` in the params, `l is at most $params.limit` fails as `value`, where it passed. The same goes for `equals`, `is not`, the order phrases, `is between`, `is … within`, `is one of`, `is in`, `contains`, the items of `every` and `some`, the copies `distinct` drops, a time written as a number, objects and lists that hold such numbers, like `o equals p` with `o` holding `{"v": 1234567890.1209567890}` and `p` `{"v": 1234567890.1209567990}`, the items `sorted by` picks in a `for` line, and the ids `$unique_ids` compares. A row no longer takes the answer of another row whose numbers OPA counted as equal, so the report doesn't depend on the order of the input, and a message quotes the row's own numbers with every digit, where `r is less than l` could say `l is 1234567890.120956789` for an `l` of `1234567890.1209567990`. Changes the report of checks on such numbers.
- A `for` line that starts with `some` and has a second item passes when one item of the first list passes, as spec 0.7 says ([for.pass](spec/semantics.md#for)), where it failed when another item's alias held a value the sentence couldn't read. With `approvers` holding `[{"username": "ada"}, {"state": "APPROVED"}]` and `commits` one commit, `for: some approvers as approver, every commits as commit` with `approver.state is "APPROVED"` passes, where 0.6.0 failed it as `absent` with `item 1 of approvers: approver.state is missing`. The same goes for a second item with `some`, `first of` or `last of … sorted by …`, and for one whose `whose` reads the first item's alias. An item that is an object, where what a sentence or a later line reads through its alias, like `approver.state`, is missing, `null` or of the wrong type, never counts as passing, even when nothing is checked for it because the second list is empty with `, if any,` or its `whose` leaves nothing, and every sentence reads the second item's alias: with `approvers` holding `[{"username": "ada"}]`, `commits` holding `[]`, `every commits, if any, as commit` and `commit.author is approver.u`, the check still fails as `absent` with `item 1 of approvers: approver.u is missing`. An item that isn't an object is judged as before, so when nothing is checked for it, it passes, and `["str", {"username": "b"}]` now passes through `"str"`. When no item passes, the check fails as before.

- A `for` line with a list that's empty with `, if any,`, or whose `whose` leaves nothing, still runs the sentences that don't read that list's alias, as spec 0.7 says ([for.if_any](spec/semantics.md#for)), where it ran none of them. With `approvers` holding `[{"u": "g", "state": "REJECTED"}]` and `commits` holding `[]`, `for: some approvers as ap, every commits, if any, as c` with `ap.state is "APPROVED"` fails as `value` with `item 1 of approvers: ap.state is "REJECTED"`, where 0.6.0 passed it. The same goes for a `for` line that starts with `every`. With the empty list first, `for: every commits, if any, as c, some approvers as ap` fails as `value` with `item 1 of approvers: state is "REJECTED"`, as `for: some approvers as ap` does, and approvers `[]` fail as `value` with `approvers is []`, where 0.6.0 passed both. With one item, `for: every xs, if any, as m` with `z is 1` fails as `value` with `z is 3` when `z` holds `3` and `xs` holds `[]`, where 0.6.0 passed it. A sentence that reads the second item's alias, like `c.author is ap.u`, has nothing to check and is left out. An item of the first list that isn't an object now fails a sentence that reads it as `not_an_object`, so approvers `["str"]` fail where 0.6.0 passed them.

- A root of the wrong type on the left of a compare, like `z` in `z is at least 1` under `every xs, if any, as m` with `z` holding `"s"`, fails the check as `unusable` with `z is "s", which isn't a number` on an empty list too, as spec 0.7 says ([for.roots](spec/semantics.md#for)), where it passed. The same goes for `is at most`, `is more than`, `is less than`, `is not`, `does not equal`, `is … within`, a text compare like `starts with`, a time compare when the value isn't a time at all, and a root on the left in a `whose`, like `count of xs whose $params.q is at least v is 0` ([tally.whose](spec/semantics.md#counts-and-sums)). With items, the root is named once with no item in front, like a root on the right: `z is at least m.v` says `z is "s", which isn't a number` where it said it for each item, and `z is at least $params.q` with no `q`, or a `null` one, says `z is "s", which isn't a number; $params.q is missing` (or `is null`) where it said only `$params.q is missing` (or `is null`). With params that aren't an object, like `3`, `z is at least 1` on an empty list was already `unusable`, and its message changes from `for every xs, if any, as m: z is at least 1 is false` to `z is "s", which isn't a number`.

- When `every`, `some`, `count of … whose` or a `for` line's sentence reads a name that walks a list, its `inputs` entry is the one a plain check of the same path has, as spec 0.7 says ([walk.inputs](spec/semantics.md#every-and-some)). With the subject `t` from `every teams` holding `[{"name": "ann", "rows": [{"v": "ann"}]}, {"name": "bob", "rows": [{"v": "bob"}]}]`, `every rows.v is in name` lists `t[].name` holding `["ann", "bob"]` at `/teams/0/0/name` and `/teams/0/1/name`, where it listed `t.name` holding `null`. The same goes for a part on a list subject, a list in the middle of a name, like `os[].name`, and a part that holds a list, which keeps its `part` tag. An alias of a `for` line that holds a list is listed the same way in the `inputs` of `failed_assertions`: `every rows.v is in d.name` with `d` holding `[{"name": "ann"}, {}]` lists `d[].name` holding `["ann", null]`, where it listed `d.name` holding `null`, as `$params.w is in d.name` already did. `for: every rows as r` with `r.v is in name` on that subject passes and lists `t[].name`, where it failed as `not_an_object` with `the subject is [...], which isn't an object` ([walk.start](spec/semantics.md#every-and-some)). Changes the report of checks that read such a name.

- A `whose` or a `that` on a `from` line takes the list position `9007199254740991` in brackets, as a sentence does ([sentence.path.brackets](spec/syntax.md#paths)), where it was written wrong with `9007199254740992 can't be a list position`. With `from: things whose l[9007199254740991] is 1` and no `l` that long, the report has the subject, and its `$applies` row fails as `absent` with `item 9007199254740992 of l is missing`. A position above it is still written wrong with the number as written, like `9007199254740992 can't be a list position` for `l[9007199254740992]`. The Rust engine already did this.

- A `followed by` piece read from `$input` on an input that is a list fails as `not_an_object` with `$input is [...], which isn't an object`, as a path on its own does and as spec 0.7 says ([compare.join](spec/semantics.md#compare)), where the message was `k is $input.k followed by "" is false`. After `contains` and `does not contain`, an `unusable` row names the left side only when it isn't a list of text: `tags contains $input.o.a.b followed by ""` with `tags` holding `["a"]` and `$input.o.a` holding `1` says `$input.o.a is 1, which isn't an object`, where it added `tags is ["a"], which isn't a number`, and `p contains "a" followed by v` with `p` holding `5` says `p is 5, which isn't a list`, where it said `"a" followed by v is "ax", which isn't a number`. Changes the message of such rows.
- A parent's part read in a `whose` or a `that`, like `art.cov.z` in `every ys whose n is at least art.cov.z as x`, is read once, before any item, as a part of the subject already was ([message.items](spec/semantics.md#messages), [walk.flaws](spec/semantics.md#every-and-some), [for.roots](spec/semantics.md#for)). When it's missing, `null` or of the wrong type, the message names it once with no item, `art.cov.z is missing`, where it said `item 1 of ys: art.cov.z is missing; item 2 of ys: art.cov.z is missing`. A parent's part that is a list fails as `unusable` with `art.cov is [{"z": 1}], which isn't an object`, except after `is in` on a `for` line, where it still passes. The same goes for a grandparent's part, for `every`, `some`, `count of` and a `for` item. The Rust engine already did this.
- On an empty list, a parent's part that can't be read now fails the check, where it passed or said only that the list is empty ([for.roots](spec/semantics.md#for), [walk.flaws](spec/semantics.md#every-and-some)). With the part `cov: c` and the input `{"arts": [{"id": "a1", "c": {}, "xs": [{"ys": []}]}]}`, `every ys.n, if any, is at least art.cov.z` passed, and now fails as `absent` with `art.cov.z is missing`. With `c` `null` it fails as `null` with `art.cov is null`, and with `c` `[{"z": 1}]` as `unusable` with `art.cov is [{"z": 1}], which isn't an object`. With the same input, `for: every ys as x` with `x.n is at least art.cov.z` said `ys is []` as `value`, and now says `art.cov.z is missing; ys is []` as `absent`. `every ys whose n is at least art.cov.z is an object` said `ys is []` as `value`, and now says `art.cov.z is missing` as `absent`. The Rust engine already did this. Changes the report of checks that read such a part.
- A name after `that` on a `for` line that the item lacks is named after the item and a colon, as after `whose` ([message.items](spec/semantics.md#messages)): `every xs that is at least c as x` says `item 1 of xs: c is missing`, where it said `item 1 of xs c is missing`. The Rust engine already did this.
- An alias that `first of`, `last of` or a position leaves without a value, because its list is empty, is named without a `$` on a later line ([message.alias](spec/semantics.md#messages)): `last of approvers sorted by t as approver, some approver.subs as commit` says `approver.subs is missing`, where it said `$approver.subs is missing`. The same goes for a position, like `ap[0]` in `first of approvers as ap, every ap[0] as c` with the input `{"prs": [{"id": "p", "approvers": []}]}`: it says `item 1 of ap is missing`, where it said `item 1 of $ap is missing`. The Rust engine already did this.

- A list on the right of `is in`, `matches` and the other list phrases, read from a part, a parent, a parent's part, `$input` or `$params`, is walked on a `for` line, in a sentence, in the line's own `whose` and in the `whose` of a `count of`, as spec 0.7 says ([for.roots](spec/semantics.md#for)), where it failed as `unusable`. A `count of` or `sum of` inside a `whose` reads its path as it does on its own ([tally.whose](spec/semantics.md#counts-and-sums)) and is read once before any item, so a problem it has fails the row on an empty list too. A `for` line's `inputs` list the walked name, like `pos[].name`.

- A name read from outside the item that walks a list is named once, with no item in front, in an `every`, a `whose` and a `for` line, as spec 0.7 says ([message.items](spec/semantics.md#messages)), where it was read as `pos is [...], which isn't an object` or repeated under each item. A `for` line says an item's own problem after a root that can't be read, even when it fails no worse than the root, and `and N more` counts each problem once.

- A list that a phrase after `is in`, `is not in` or `matches` walks and that reads fine isn't named as `os is [...], which isn't an object` when the item can't be compared: `every rows.v is in os.name` with `os` holding `[{"name": 3}]` says `item 1 of rows: v is "bob", which isn't a number`, as the Rust engine does.

- A check that reads one name both item by item and as one value lists both reads in its `inputs`, as spec 0.7 says ([walk.inputs](spec/semantics.md#every-and-some)): `pos[].name` holding `["a"]` and `pos.name` holding `null`, as the Rust engine does.
- A root that a check walks as a list, and that holds an item it can't read or values it can't use, fails the check on an empty list too, or when a `whose` leaves no item, as spec 0.7 says ([tally.walk](spec/semantics.md#counts-and-sums), [for.roots](spec/semantics.md#for)), where the check passed. That goes for a part, a parent, a parent's part, an alias of an earlier `for` line, a field of the subject written with a dot, `$params` and `$input`, read by `every`, `some`, `count of`, `sum of`, a `whose`, a `that` and a `for` line. With the part `pos` holding `[{"name": "bob"}, {}]` and `rows` `[]`, `count of rows whose v is in pos.name is 0` fails as `absent` with `item 2 of pos: name is missing`, where it passed. A row that already failed keeps its report.

- A check that doesn't go through a list item by item, like `k is $input.m named by $params.k`, `k is m named by $input.k` or `tags contains $input.m named by $params.k`, fails as `not_an_object` with `$input is [...], which isn't an object` when the input is a list and the `named by` key can't be read, as spec 0.7 says ([path.not_an_object](spec/semantics.md#reading-a-path)). With no `k` in the params, `k is $input.m named by $params.k` and `k is $input named by $params.k` failed as `absent` with `$params.k is missing`, and as `null` or `unusable` with a `null` or a number, and `k is m named by $input.k` failed as `unusable`. Each check decides this on its own, whatever the other checks of the requirement are. The cause is `not_an_object` in every plain check, and the message is the list message for the forms the cases pin: a few, like `n plus m named by $input.k is 2`, give the same cause with a different message in the two engines ([OPEN.md](spec/OPEN.md#where-ergorego-and-the-rust-engine-differ)). A one-line `every` or `some`, a `for` line, a `count of` or `sum of`, a child subject's checks and the `whose` of a `from` line don't change. Changes the report of such checks.

- A check whose two sides can't be read in different ways fails with the worse cause of the two when one side reads a key from `$params` or `$input`, as spec 0.7 says ([path.ref_step](spec/semantics.md#reading-a-path)), where the key decided. `k is m named by $params.k` with no `k` on the subject and `$params.k` `null` fails as `absent` with `k is missing, and m named by $params.k is null`, where it failed as `null` with `$params.k is null`. The same goes for an `add`, a `count of` or a `sum of`, like `k is 1 plus m named by $input.k` and `count of zzs is m named by $input.k`, a one-line `every` or `some`, a `for` line, whose `failed_items` change cause too, and the condition of a `from` line, whose `$applies` row now says `k is missing`. In the `whose` of a `count of`, each item fails with the worse of its own cause and the key's: `count of rs whose zz is m named by $input.k is 1` with `$input.k` `null` and no `zz` on the items fails as `absent` with `item 1 of rs: zz is missing; item 2 of rs: zz is missing`, where it failed as `null` with `$input.k is null`, and an item that fails worse than a key that is missing or `null` gives its cause: `count of rs whose v.y is m named by $input.k is 1` with `v` holding `"a"` fails as `unusable` with `item 1 of rs: v is "a", which isn't an object`, and an item that isn't an object fails as `not_an_object`, where they failed as `absent` with `$input.k is missing` or as `null` with `$input.k is null`. With a key that is missing or `null`, `count of rs.v whose zz is m named by $input.k is 1` with `rs` holding `[{"v": 2}, {"v": 4}]` fails as `not_an_object` with `item 1 of rs: v is 2, which isn't an object; item 2 of rs: v is 4, which isn't an object`, where it failed as `absent` or `null`. A key in a path read from a root ends with the key's outcome, and `ergo.rego` names it first when the root is `$input`, the key is read from `$input` and one condition reads it: `count of rs whose zz is $input.m named by $input.k is 1` with the key `null` fails as `absent` with `$input.k is null; item 1 of rs: zz is missing; item 2 of rs: zz is missing`, where it failed as `null` with `$input.k is null`. A key in a path read against the item is named only when the row fails with its cause, so `count of zzs whose v is m named by $input.k is 0` with no `zzs` and the key `null` still fails as `absent` but says `zzs is missing`, where it said `zzs is missing; $input.k is null`. A phrase that reads the path as a list, like `count of rs whose zz is in m named by $input.k is 1`, still takes the key's cause when `rs` can be read, and with no `rs` and the key `null` or `$params.k` `null` it fails as `absent` with `rs is missing`, where it said `rs is missing; $input.k is null`. An option of an `any_of` follows its plain check: `a: k is m named by $input.k` with the key `null` and no `k` says `a: k is missing`, where it said `a: $input.k is null`. A key that is missing or `null` beside a list of mixed values, like `m named by $params.k is in vs` with `vs` holding `["a", 4]`, fails as `unusable` with `vs is ["a", 4], which isn't a list of one kind of value`, where it failed as `absent` or `null`. Changes the report of such checks.

- A `count of`, a `sum of` or a `plus` that reads a `named by` key from `$input` when the input is a list says `$input is [...], which isn't an object`, as spec 0.7 says ([path.not_an_object](spec/semantics.md#reading-a-path)), and still fails as `unusable`. `sum of xs.m named by $input.k is 1` and `count of tags is n plus m named by $input.k` said `... needs more than 15 digits`, which had nothing to do with the problem, and `count of xs.m named by $input.k is 1` said `count of xs.m named by $input.k is 1 is false`. Under a `for` line the message no longer adds `; item 1 of xs: ...` after it.

## 0.6.0

### Changed

- A `from` line with more than one name needs `every` to read a list, and `every` works on a child subject, as spec 0.6 says. `every artifact.pull_requests` replaces `artifact.pull_requests`, and `every trail.artifacts` replaces `trail.artifacts`. Without `every`, `$min_subjects` fails as `unusable` and names the list and the fix. A line that ends at text, a number or true or false gives that value as a subject, the subjects of a line must be of one type, `every` reads one list per name, a name it reads as a list must be one in every item, `every deployment` is written wrong with `deployment is a subject: write deployment whose … to narrow it, without every`, and a list before `named by each of` says to use a child subject. A failure for mixed types, or for a name that is a list in some items only, lists the items it names in `failed_items`, and a child subject of such a line is still read under each parent. Reports change for every policy that reads a list through a path of two names or more, see [spec/CHANGELOG.md](spec/CHANGELOG.md).
- Names resolve where spec 0.6 says, from their root or against the focus. A bare name on the right of the phrase after `every` or `some` reads the subject's field, and so do a name written with a dot and a `named by` field there. `whose` and `that` after `every`, `some`, `count of`, `sum of` and on a `for` item read the value the path ends at, so `count of approvers.username whose state is "APPROVED"` fails as `not_an_object`. The subject's name followed by a step, like `pr.author`, reads the subject's field inside a relative clause. In a `from` line, the right side of a `some` or `every` condition reads the candidate subject. Reports change for policies that write these, see [spec/CHANGELOG.md](spec/CHANGELOG.md). This version follows spec 0.6, so a policy says `ergo_spec: v0.6`, and the report's `ergo` says `v0.6`.
- As spec 0.6 also says: `pr named by k` and `pr[0]` are allowed inside a relative clause; a `whose` that compares a field with itself says `write pr.x`; `distinct` no longer makes a bare name on the right written wrong; a `sum of` whose `whose`, or the right side of its `that`, reads a name of the value it adds is written wrong; a `named by` on the right of `every` or `some` reads the subject's key whatever the path starts at, `$params` and `$input` included; `named by pr.k` takes the key from the subject inside a relative clause, after any path; a root name in a `whose` or on the right of `every` or `some` is read once, up front, so a problem with it fails the row even on an empty list; a `whose` that compares a field with itself gives no advice when the subject's name needs double quotes; and messages name a value past the list after its item and a colon, list every item a `count of` or `sum of` couldn't read, say a root name no item can use once, and a root name's problem inside a relative clause once with no item, and an item of its own list once, like `item 2 of $params.envs is null, which isn't an object`, name a `named by` key that can't be read, name the item in `item 2 of xs: k is missing` for `pr named by k` in a relative clause, and write the item's path in full when a name on the right is spelled the same.
- As spec 0.6 says, `contains` and `does not contain` read one value and never walk a list on their right side, so a list the path meets on the way fails as `unusable`, and a path like `$input.k` or `$input.m named by key` on a list input as `not_an_object` with `$input is [...], which isn't an object`, while a list it ends at is still one value. `$refs` list such a path as written, with the value `null`. The list after `named by each of` never walks a list either, and a message names text, a number or a list that stops the read of its keys. A right side that walks a list names the value where the read stopped when another item holds a list there, where it said `item 1 of o is null`. Reports change for policies that write these, see [spec/CHANGELOG.md](spec/CHANGELOG.md).
- As spec 0.6 says, `every`, `some`, `count of`, `sum of`, a `for` item without a position and the right side of the phrases that take a list read each item of a list a path starts at, whether it is the subject, a part, a `for` alias or `$input`, and so does a second `for` item that starts at an alias holding a list. With the subject `t` holding `[{"name": "a"}, {"name": "b"}]`, `every name is "a"` fails as `value` with `item 2 of t: name is "b"`, where it failed as `not_an_object`. A check that also reads the subject's own field outside those, like `every name is other` or a `for` sentence `o is boss`, still fails as `not_an_object`, once. The right side of a list phrase after `every`, in a `whose` or in a `that` now reads a list in the middle of a name or an alias that is a list item by item, like `every xs.v is in ys.v`, where it failed as `unusable` or `not_an_object`. A path from `$input` on a list input, `named by` forms included, says `$input is [...], which isn't an object`, and `$input[0].id` on `[1]` fails as `unusable` where it failed as `absent`. A `for` item that isn't an object is named by its value, `item 2 of t is 3, which isn't an object`, where it said `is null`. A check that can't use a param or a `named by` key no longer says the list it reads isn't an object, in `every`, `count of` and `sum of`, and a root name inside a `whose` that isn't a list, or that is missing or `null` in an item of the subject, is said once, with no item.
- A path that meets `null` partway along fails as `null`, where it failed as `absent`, and the message names the step that is `null`, as spec 0.6 says: `c.z is 1` with `c` `null` says `c is null`, where it said `c.z is missing`, and `pl.z is 1` with the part `pl` `null` says `pl is null`. The same goes for `$input`, `$params`, a parent's field, a `for` alias and a position on a `null` subject, alias or `$input`. `exists` and `does not exist` keep their causes and name the step. A key read from a field right after the `null` still decides. A `whose` condition on a `from` line reads the same way, so its `$applies` row fails as `null` with `c is null`, while a `from` line that walks through the `null`, like `every prs.c.z`, still fails `$min_subjects` as `absent`. A key read from a field after the `null` is named too, after the step, like `s is null; p is 3, which isn't text`.
- `require: some` on a child subject needs a passing subject under each parent, as spec 0.6 says ([require.some.parent](spec/semantics.md#requirements)). A commit whose pull requests all fail makes `every commit.pull_requests` with `require: some` `not_met`, where an approved pull request of another commit made it `met`. The failing subjects under a parent that has a passing one are no longer violations or counted in `causes`. Reports change for policies that use it, see [spec/CHANGELOG.md](spec/CHANGELOG.md).
- A requirement on a child subject checks the ids of every ancestor of its subject too, the parent and the grandparent, on a new `$unique_ancestor_ids` row whose subject is the ancestor, as spec 0.6 says ([unique_ids.ancestors](spec/semantics.md#requirements)). The same goes for `some`, `count of … whose`, `sum of … whose` and a `for` item's `whose`. The left side of a `whose` and a name with a dot, `.x.z`, still read the item's field. The ten-step limit now counts such a part's own path, so a part of ten names there is written wrong, as it is after `every`.
- A parent subject's name on the right of a `whose` inside a `count of` or `sum of`, like `fam.z` in `count of items whose n is count of fam.z is 1`, read each item's field of that name. It now reads the parent, as it does in `every`, `some` and a `for` item's `whose`. The left side and `.fam.z` still read the item's field, and a parent's part counts its path toward the ten-step limit there.
- A walk over ten steps on a `for` line, in its `whose` too, gives `for: every and some over more than ten steps aren't supported yet`, with the `for: ` that [sentence.for.line](spec/syntax.md#the-for-line) puts on every problem with the `for` line. It had no `for: ` before.
- A `from` line with `every` on a `null` input, like `every commits` or `every $input[0]`, fails `$min_subjects` as `null`, as its `failed_items` already said, where it failed as `absent`. Reports change for such policies.

### New

The `$applies` row reads the same inputs and gives the same cause as the sentence does as a check. A subject whose list is missing, `null` or not a list fails the requirement as `absent`, `null` or `unusable`, as any condition that can't be decided does. Its `$applies` row has `failed_items`, as a check's row does, and `[]` when it passes. For `from: releases whose some files.path does not match "^docs/"`, the row of release `1.4.1` in `{"releases": [{"id": "1.4.1", "files": [{"path": "docs/typo.md"}]}]}`, which only changes `docs/typo.md`, is:

- `it` is the subject itself. A list of plain values, like ids, regions or tags, can now be checked: with a subject read from `every deployments.regions`, `it is one of $params.allowed_regions` fails the region that isn't allowed. `it` works for any subject (a string, a number, a list, an object, `null`) and fails the way the same phrase fails on a field holding that value. A position works on a subject that is a list, written in words as for a field: `first of it`, `item 2 of it`. A row's `inputs` name it `it`, and a failed item `item 1 of it`. Anywhere else `it` is written wrong, with a message that says why, like `it is the whole subject: write name, not it.name`. See [REFERENCE.md](REFERENCE.md#the-subject-itself).
- `ergo.as_sentences` rewrites a check from before 0.1 whose path is empty, `[]`, with `it`, so `{op: equals, path: [], value: "x"}` becomes `it is "x"`, where it was left as it was. A path that starts at a field called `it` is written `.it`.

A read that stops early points at the last value it reached, so a pointer never leads to a value Ergo didn't read. [Where a value was read](REFERENCE.md#where-a-value-was-read) shows it.

## 0.1.0

The first release. It follows spec 0.1.

Ergo went public on 6 October 2026. This is what changed since, for anyone who tried it then, and what you need to know to use it now. A policy written before 0.1 needs the changes under [Moving a policy from before 0.1](#moving-a-policy-from-before-01) before 0.1 reads it.

### Checks are sentences

A check used to be an object, like `{op: non_empty_string, path: [approved_by]}`. Now it's a sentence: `approved_by is a non-empty string`. Sentences cover lists (`every`, `some`, `whose`), counts and sums (`count of`, `sum of`, `plus`), text (`starts with`, `matches`), times and plain dates (`is before`, `days elapsed from`), one item of a list (`item 1 of`, `last of commits sorted by timestamp`) and a list read by a key (`named by`). The report shows each check as the sentence you wrote, so whoever reads the report reads the rule.

The old shape isn't read any more. A policy written that way is written wrong, and the report says so. `ergo.as_sentences(policy)` rewrites what it can as sentences and leaves the rest as it was, like `all`, `any`, `any_of` and `count` checks, for you to rewrite by hand. [Moving a policy to sentences](https://github.com/kosli-dev/ergo/blob/rego-v0.1.0/REFERENCE.md#moving-a-policy-to-sentences) shows what it leaves. Custom operators and substitutes went with the old shape, because a sentence can't call an operator, and an `any_of` of sentences says what a substitute did. A file of custom operators next to `ergo.rego` no longer compiles, so it fails loudly rather than being ignored.

### Subjects are defined once

A policy lists its subjects, the deployments or artifacts or expenses it checks, under `subjects`, each with a `from` line like `deployments whose environment is "prod"` and an `identified_by` field, and each requirement names the one it checks. A subject can be found inside another, like the artifacts of each deployment, up to three levels, and can name parts with `has`. The report lists the subjects and where each one came from, and a row that read a part says which part and which id.

### Reports say more

A failed `every` or `some` lists the items that failed. An unmet requirement says why, worst cause first, with how many rows each. A policy, a requirement and a check can carry a `description` and `meta`. A policy with a field Ergo doesn't know, or without `ergo_spec: v0.1` at its top, is written wrong, with a row that says what's wrong, and a requirement written wrong gets only that row. Every report says what made it, under `engine`, and which spec version it follows, under `ergo`.

Rows name what they read the way sentences write it: `$params.allowed` where it was `$$params.allowed`, and `item 2 of xs` where it was `xs.1`. Numbers are written in their plain form, so `1.50` in the input is `1.5` in the report. The causes `substituted`, `unmatched` and `ill_formed` are gone with what produced them.

### Verdicts that changed

Some checks that passed at the launch fail now, because Ergo could not tell whether they held:

- A `from` that leads nowhere, to `null` or to something that isn't a list or an object, fails `$min_subjects` as `absent`, `null` or `unusable`, even with `min_subjects: 0`. It used to count as nothing to check.
- A comparison on a field of the wrong type fails as `unusable`. `is not one of` and `does not contain` used to pass on one, and `is at least` used to order two strings, so `"9"` was at least `"80"`.
- A `whose` on a field of the wrong type fails the requirement. The subject used to be left out quietly.
- Params that aren't an object, like a string, fail every check as `unusable`. `null` still means no params.

### A written spec

Ergo has a spec that doesn't depend on Rego: a grammar for the sentences, JSON Schemas for a policy and a report, and cases that pin what each check means. CI runs every case against `ergo.rego`. The schemas are at [ergo.kosli.com/spec/0.1/policy.schema.json](https://ergo.kosli.com/spec/0.1/policy.schema.json) and [ergo.kosli.com/spec/0.1/report.schema.json](https://ergo.kosli.com/spec/0.1/report.schema.json), and [spec/CHANGELOG.md](https://github.com/kosli-dev/ergo/blob/rego-v0.1.0/spec/CHANGELOG.md) lists what the spec changed against the old shape.

### Faster and lighter

A report takes about two thirds of the time it took at the launch, and `ergo.compile`, which reads a policy once and reuses it for many reports, cuts it further. It's experimental and may change. A report on 100 deployments compiled to Wasm used 264 MB of memory at the launch and uses under 20 MB now, and CI keeps a budget on it. Ergo reads nothing from the machine, so it compiles on a host that leaves out the built-ins that read the clock or the network, and a host that checks `input` against a closed JSON Schema can publish an Ergo policy.

### Moving a policy from before 0.1

- Call `ergo.report(input, policy, params)`. It was `ergo.report(input, requirements)`, with `report_with_params` for params. The policy is one object with `ergo_spec`, `subjects` and `requirements`, and params are `{}` when there are none. [Getting started](https://github.com/kosli-dev/ergo/blob/rego-v0.1.0/README.md#2-write-a-policy) shows the Rego that hands a YAML file over.
- Put `ergo_spec: v0.1` at the top of the policy file. From Rego, pass it as `"ergo_spec": data.ergo_spec`. Without it, every requirement is written wrong.
- Move `subject_type`, `from`, `id` and `applies_to` out of each requirement into one entry under `subjects`, with a `from` line that holds the `applies_to` conditions after `whose`, and `identified_by` where `id` was. Each requirement then says `subject: <name>`. Those four fields on a requirement are unknown now.
- Rewrite each check as a sentence, with `ergo.as_sentences` for the first pass.
- Anything that matched on row `inputs`, `$refs` or `failed_items` by name needs the new names above.

### What to call

`ergo.report(input, policy, params)` gives the report.

`ergo.violations(report)` gives the rows that failed and leaves out the ones that aren't problems, like a subject that was out of scope.

Ergo is one file, `ergo.rego`, with no dependencies. It needs OPA 1.20.1 or later: OPA 1.19 compares some numbers wrong, and OPA 1.20.0 stops on some of them. [What Ergo does](https://github.com/kosli-dev/ergo/blob/rego-v0.1.0/README.md#what-ergo-does) in the README says the rest, and the [tutorial](https://ergo.kosli.com/tutorial/) teaches the sentences with a bakery.
