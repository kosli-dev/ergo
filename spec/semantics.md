# How Ergo turns a policy and an input into a report

Draft 0.3. This file says what a check means, whatever syntax it's written in. [syntax.md](syntax.md) says how a policy is written, its sentences included, how it can be written wrong, and how the report names paths. It covers reading values, causes, every operator of the model, and how requirements, scope, statuses and violations work. Questions the spec hasn't settled are in [OPEN.md](OPEN.md).

Each rule has a name in brackets, like `[present.missing]`. The cases in [`cases/`](cases) list the rules they test, so you can find the cases for a rule and the rule behind a case. An implementation follows every rule here, and where it does something else, it's wrong, whatever `ergo.rego` does.

## Terms

- The **input** is the JSON document being checked.
- The **params** are a second JSON document the policy can read, or nothing.
- A **subject** is one thing a requirement checks, found in the input by the `from` of the subject definition it names.
- A **check** is one named test in a requirement's `checks`. A condition after `whose` or `that` in a subject's `from` line is a check too, called a **filter**.
- A **row** is the result of one check on one subject, or of one check Ergo adds to a requirement.

## The model of a check

A syntax reads each check into this model. Everything below is said in terms of it.

- A **check** has an operator, like `equals` or `every`, and the parameters that operator takes.
- A **path** has a start and a list of steps. It starts at the subject, at the input, at the params, or at an alias given by a subject's `from` or by an enclosing list check.
- A **step** is a key (a string, which reads a key of an object), an index (a whole number from 0 to 9007199254740991, which reads an item of a list), or a ref step (a ref whose value is the key, which has to be a string, so a ref step never reads an item of a list).
- A **value** is a JSON value or a ref.
- A **ref** is a path that starts at the input or the params and whose steps are all keys or indexes.

**[written_wrong]** A check that can't be read into this model is written wrong. The requirement's `$well_formed` row fails with cause `value` and lists what's wrong, and the requirement gets no other row, as [well_formed](#requirements) says. [syntax.md](syntax.md#written-wrong) says what counts as written wrong in a sentence, and [written_wrong.row](syntax.md#written-wrong) how it's reported.

## Reading a path

Reading a path ends in one of these outcomes. Each one except `found` is also a [cause](#causes).

| Outcome         | When                                                                                                                     |
| --------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `found`         | Every step was read, and the value at the end isn't `null`.                                                              |
| `null`          | Every step was read, and the value at the end is `null`.                                                                 |
| `absent`        | A key isn't in its object, an index is past the end of its list, or a step comes after a value that's missing or `null`. |
| `unusable`      | A step comes after a value that can't hold it, or a number can't be read or compared exactly, see [Values](#values).     |
| `not_an_object` | The path reads a field of a subject that isn't an object.                                                                |

**[path.start]** A path starts at the subject, the input, the params or an alias. With no params, or with `null`, a path into the params ends `absent` and its message says it is missing, like `$params.a is missing`. Params that are there but aren't an object fail the whole report, as [REFERENCE.md](../REFERENCE.md#params) says. A path into them that stops on them names them in its message, like `$params is 3, which isn't an object` for `$params.a is 1`. A path that starts with a position, like `every $params[0].a is 1`, says `$params is 3, which isn't a list`, and one that reads a position that is there and then a key says what it found at the position, `item 1 of $params is 3, which isn't an object`. A check that reads them whole, like `x is in $params`, or reads a value that is there, like `x is $params[0]` with `[[1]]`, says what it says with any params, here `x is 1, which isn't a list`. The `from` line of a subject that isn't a child subject, when it reads them with `named by each of` or a `named by` step, like `things named by $params.env`, makes no subjects, and its `$min_subjects` row names them in the same way: `things named by each of $params.ks` says `$params is 3, which isn't an object`, and `things named by each of $params[0]` says `item 1 of $params is 3, which isn't a list of text` with `[3]`, and `$params is [["k"]], which isn't an object` with `[["k"]]`, where the list of keys is there. A child subject's `from` line that reads them that way, like `t.m named by $params.env`, and a `from` line that reads them in a `whose`, like `things whose id is $params.x`, don't name them yet: their `$min_subjects` row still fails as `unusable`, with a message about something else, like `in-scope k count is 0`.

**[path.not_an_object]** A path with steps that starts at a subject that isn't an object ends `not_an_object`, `null` subjects included, unless its first step is a position, or it walks a subject that is a list as [walk.start](#every-and-some) says. A position reads the subject as a list, as [path.absent](#reading-a-path), [path.null](#reading-a-path) and [path.unusable](#reading-a-path) say, so `first of it` ends `absent` on `[]`, `null` on `null`, with the subject's name in the message, like `region is null`, and `unusable` on `"s"`. A path that starts at a `for` alias or at `$input` is read the same way. That holds with a `named by` after it too, like `$input named by key` or `$input.m named by key`, on the left or on the right of a phrase, and for `$input.k` read inside a relative clause, which is said once with no item. It holds whatever the key after `named by` holds, so `$input.m named by $params.k` and `$input named by $params.k` end `not_an_object` when `k` is missing, `null` or not text, and a path whose key is read from such an input, like `m named by $input.k`, ends `not_an_object` too ([path.ref_step](#reading-a-path)). So on the input `[{"id": "a"}]`, `$input.id exists` ends `not_an_object` and says `$input is [{"id": "a"}], which isn't an object`, and so do `k is m named by $input.k` and, with no `k` in the params, `k is $input.m named by $params.k`. The cause is `not_an_object` in both engines for every plain check, but the message is the one above only in the forms the cases pin: a few plain forms say something else in one engine or in both ([OPEN.md](OPEN.md#where-ergorego-and-the-rust-engine-differ)). On `[1]`, `$input[0].id is "a"` ends `unusable` and says `item 1 of $input is 1, which isn't an object`. A key read from such an input, like `m named by $input.k`, ends the path `not_an_object` in every sentence, as [problems.same_path](#which-problems-a-message-says) says, and the `$applies` row of a `from` line whose condition reads it fails as `not_an_object`. A `from` line whose path or `named by each of` list reads such a key, like `$input[0].m named by $input.k` or `$input named by each of $input.ks`, fails its `$min_subjects` row as `not_an_object`, unless the params aren't an object, which fails it as `unusable`. The check says `$input is [...], which isn't an object` once, with the input written out and no item in front: on the input `[{"k": "a", "m": {"a": "a"}, "rs": [{"v": "a"}]}]`, `every rs.v is m named by $input.k`, `some rs whose v is m named by $input.k exists` and `count of rs whose v is m named by $input.k is 1` each say `$input is [{"k": "a", "m": {"a": "a"}, "rs": [{"v": "a"}]}], which isn't an object`, and the `failures` of the `every` and the `some` list each item as `not_an_object`. The same goes for a list of a `for` line that reads such a key and for a `whose` there, like `every rs as r, every ls named by $input.k as g` and `every rs whose v is m named by $input.k as r`, which say nothing about the items. When the params aren't an object either, a check that reads them says it once after the input, like `$input is [...], which isn't an object, and $params is 3, which isn't an object` for `count of rs.v that is $params.m named by $input.k is 1`, and says nothing about the items. On a `for` line, a sentence with a `sum of`, a `count of` or an `add` then names each item that isn't an object by its value, like `item 1 of xs is 1, which isn't an object` for `sum of x.m named by $input.k is 1` with `xs` holding `[1]`, and `item 1 of xs is null, which isn't an object` with `xs` holding `[null]`. What the key holds matters only for a path that starts at `$input` and takes its key from elsewhere, like `$input.m named by $params.k`, which ends `not_an_object` whatever `k` holds in a check that doesn't go through a list item by item, whatever the other checks of its requirement are. A one-line `every` or `some`, a `for` line, a `count of` or `sum of`, a child subject's checks and the `whose` of a `from` line don't follow that yet, and neither does an `any_of` or a multi-sentence check that holds one of them, whose plain options keep the key's cause, like `a: $params.k is 3, which isn't text`. There `$input.m named by $params.k` ends with the key's outcome, like `absent` when `k` is missing, in `k is $input.m named by $params.k` on a child subject, in the `whose` of a `from` line and on a `for` line, and so does `count of $input.m named by $params.k`, which walks the input as [path.field_step](#reading-a-path) says for a walked list. Other such forms aren't settled yet ([OPEN.md](OPEN.md#where-ergorego-and-the-rust-engine-differ)).

**[path.absent]** A key the object doesn't have ends `absent`, and so does an index past the end of the list. Once a value is missing partway along, the path ends `absent`, however many steps are left.

**[path.null]** A path whose last step reads `null` ends `null`, and so does a path that meets `null` partway along: the read stops there, however many steps are left, and the message names the step that is `null`. With the subject's `c` `null`, `c.z is 1` fails as `null` with `c is null`, and the same goes for a part, `$input`, `$params`, a parent and an alias: `pl.z is 1` with the part `pl` `null` says `pl is null`, and `$input.c.z` with `c` `null` says `$input.c is null`. The row's `inputs` still name the whole path, with the location of the `null`. A key read from a field is read when its step is reached, as [path.field_step](#reading-a-path) says, and a ref step is read first, as [path.ref_step](#reading-a-path) says, so a key that can't be read still decides when nothing before it stops the path. A key that can't be read after the `null` is named too, in the order [problems.item_order](#which-problems-a-message-says) gives: `s.x named by p` with `s` `null` and `p` `3` says `p is 3, which isn't text; s is null`.

**[path.unusable]** A key on anything but an object, or an index on anything but a list, ends `unusable`. So does any step after a string, number or boolean. So the key `y` on `"x": "a"` and on `"x": [{"y": 1}]` ends `unusable`, and the index `1` on `"x": {"1": "a"}` does too.

**[path.ref_step]** A ref step reads its ref first and uses the value as the key for that step. A path can break in more than one place, and each problem is said: when the ref ends anything but `found`, the value before the step is read too, and when it can't take a key, because it is missing, `null` or not an object (not a list or an object where the path is walked), that is a problem as well. The key and the value before it are roots of the sentence, so they are said worst cause first and then by name, as [problems.item_order](#which-problems-a-message-says) says, and a list that a walk, a `count of`, a `sum of`, a `for` line or a `from` line walks is said after the roots, as [problems.all_said](#which-problems-a-message-says) says. The path's outcome is the worst of them, in the order of [causes](#causes). Each keeps its own input with its own outcome. So `k is m named by $params.k` with no `k` in the params and `m` holding `"s"` fails as `unusable` with `m is "s", which isn't an object; $params.k is missing`, with `m` `null` as `absent` with `$params.k is missing; m is null`, and `every o named by $params.k is 1`, `count of o named by $params.k is 1` and a `for` line or `from` line that reads `o named by $params.k` with `o` holding `"s"` fail as `unusable` with `$params.k is missing; o is "s", which isn't a list or an object`. An empty list fails a walk, so `every o named by $params.k is 1` with `o` `[]` says `$params.k is missing; o is []` and fails as `absent`, but not with `, if any,` and not in a `count of` or `sum of`, which add nothing for it. A key read from a field isn't a ref step: it follows [path.field_step](#reading-a-path). The path's outcome is the check's, so in a check that reads two paths the worse of the two outcomes wins, as [compare.fail](#compare) says, wherever the ref starts: `k is m named by $params.k` with no `k` on the subject, `m` an object and `$params.k` `null` fails as `absent`, with `k is missing, and m named by $params.k is null`, and with a `k` on the subject it fails as `null`, with `$params.k is null`. A side that works out a number, an `add`, a `count of` or a `sum of`, does the same when the key is missing or `null` ([tally.fail](#counts-and-sums-in-sentences)): with no `k` and no `zzs` on the subject, `m` an object and `$input.k` `null`, `k is 1 plus m named by $input.k` fails as `absent` with `k is missing, and m named by $input.k is null`, and `count of zzs is m named by $input.k` with `zzs is missing, and m named by $input.k is null`. So does a one-line `every` or `some`, where `every rs.zz is m named by $input.k` with no `zz` on the items fails as `absent` with `item 1 of rs: zz is missing; item 2 of rs: zz is missing`, and the sentence of a `for` line, where `r.zz is m named by $input.k` fails as `absent` and says `$input.k is null; item 1 of rs: r.zz is missing`. In the `whose` of a `count of` the key is said once, before any item, and each item takes the cause of its own paths ([tally.whose](#counts-and-sums-in-sentences)), and the condition of a `from` line does the same, so its `$applies` row says `k is missing`, naming only what is in the state of its cause ([message.cause](#messages)). A ref that starts at `$input` on an input that is a list, like `$input.k`, ends `not_an_object`, so the path does too, in every sentence and in a `from` line, and the check says `$input is [...], which isn't an object` once, as [path.not_an_object](#reading-a-path) says. Only a string is a key, so a value that isn't one ends `unusable`, a whole number included: `m named by $params.k` with `k` holding `1` and `m` holding `[5, 1]` ends `unusable` and doesn't read `1`.

**[path.field_step]** A field step reads one field of the value a bare name resolves against at that point ([sentence.resolve.root](syntax.md#where-a-name-resolves)), the subject or, inside a relative clause, the focus, and uses it as the key for that step. So on the right side of a one-line `every` or `some`, `m named by k` reads the subject's `k`, and so does a path there that starts at a part, a parent, an alias, `$params` or `$input`: `every xs.v equals $params.m named by k` reads the subject's `k` and never an item's, so a `k` that's missing, `null` or not text fails the row once, as the plain check does, with `k is missing`. The steps before the field are read first, so when one is missing or can't be read the path ends as it does, and the field doesn't decide the cause: `$params.m named by p` with no `m` in the params is `absent` whatever `p` is. A field that can't be read, missing, `null` or not a string, never lets a check pass, even `does not exist`, whatever the steps before it hold: `x[0] named by zz does not exist` with no `x` fails as `absent` when `zz` is missing, `null` or a number, and passes only when `zz` is text. A `null` before the field doesn't stop the path before the field is read, and the message names the step that is `null` and the field when it can't be read, in the order [problems.item_order](#which-problems-a-message-says) gives: `s.x named by p` with `s.x` `null` is `null` with `p is null; s.x is null` when `p` is `null`, and `null` with `s.x is null` when `p` is a string, as `s.x.k` is. A `null` further back is named first the same way, as [path.null](#reading-a-path) says: with `s` `null`, `s.x named by p` is `null` with `p is missing; s is null` when `p` is missing, and with `s is null` when `p` is a string, and `x[0] named by zz does not exist` with `x` `null` fails as `null` with `zz is missing; x is null` when `zz` is missing. In an `every`, `some`, `count of`, `sum of` or a `for` line, a list before the field is walked, not read, so it doesn't stop the path: `every rows.w named by k` is `null` when `k` is. A `null` there, before the value the field picks from, ends the path `null` whatever the field holds, as the walk does without the field: `every rows.w named by k` with `rows` `null` is `null` when `k` is missing or a number too, and its `failures` has `rows` as a `list` entry, as the walk without the field does. Where nothing walks it, a list before the field can't be read, so the path ends `unusable` whatever the field holds: `rows.w named by k is "xy"` with `rows` a list is `unusable`. Otherwise a field that's missing ends the path `absent`, a `null` one `null`, and one that isn't a string, a number included, `unusable`. On a subject or item that isn't an object, the path ends `not_an_object`. That includes a path that reads inside an alias that isn't an object, like `w.k named by zz` with `w` a list, which ends `not_an_object` whatever `zz` holds. When the steps before the field can be read, the field decides first, as above, even when the value read is not an object: `w named by zz` with `w` holding `3` is `absent`, `null` or `unusable` when `zz` is missing, `null` or not a string, and `not_an_object` when `zz` is text. An alias that is a list, read by a position and then by a key from a field, like `w[0] named by zz`, is read as a list: the steps before the field are read first, and the field decides as above. The step is part of its path, as a `named_by` step is, so in a check that reads two paths, the other path's cause can come first, as it can for a ref step ([path.ref_step](#reading-a-path)). The row's `inputs` show the field too, unless it's read on an item, as the entry right after the one of the path that reads it, wherever that entry goes: `m named by p is q` lists `m named by p`, `p` and `q`, `q is count of m named by p` lists `q`, `count of m named by p`, `m named by p[]` and `p`, and an `every` or `some` lists the field right after the list it walks. A `for` line's check lists the field too, among its entries sorted by name, as [for.inputs](#for) says. Sentences write such a step as `<path> named by <field>`.

## Causes

Every row has a cause. When a check reads several values, the row takes the first cause in this order:

1. `satisfied`
2. `not_an_object`
3. `ambiguous`
4. `unusable`
5. `absent`
6. `null`
7. `value`

`satisfied` means the row passed. Every other cause means it failed. `value` means everything was read and the values didn't pass. `ambiguous` means a position on a `for` line picked items that tie, see [for.pick](#for), and the other causes are the outcomes of reading a path.

## Values

**[value.equal]** Two values are equal when they have the same type and the same content. Numbers are compared by value, so `1` equals `1.0` and `1e0`. Strings are equal when they hold the same code points. Lists are equal when they have the same length and equal items in the same order, and objects when they have the same keys with equal values. `"1"` doesn't equal `1`, and `[1, 2]` doesn't equal `[2, 1]`.

**[value.ref]** A value that's a ref is read from the input or the params, and the check runs with the value it reads. If the ref ends anything but `found`, the check fails with the ref's outcome as its cause, whatever the subject holds. A ref that reads `null` fails it as `null`, even when the field is `null` too. A value read through a ref is data, so nothing inside it is read as a ref.

**[value.refs]** A check that has refs gets `$refs` in its definition in the report: one entry for each ref, named as in [syntax.md](syntax.md#naming-a-path), with the value it read, or `null`. They're sorted by name. A ref is every path from `$params` or `$input` the check reads, wherever it is in the sentence: on either side of `is`, `is at least` or another comparison, after `is in` or `contains`, after `count of` or `sum of`, the list `every` or `some` walks, a piece of `followed by`, a key after `named by`, in a `whose`, on a `for` line and in an `any_of` option. So `v is $params.x.y`, `count of $params.q is 1` and a `for` line's `every $params.q is 1` each list their path, like `{"name": "$params.q", "value": [1, 2], "locations": ["$params:/q"]}`. A path that walks a list on the way, like `$input.sbom.components.name` after `is in`, or `$params.objs.x` that `every`, `some`, `count of`, `sum of` or a `for` line walks, is listed as [walk.right.inputs](#compare) says, like `{"name": "$params.objs[].x", "value": ["y"], "locations": ["$params:/objs/0/x"]}`, and has no entry of its own as written. The same path read without a walk, like `v is $params.objs.x`, has an entry for that read too. A path with `named by` is listed as the path before `named by`, with its whole value and where that was read, wherever it is in the sentence, since the part it picks can differ for each subject: with params `{"m": {"x": "a", "y": "b"}}`, `v is $params.m named by k` lists `{"name": "$params.m", "value": {"x": "a", "y": "b"}, "locations": ["$params:/m"]}`. The part each subject picks stays in its row's `inputs`, and a key read from `$params` or `$input` after `named by` is listed as a ref of its own. When the path before `named by` is missing, `null` or of the wrong type, it is listed as any path is: `null` and where the read stopped, or what it read. A path written in a check's `meta` or `description` isn't listed. The `$applies` entry of a `from` line's conditions lists fewer for now: a list or patterns after a phrase like `is in`, `contains all of` or `matches`, a key after `named by` and a piece of `followed by`, so `things whose n is at least $params.p` gives it no `$refs`.

**[value.number]** Two numbers are compared on every digit, however many they have, so `1234567890.1209567990` is more than `1234567890.1209567890`, and `0.1` equals `0.10000000000000000000`. That goes for every check that compares numbers, a list item, a copy that `distinct` drops and a number a message quotes, and a row gets the same answer whatever the other rows hold. A number in the policy has at most 15 significant digits, or it's written wrong ([sentence.value.scalar](syntax.md#values)), so only the input and the params hold longer ones. An implementation has to read them without losing digits: one in JavaScript or Python reads the JSON from its text, like the `source` that newer versions of `JSON.parse` pass to a reviver, or Python's `json.loads` with `parse_float=decimal.Decimal`.

The spec only covers numbers in the input and the params that are `0` or have a magnitude between `2.2250738585072014e-308` and `1.7976931348623157e308`, the range of a 64-bit float. Ergo doesn't control the input or the params, so the spec doesn't say what happens to any other number. An implementation compares such a number and writes it in the report as its runtime does, or fails the check as `unusable` when it can't read or compare the number exactly, like one whose exponent is too long to hold. So reports may differ between implementations. `ergo.rego` compares it exactly up to an exponent of ±1e6, see [OPEN.md](OPEN.md#numbers-with-huge-exponents), and copies it as written, while one in JavaScript reads `1e400` as `Infinity` and `1e-400` as `0`.

## What a row shows

**[path.inputs]** A check that reads one path, like `present`, `missing`, `equals` or `in`, has one entry in its row's `inputs`: the path's name and the value read, or `null` when nothing was.

**[path.right_inputs]** A check that also reads a list of values or patterns from a path, like `x is in $params.l`, `x contains all of $input.required` or `x matches $params.patterns`, lists that path in its row's `inputs` right after the entry of the path it checks, as [compare.inputs](#compare) lists the right side of a comparison: the path's name, the value it read or `null` when nothing was, and where. It does so whatever the cause, so a list that is missing, `null` or isn't a list is listed too, and the entry is the one the same path has after `is at least`. A path that walks lists is named and holds what [walk.right.inputs](#compare) says. A list written in the sentence, like `x is one of "a", "b"`, isn't read, so it has no entry. The path stays in the check's `$refs` ([value.refs](#values)). The rows of `every`, `some` and `count of` list such a path where they list the right side of `is at least`: one from `$input` is listed, like `$input.l` in `every xs.n is in $input.l`, and one from `$params` isn't, as [walk.inputs](#every-and-some) says. A `for` line's own row lists one from either, like `$params.l` for `x.n is in $params.l`, as [for.inputs](#for) says.

**[row.parts]** A failed row lists every part that failed, at every level, in the same way wherever it sits, in its `failures`. A part is an option, an assertion, or an item of a list that a sentence, `for` line or `from` line walks, or that list when it fails while walking. A passed row has no `failures`, `message` or `outcome`. `failures` replaces `failed_items`, `failed_assertions` and the second list's `items`, on every row, an `$applies` row too, and inside entries. Every failed `$min_subjects` row has `failures` too, in place of `failed_items`, `[]` when it has no entries, whatever its `from` line, and so does every failed `$unique_ids` and `$unique_ancestor_ids` row, with an entry for each subject without an id ([unique_ids](#requirements)). With `every`, each place [subjects.every.broken](#requirements) names is a `list` entry when the list itself failed, like `sbom.components` with the input `sbom.components`, or an `item` entry when it broke inside an item, like `item 2 of builds` with the input `builds[1].version`. The row's `inputs` keep the count, and add the read of a list that failed and any key of the line that can't be read.

Each entry has `kind`, `name`, `cause`, `inputs`, `failures` and `message`. `failures` holds the parts under it that failed, and is `[]` at a leaf, and `inputs` is `[]` when the part read nothing itself. `kind` is `option`, named by the option's name. Or `assertion`, named by the sentence as written, so a one-sentence check has one assertion entry too. Or `item`, named like `item 2 of xs`, or `item 1 of w.ys` for a second list. Or `list`, a list that failed while walking, because it is missing, `null`, not a list, or empty where that fails, named as the message names it, like `xs` or `x.ys`. An `every` or `some` whose `whose` leaves no item, and that fails because of it, has a `list` entry too: `every xs whose k is 1 exists` on `[{"k": 2}]` has a `list` entry `xs` with the message `xs is [{"k": 2}]`, the cause `value` and the input `xs` holding the list, with the `outcome` `usable`, and its assertion says `""`. A `named by` key that can't be read, because it is missing, `null` or not text, is not a `list`: the problem is the key's, said once on the assertion, with the key as its input, like `$params.env` with `outcome` `absent` and the message `$params.env is missing`, whether the key sits in a walked path or a `from` line. A key on a `for` line is read by the line, so it sits on the row instead: the row's `inputs` hold the key with its `outcome`, and the sentences that read an alias have no entry, because they never ran. With no `k` in the params, `for: every o named by $params.k as x` with `x is 1` and `x is 2` says `$params.k is missing`, and its `failures` is `[]`. The list before the key is still read without it: when it fails whatever the key is, because it is missing, `null`, not a list or an object, or empty where that fails, it is said after the key and has a `list` entry, on the row for a `for` line and under the assertion for a one-line walk, and the row takes the worse cause. With `o` holding `"s"`, both say `$params.k is missing; o is "s", which isn't a list or an object` and fail as `unusable`. On a second `for` list, each item of the first list whose list fails like that is said after the key, like `$params.k is missing; item 2 of ws: w.o is missing`. `failures` is `[]` only when the list itself is fine. A root that a `for` line reads in its own `whose` is read by the line too, once, before any item ([for.roots](#for)), so it sits on the row's `inputs` with its `outcome`, like a key, and is said once in the row's message. It is never a `list` entry, which is only for a list that failed itself: `for: every xs whose v is in $params.l and whose w is in pr.l as m`, with `pr.l` holding `"s"`, `$params.l` `null` and `xs` holding `[{"v": 1}]`, has `pr.l` with `outcome` `unusable` and `$params.l` with `outcome` `null` in the row's `inputs`, and no `list` entry `xs`.

An entry's `cause` is its own: the worst of its own problems and of the entries under it, in the order [Causes](#causes) gives. Only the row takes the worst of all. So in the `for` line above, `item 1 of xs` fails as `absent` with `w is missing`, and the row fails as `unusable`, from `pr.l`.

Entries come in one order of levels everywhere: the row, then the options or the assertions, then under an option its assertions, then items, then the items of a second list. Options come by name and assertions as written. Under one assertion the `list` entry comes first and then the items in list order ([problems.all_said](#which-problems-a-message-says), [problems.item_order](#which-problems-a-message-says)). A list walked inside an item sits under that item, so `every pull_requests.commits.signed is true` has `item 2 of pull_requests` holding `item 1 of commits`. A `for` line puts its items under each sentence, not the other way round, so an item that fails two sentences is under both. The one exception is what the `for` line's own walk breaks before any sentence is checked ([for.shared_failures](#for)): it sits on the row once, after the assertion entries, and so an item can sit directly under the row.

An entry's `inputs` hold only what that part read at its own level, in the order its own row would give them ([for.failure_inputs](#for), [compare.inputs](#compare), [tally.inputs](#counts-and-sums-in-sentences)). An assertion holds what it read outside its items, like `$params.min` or the value of a `count of`. The list a sentence walks is never one of them, in any form: when the list fails, its own read is on its `list` entry, and when it reads fine, what was read on its items shows in the row's own `inputs`. So `every xs.ys.n is 1` on `{}` has an assertion with the `inputs` `[]` and under it the `list` entry `xs`, alone in its check, beside other sentences and in an option alike, and `count of o named by $params.k whose k is 1 is 3` doesn't list `o named by $params.k`. An item holds what was read inside it, named with its position, like `xs[1].v`, or through the alias as written, like `x.v`, or the item itself, like `xs[1]`, when the sentence reads the whole item. A list holds its own entry. A problem sits at the level [problems.where_said](#which-problems-a-message-says) puts it: something read outside the item sits on the assertion, once, and items hold only their own problems. An item that a `count of` didn't count, or that made a `sum of` differ, is not a failed part. An item that couldn't be read is, whatever its cause, and so is a list under it that failed while walking: each is an `item` entry under the assertion, in list order, and the assertion and the row take the worst cause among them. With `xs` holding `[{"v": null, "k": 1}, {"k": "z"}, {"v": 2, "k": 1}]`, `sum of xs.v is 5` fails as `absent` with `item 1 of xs: v is null; item 2 of xs: v is missing`, and its assertion entry has the message `""`, the input `sum of xs.v`, and the items `item 1 of xs` (message `v is null`, input `xs[0].v` with `outcome` `null`) and `item 2 of xs` (message `v is missing`, input `xs[1].v` with `outcome` `absent`). `count of xs whose k is 1 is 3` has `item 2 of xs`, with the message `k is "z", which isn't a number` and the input `xs[1].k` with `outcome` `unusable`.

A sentence has the same entries under its assertion wherever it sits: alone in its check, beside other sentences in an `assert` list, in an option of an `any_of`, as a condition of an `$applies` row with other conditions, or on a `for` line. So `assert: ["every xs.ys.n is 1", "z is 3"]` on `{"z": 2, "xs": [{"ys": [{"n": 1}, {}]}]}` has, under `every xs.ys.n is 1`, the item `item 1 of xs` (message `""`) holding `item 2 of ys` (message `n is missing`, input `xs[0].ys[1].n`), as the check with only that sentence has, and `z is 3` is its own entry. On a `for` line, the items a sentence walks sit under the item of the `for` line they belong to, one entry for each list level. The list is named as it is written, with the alias, so the entry name and the lead in the message are the same string, and an input is named as written too, with the alias kept and the position filled in: under `for: every xs as x`, `every x.ys.n is 1` on `xs` holding `[{"ys": [{"n": 1}, {}]}, {}]` has `item 1 of xs` (message `""`) holding `item 2 of x.ys` (message `n is missing`, input `x.ys[1].n` with `outcome` `absent`), and `item 2 of xs` (message `""`) holding the `list` entry `x.ys` (message `x.ys is missing`, input `x.ys` with `outcome` `absent`). A deeper list is named as in a plain walk, without the alias, so `every x.ys.zs.n is 1` gives `item 1 of xs` holding `item 1 of x.ys` holding `item 2 of zs`, with the input `x.ys[0].zs[1].n`. The item of the `for` line holds, as its own `inputs`, only what the sentence read through its alias outside those items, like `x.min` in `every x.ys.n is at least x.min`, and the value a `count of` or a `sum of` works out on it, like `sum of w.xs.v`, as an assertion does in a check of its own.

Every path a sentence reads is an input of the entry at the level that read it, when that entry exists: the row (the `for` line's own walk and its keys), the assertion (roots read outside the items), an item (what is read inside it), or a `list` entry (the list's own read). A path read through an earlier list's alias belongs to that list's item ([problems.where_said](#which-problems-a-message-says)). This holds in every form (plain check, one-line walk, `for` line, second list, `from` line condition, `$applies`), whether the list is empty or not ([for.roots](#for) reads roots once, before any item, even then). The input's `outcome` is how reading it ended, the worst problem along it, with `found` becoming `usable`, or `unusable` when the check can't use the value. A root read through a list ends with the worst problem of its items: `every ws.n whose v is in pos.name is 2` with `pos` holding `[{"name": "bob"}, {}]` reads `pos[].name` as `["bob", null]` with the outcome `absent`, on the assertion and on the row. Its `locations` say where the read stopped ([location.read](#where-a-value-was-read)). Every problem is said, the roots of a sentence worst cause first and then by name. An item that is fine has no entry, so its reads show only in the row's own inputs. So `for: every xs as x` with `x.v is at least z` and `z` holding `"s"` lists `z` with `outcome` `unusable`, on the row and on the sentence, as it lists `$params.z` in `x.v is at least $params.z`, and on an empty `xs` the sentence still lists `z`. A key from outside the items in a `whose` sits on the assertion, or on the row for a `for` line, and an item that says the value before the key has that value as its input, cut where the read stopped, like `xs[1].m`, with the worst outcome along the path.

A `count of` or a `sum of` whose list fails before any item is read, because it is missing, `null`, not a list or an object, or a value before a `named by` key that can't take a key, has a `list` entry under its assertion, as `every` and `some` do, and the list isn't an input of the assertion: `count of o is 1` with `o` holding `"s"` has an assertion entry with the input `count of o` and the message `""`, and under it a `list` entry `o` with the input `o`, `outcome` `unusable`, and the message `o is "s", which isn't a list or an object`. A `list` entry's input is the list's own read, as an `every` over the same list gives it: the value it read, `null` when the list is missing, and `locations` where the read stopped ([location.read](#where-a-value-was-read)), like `/things/0` for a missing `xs` and `/things/0/xs` for a `null` one. The same goes for a list under the item of a `for` line, like `x.ys` or `w.xs`. This holds in a plain check, in a sentence of an `assert` list or of an `any_of` option, and in an `$applies` row. When the list reads fine, what was read on its items isn't an input of the assertion either, so `count of xs whose v is 1 is 2` on two items has only `count of xs whose v is 1` there, and `xs[]` shows in the row's `inputs`.

An item also has `value`, the item or what its alias stands for, and `locations`, where it sits in the input, every copy for `distinct` ([location.failed_items](#where-a-value-was-read)). Items tied on a sort key, and items whose sort key can't be read or is of mixed kinds, are items like any other, and the sort key is one of their inputs, named with its position, like `commits[0].timestamp`. An item of a second list that the `whose` can't read is a failed part too, with the read as its input, and the row's message says it as a one-list line does, like `item 1 of envs: item 2 of deploys: env is missing`.

An option and an assertion have `locations` in the policy: `$policy:` and a JSON Pointer from the root of the policy, like `$policy:/requirements/r/checks/c/any_of/approved exception/1` or `$policy:/subjects/t/from`. When one string holds several sentences, joined with `and` or on a `from` line, each gets `#N` for its number in that string, counted from 1, like `$policy:/requirements/r/checks/c/assert/2#1`. There are no character positions.

Each entry's `message` is what the row's message says about that part, without the names in front, or `""` when it says nothing itself. So a part whose text all comes from the entries under it says `""`, an option included: with the options `a: every xs.v is 1` and `b: ["z is 3", "every xs.v is 2"]`, on `{"z": 2, "xs": [{"v": 2}, {}]}`, both options say `""`, the text sits once on the entries under them, and the row says `a: item 1 of xs: v is 2; item 2 of xs: v is missing; b: z is 2, and item 2 of xs: v is missing`. It is what that part says on its own, so with `x is 1` and `x is 2` and `x` at 5, both entries say `x is 5`. The row's message is built from them with the prefixes [message.join](#messages) gives: every clause of the row's message comes from an entry, and one that several entries give is said once. Every entry shows up in the message, apart from the items after the third, which the message counts in `and N more`. That count is the same as [message.items](#messages) gives: items, or pairs of items on a two-list `for` line, never sentences. `failures` itself lists every item.

An input's `outcome` is how reading its path ended, as [Reading a path](#reading-a-path) says, with `found` becoming `usable`, or `unusable` when the value was read fine but the check can't use it. So the values are `usable`, `unusable`, `null`, `absent` and `not_an_object`, and never `found` or `value`: whether the check passed stays in `cause`. With `x is at least y` on `{"x": "1", "y": 2}`, the row fails as `unusable`, `x` has outcome `unusable` and `y` has `usable`, even though the check stopped before comparing it. On a failed row every input that reads a path has `outcome`, in the row's `inputs` and in those of each entry. A value Ergo works out, like a `count of`, a problem list or `require` has none. Every entry of a check's `$refs` has `outcome` too, always, one answer for each ref, so [violations](#violations) copies it into each violation's inputs.

**[row.inputs_once]** A row shows each entry of its `inputs` once. When a check reads the same value twice, like `count of approvals plus count of approvals is 4`, the second read gives no entry of its own when its name, its value and its locations all match the first's, as [location.merged](#where-a-value-was-read) says, and the rest keep their order.

## Messages

**[message.row]** Every failed row has a `message`, a line of plain text that says what Ergo found, never what the check expected, so someone who doesn't read policies can follow it. A row that passed has none. The message is worked out from the policy and the input only, so the same report gives the same messages.

**[message.value]** A row that failed with cause `value` names each value it compared, as `<name> is <value>`, and joins them with `, and `, in the order of the row's `inputs`: `x is 4`, or `approver is "ana", and author is "ana"`. The name is the input's name as the row's `inputs` show it.

**[message.cause]** A row that failed with any other cause names only the inputs in that state, except that a check's own row that fails as `absent` or `null` names every input read from the subject or an item that is missing or `null`: `c.z is d.z` with `c` `{}` and `d` `null` says `c.z is missing, and d is null`. `absent` reads `<name> is missing`, `null` reads `<name> is null`, `unusable` reads `<name> is <value>, which isn't <kind>`, like `x is "3", which isn't a number`, and `not_an_object` reads `<name> is <value>, which isn't an object`, where the name for the subject itself is the subject's name, like `region`, and `the subject` where a report has no name for it. `ambiguous` names the items that tie and the key they were sorted by: `item 1 and item 2 of commits tie on ts`. On a `for` line with two items, a tie in the second list names the key of the second item, and a tie in the first list the key of the first: `item 1 and item 2 of p.items tie on hi` under `first of ws sorted by w as p, first of p.items sorted by hi as q`.

**[message.print]** A value is printed as JSON, with `, ` between items and `: ` after keys, and keys sorted. Text over 60 code points keeps its first 60 and ends with `…"`. A list over 3 items shows its first 3 and then `and N more`, as in `["a", "b", "c", and 2 more]`. An object whose JSON is over 80 characters prints as `an object with N keys`, or `an object with 1 key`. A line separator (U+2028, U+2029 or U+0085) inside text, or inside a name, is written as `\u2028`, `\u2029` or `\u0085`, so a message stays on one line.

**[message.worked_out]** A value Ergo works out, like a `count of`, a `sum of`, a `plus` or an elapsed time, is printed as the number it gave, under the name of that side, not as the values it came from: `count of tests is 1`, `sum of items.n plus extra is 12`.

**[message.followed_by]** A side written with `followed by` is printed as the text it joins to: `spec is "v0.4", and "v" followed by version is "v0.4.1"`.

**[message.items]** An `every` or `some`, and a `for` line, lists only the items that failed, each as `item N of <list>: ` and what was found there, counted from 1, and joined with `; `: `item 2 of tests: ok is false; item 3 of tests: ok is missing`. An item of a list in a list names both. On a plain walk, which has no alias, the inner list is named without the outer item: `item 1 of commits: item 2 of reviews: ok is false`. On a `for` line it is named as written, with its alias: `item 1 of prs: item 1 of pr.meta.cs: c.ok is null`. When no step sits between two positions, like `x[0][0]`, the inner list is named `it`: `item 1 of x: item 1 of it: item 1 of it is 1, which isn't an object`. After three items, the message ends with `; and N more`, where N counts items, or pairs of items on a `for` line with two items, and never sentences. On a `for` line over one list, the part of a sentence that doesn't walk a list goes with its item, whenever the item is shown, and isn't counted. The inputs of an item in `failures` keep their paths as they were, like `xs[1].v`, and the entry names and messages say the same as the row's message ([row.parts](#what-a-row-shows)). On a `for` line, an item that isn't an object, where a `whose` reads a field of it, is named like a sentence names it, with no colon: `item 2 of commits is null, which isn't an object`. A `for` line on a subject that isn't an object names the subject the same way, `thing is 3, which isn't an object` with subject `thing`. Within an item, what a sentence found in the items of a list under it comes before a part it couldn't read: `item 1 of ws: item 2 of items is null, which isn't an object; item 1 of ws: cov.x is missing`. In a sentence, a `count of`, a `sum of` or a `whose` that reads an item that isn't an object, `null` included, names it as `item N of <list> is <value>, which isn't an object`, like `item 2 of commits is null, which isn't an object`. When the focus is past the list, the message names the item of the list, then the rest of the path after a colon, then what was found: `item 1 of approvers: username is "ann", which isn't an object`, `item 2 of approvers: username is missing`, and on a `for` line `item 1 of xs: item 2 of ys: z is "s", which isn't an object`. `item N of <list> is <value>, which isn't an object` stays for a focus that is the item itself. A `count of` or `sum of` names every item it can't read, in list order, whatever its cause, as an `every` does: an item whose `whose` can't read its focus, whose value is missing, `null` in a `sum of`, or not a number in a `sum of`, that isn't an object, or whose inner list fails while walking. So `sum of xs.v is 5` on `[{"v": "a"}, {}, {"v": null}]` says `item 1 of xs: v is "a", which isn't a number; item 2 of xs: v is missing; item 3 of xs: v is null` and fails as `unusable`. An item it left out, or whose value only changed the count or the sum, isn't named. A whose that doesn't read the focus, like `whose $params.z is 1`, names the item alone. When a name read from a root on the right of the phrase after `every` or `some`, a subject's field, `$params`, `$input`, an alias, a part or a parent, is missing, `null`, or of a type the phrase can't use whatever the item holds, like text after `is at least`, no item can pass, and that name's problem is said once, first, with no item in front: `m is "zz", which isn't a number`, `$params.q is missing`. Each item that fails on its own is said after it, in list order: with `$params.min` holding `"s"` and `xs` holding five `{}`, `every xs.v is at least $params.min` says `$params.min is "s", which isn't a number; item 1 of xs: v is missing; item 2 of xs: v is missing; item 3 of xs: v is missing; and 2 more` and fails as `unusable`. A key that can't be read is named, as the plain check names it: `k is null` for `every xs equals m named by k`. The key is named alone only when the key is what can't be read: when the steps before it are missing, the whole path is named as written, as the plain check names it, so `every xs.v equals pl named by k` with the part `pl` missing says `pl named by k is missing`. A name read from a root anywhere in a relative clause is named the same way, once, as [problems.where_said](#which-problems-a-message-says) says. With subject `l`, `count of $input.xs whose v equals l[0] is 1` says `l is "s", which isn't a list` when `l` is `"s"`, and `count of xs whose v equals pr.a.b is 1` says `pr.a is 3, which isn't an object`. When the clause compares the item's value with the root, with `is`, `is not`, `is one of`, `is in` or a phrase that orders numbers or times, like `is at least` or `is after`, or with any phrase when the root is read through a key the item holds, like `$input.m named by key`, such a root doesn't hide the items the relative clause can't read: the root comes first, and then each item whose own value the clause can't read, in list order, whatever its cause, even when it fails no worse than the root, in a `count of`, a `sum of`, an `every` and a `some` alike, as on a `for` line ([for.roots](#for), [problems.all_said](#which-problems-a-message-says)). With `starts with`, `matches` or `contains` and a root read without such a key, only the root is said for now ([OPEN.md](OPEN.md#left-for-a-later-pr)). So with `$params.min` holding `"s"` and `xs` holding `[{"v": 1}, {}]`, `count of xs whose v is at least $params.min is 1` says `$params.min is "s", which isn't a number; item 2 of xs: v is missing`, where `x.v is at least $params.min` under `for: every xs as x` says `$params.min is "s", which isn't a number; item 2 of xs: x.v is missing`. The root is an input of the assertion, once, and each such item is an `item` entry under it with its own read ([row.parts](#what-a-row-shows)). The same holds on a `for` line: `for: every ms as m, every m.ws whose v is in pos.name as w` with the part `pos` holding `[{"name": "bob"}, {}]` and an item of `ws` without `v` says `item 2 of pos: name is missing; item 1 of ms: item 2 of m.ws: v is missing`. An item whose focus isn't an object, so the `whose` can't read its field, is one of them: `every ws.n whose v is in pos.name is 2` with the same `pos` and `ws` holding `[{"v": "bob", "n": 2}, {"n": 2}]` says `item 2 of pos: name is missing; item 1 of ws: n is 2, which isn't an object; item 2 of ws: n is 2, which isn't an object` and fails as `unusable`. The params themselves are a root too: when they aren't an object, `$params is 3, which isn't an object` is said once, and then each item or the list, so with the params `3` and no `es`, `count of es whose v is in $params.z is 0 plus $params.q` says `$params is 3, which isn't an object; es is missing`. When more than one of them can't be read, each is named, whatever its cause, worst cause first and then by name, and they come before what the items say: `count of xs whose aa equals $params.q and whose b equals pr.z is 1` on `xs` holding `[{"aa": 1, "b": "s"}, {}]`, with neither root there, says `$params.q is missing; pr.z is missing; item 2 of xs: aa is missing; item 2 of xs: b is missing`, and `every xs whose w is in pr.l and whose v is in $params.l, if any, exists` on `xs` holding `[{"v": 1}]`, with `pr.l` `"s"` and `$params.l` `null`, says `pr.l is "s", which isn't a list; $params.l is null; item 1 of xs: w is missing`. A missing one is named by its whole path as written, like `pl.z is missing`, except that a key that can't be read, like `pr.k` in `$params.m named by pr.k`, is named alone. When the list can't be read either, its problem comes after them, as [problems.all_said](#which-problems-a-message-says) says. A root's own positions are still named as positions of that root, like `item 1 of l is missing`. On a `for` line, a prefix naming an item is left out when the name doesn't depend on that item: `for: every xs as x, every x.ys whose v equals pr named by pr.k as y` says `pr.k is missing`, and `every x.ys whose v is x.k as y` says `item 1 of xs: x.k is missing`, keeping the first item it depends on. Only a name read against the focus gets the item: `item 1 of xs: v is missing`. Inside one item, what the item can't read on its own is named in the order the sentence reads it: with `$input.m` `null` and an item without `key` or `v`, `count of xs whose v is $input.m named by key is 0` says `$input.m is null; item 1 of xs: v is missing, and key is missing`, and `count of xs whose $input.m named by key is v is 0` says `$input.m is null; item 1 of xs: key is missing, and v is missing`. The root is still said once, first, whatever the item holds, so with `$input.m` holding `3`, `count of xs whose tags contains $input.m named by key is 1` says `$input.m is 3, which isn't an object; item 1 of xs: tags is {"a": ["x"]}, which isn't a list` for an item whose `tags` holds `{"a": ["x"]}`, and a key the item holds is said once even when both sides of the phrase read a root through it. When that name walks a list of its own and an item of it can't be read, the message names that item of the name's list, with no item of the phrase, and lists such items as an `every` does, three at most: `item 2 of $params.envs is null, which isn't an object; item 3 of $params.envs: name is missing` for `every xs.n is in $params.envs.name`. A problem of the pair stays with its item: `item 1 of xs: n is 1, which isn't text`. When the sentence also reads a name spelled like the item's, the item's name is written as the walked path: `item 2 of conditions: conditions.type is "b", and type is "a"`.

**[message.part]** A path through a part that breaks before the part is reached says so, naming the part and the value that stopped the read: `cov can't be read: reports is "none", which isn't an object`, or `which isn't a list or an object` under an `every`, `some` or `count of`. When the part is reached and what it holds can't take the next step, the part is named as the value, as `cov is "x", which isn't an object` says.

**[message.alias]** In a `for` line, a name read through an alias is written as the policy wrote it, with its alias, wherever it is said, in the row's message and in the names and messages of `failures`: `item 2 of commits: c.signed is false`, and `item 1 of deploys: d.ok is false` when a `whose` picked the deploys. The alias on its own becomes the item, when it's the only thing a sentence read: `item 1 of commits is null`. A name that isn't read through the alias, like a subject's field, a param, `$input`, a name in `named by`, a worked-out value or another item, is written as the policy wrote it too: `item 2 of commits: c.author is "ann", and owner is "ann"`. A path read through an alias is cut where the read stopped ([location.read](#where-a-value-was-read)): `pr.meta.commits is null`, and `pr.meta is null` when `meta` is `null`. A `for` line's second list is named as written in the lead of its items, with the alias, `item 1 of pr.meta.cs`. An alias or a part is always named as the policy calls it, never with a `$` in front: `item 1 of z: z.k is 1`, and `x is 2, and cov.x is 1` for a part on the right. Names the policy writes with a `$`, like `$params.limit` and `$input`, keep it. A message never changes what the input held, so a value or a key that spells an alias, like `"$z: x"`, prints as it is.

**[message.join]** A check with several sentences gives each failed sentence's message, joined with `; `, in the order of its sentences: `x is 2; y is missing`. In an `any_of`, each option's message starts with the option's name: `one: x is 2; two: y is missing`. On a `for` line, an item is named once, and the sentences that failed for it follow, joined with `, and`: `item 2 of prs: item 1 of approvers: approver.state is "COMMENTED", and approver.username is "bob"`. A sentence that fails for several items of the second list gives each pair of items its own part, joined with `; `, and a sentence that doesn't read the second item joins the first part. A sentence that walks another list, like a list of the subject, gives each of that list's items its own part in the same way, under the first list's item: `item 1 of ws: item 1 of xs: k is 1; item 1 of ws: item 2 of xs: k is missing`. The pairs come in the order of the items, the first list's item and then the second's, not in the order of the sentences. On a line with one list, a sentence that walks a list under the item has its own part, and so does one that doesn't: `item 1 of cs: item 2 of reviews: ok is false; item 1 of cs: a is 2`. When two sentences walk the same list under the item, their parts come in the order of that list's items too, not in the order of the sentences: `for: every xs as x` with `every x.ys.n is 1` and `every x.ys.m is 1`, on `xs` holding `[{"ys": [{"n": 1, "m": 2}, {"m": 1}]}]`, says `item 1 of xs: item 1 of x.ys: m is 2; item 1 of xs: item 2 of x.ys: n is missing`. When they walk different lists under the item, each list's items come in list order, and the lists come in the order of the sentences: with `every x.ys.n is 1` and `every x.zs.n is 1` on `xs` holding `[{"ys": [{"n": 1}, {"n": 2}, {"n": 3}], "zs": [{"n": 4}]}]`, the line says `item 1 of xs: item 2 of x.ys: n is 2; item 1 of xs: item 3 of x.ys: n is 3; item 1 of xs: item 1 of x.zs: n is 4`. A check with several sentences outside a `for` line keeps the order of its sentences, so `assert: ["every xs.ys.n is 1", "every xs.ys.m is 1"]` on the same `xs` says `item 1 of xs: item 2 of ys: n is missing; item 1 of xs: item 1 of ys: m is 2`. A message that is the same as one before it in the row is left out, so `x is 1` and `x is 2` with `x` 5 say `x is 5` once, and so does a clause that repeats one before it in a message, so `tags contains none of tags` says `tags is ["a"]` once. A clause that an earlier sentence of the row already gave is left out of the row's message too, in a check with several sentences, in an `any_of` option and among the sentences of one item on a `for` line: on `{}`, `assert: ["expires_at exists", "expires_at is after as_of"]` says `expires_at is missing; as_of is missing`, and the option `e: ["expires_at exists", "expires_at is after as_of"]` says `e: expires_at is missing, and as_of is missing`. The same holds for the clauses of a `$min_subjects` row: one that [subjects.one_type](#requirements) gives after [subjects.every.same](#requirements) already gave it is left out. Each sentence's own entry in `failures` still says its whole message.

**[message.applies]** An `$applies` row that rules a subject out says what its filter found, as a check would: `env is "staging"`.

**[message.empty]** A `for` line that picks no item, because a `whose` leaves none or the list is empty, prints the list it read as found, naming only the lists that a `whose` or a position narrowed, or that are empty: `commits is [{"signed": false}]`, `commits is []`. A `for` line whose sentence can't be checked at all, because a param it reads as a list isn't one, prints the list it read in the same way: `xs is [{"k": 1}]`. When there's no list to print, it prints the check as the report writes it, then `is false`: `for every xs as x: x.k is in $params.l is false`.

**[message.from]** A `$min_subjects` row that failed because its `from` line couldn't be read says where the read stopped, in the words of [message.cause](#messages): `item 2 of things is missing`, `things is 5, which isn't a list or an object`. A subject read under another subject names the path as it walks that parent's value, without the parent's name: `ws is missing`, `item 1 of ws is missing`, `meta.owner is missing`. When the read stops before its first step, the message names where it starts: `$input is null`, or the parent subject's name, like `artifact is "x", which isn't an object` and `item 1 of artifact is missing` for a child of `artifact`. A path that stops at something that isn't a list or an object says what it found there.

## Which problems a message says

These four rules hold for every row, whatever sentence it comes from. The rules for each sentence add to them. The shapes where an engine or a rule does something else are listed in [OPEN.md](OPEN.md#differs-from-the-general-rules).

**[problems.same_path]** A path gives the same outcome in every sentence it is in: a plain check, a `count of` or `sum of`, a `whose`, a one-line `every` or `some`, a `for` line, a child subject's checks, a `from` line and its `$applies` row. With no params and `xs` holding `[{"v": 1}, {"v": 2}]`, `v is $params.q`, `every xs.v is $params.q`, `count of xs whose v is $params.q is 1` and `x.v is $params.q` under `for: every xs as x` all fail as `absent` with `$params.q is missing`.

**[problems.where_said]** A problem in something read from outside the item, the subject, `$input`, `$params`, a part or a parent, is said once, before any item, with no item in front. A problem in a path inside the item, or through an earlier `for` line's alias, is said for each item it is about. With the params `{"min": "s"}` and `xs` holding `[{"v": 1}, {}, {"v": 2}]`, `for: every xs as x` with `x.v is at least $params.min` says `$params.min is "s", which isn't a number; item 2 of xs: x.v is missing`. With `ws` holding `[{"min": 1, "ys": [{"n": 2}]}, {"ys": [{"n": 1}]}, {"ys": [{"n": 3}]}]`, `for: every ws as w, every w.ys as y` with `y.n is at least w.min` says `item 2 of ws: w.min is missing; item 3 of ws: w.min is missing`.

**[problems.all_said]** Every problem Ergo finds is said once: the roots first, then the list's own problem, like `xs is []`, then what each item says on its own. The row takes the worst cause of all of them, in the order [Causes](#causes) gives, and only of them: with the params `3`, `count of es whose v is in $input.z is 0` doesn't read the params, so with no `es` it fails as `absent`, with `$input.z is missing; es is missing`. With the params `{"min": "s"}`, `for: every xs as x` with `x.v is at least $params.min` and `xs` holding `[{"v": null}, {}]` fails as `unusable`, not `null`, with `$params.min is "s", which isn't a number; item 1 of xs: x.v is null; item 2 of xs: x.v is missing`, and with `xs` holding `[]` it says `$params.min is "s", which isn't a number; xs is []`.

**[problems.item_order]** Items are said in the order of their list, never sorted by cause. Only the roots of one sentence are sorted, worst cause first and then by name, as [for.roots](#for) says. A field of the subject, a `$params` or `$input` path, a part, and a key after `named by`, read from a ref or from a field, are all roots, so one order holds for all of them, whichever side of the phrase they are on: with no `k` in the params, `k is m named by $params.k` says `$params.k is missing; m is null` with `m` `null`, `m is "s", which isn't an object; $params.k is missing` with `m` holding `"s"`, and `$params.k is missing; k is missing; m is missing` on a subject with neither, and `x is at least y` with `x` `null` and no `y` says `y is missing, and x is null`. The list a sentence or a line walks isn't a root: its own problem comes after the roots ([problems.all_said](#which-problems-a-message-says)). With `xs` holding `[{"v": 2}, {"v": null}, {}]`, `every xs.v is 1` fails as `absent` with `item 1 of xs: v is 2; item 2 of xs: v is null; item 3 of xs: v is missing`.

## Where a value was read

**[location]** Every entry in a row's `inputs`, in a check's `$refs`, in the `inputs` of an entry of `failures` and an item in `failures` has `locations`: a list of where Ergo read its value or where the item sits. A location is a JSON Pointer ([RFC 6901](https://www.rfc-editor.org/rfc/rfc6901)) from the root of the input, like `/deployments/3/approved`, or, for a value read from the params, `$params:` followed by a pointer from the root of the params, like `$params:/max_days/high`. An option or an assertion has one that points into the policy, `$policy:` followed by a pointer from the root of the policy. List positions count from 0, and a key is escaped as RFC 6901 says, `~` as `~0` and `/` as `~1`. Locations never change `passed`, `cause` or a value. `[]` means no location could be given, like for a read that starts at a name nothing holds.

**[location.start]** A subject's location is where it is in the input, like `/deployments/3`, or `/services/web` for a subject read from an object's values. A subject listed by `named by each of` whose key isn't in the object points at the object. A child subject's starts at its parent's. A path that starts at the subject, a part, an alias or a parent's name starts at that value's location, one that starts at `$input` at the root of the input, and one that starts at `$params` at the root of the params.

**[location.read]** A path's location goes as far as its read went. A path that ends `found` or `null` points at the value it read. One that ends `absent` or `unusable` points at the last value it read: the object without the key, the list too short for the index, or the value that couldn't hold the step. So a pointer never leads to a value Ergo didn't read, and `item 2 of x` on `{"x": {"1": "a"}}` points at `/x`, not at `"a"`. A path that ends `not_an_object` points at the subject. A ref step or a field step adds the key it read. When that key can't be read, the path stops before the step. A path into params that aren't given is `$params:`. An entry that holds one value for each item of a list follows [location.each](#where-a-value-was-read) instead, so a walk or a `count of` on a list that is missing keeps `value: []` and `locations: []`.

**[location.one]** An entry that shows the value of one path, like the entry of [path.inputs](#what-a-row-shows) or of a field step, has one location.

**[location.refs]** An entry in `$refs` has its ref's location, and keeps it when [violations](#violations) adds it to a violation's `inputs`.

**[location.merged]** When a row lists an input once though several checks or filters read it, like an `all_of`, an `any_of`, a `for` line, an `$applies` row or a check that reads it twice ([row.inputs_once](#what-a-row-shows)), reads merge into one entry only when their name, their value and their locations all match. Two reads that print the same name and value but come from different places, like a parent's `b.x` and a child's own `.b.x`, each keep an entry. The entries are sorted by name, then value, then locations.

**[location.each]** An entry that holds a value for each item, like a walk's ([walk.inputs](#every-and-some)) or a list on a `for` line ([for.inputs](#for)), has one location per value, in the same order. A walk that stopped before it walked anything holds `[]` and has no locations.

**[location.worked_out]** An entry whose value Ergo works out, the number of a `count_of`, `sum_of`, `add` or `elapsed` side, has the locations of the entries shown for that side after it, in their order, once each, leaving out the entry of the field a field step reads, as the path's own entry does ([path.field_step](#reading-a-path)): `n named by p plus q` points at `/n/k` and `/q`, not at `/p`. The `$min_subjects` entry has the location of each subject it counts, in the order of the rows. The `$unique_ids` and `$unique_ancestor_ids` entries have the location of the id of every subject that shares one, in the order the ids are listed, then of the subjects. The entries of `$well_formed` read the policy and have no locations, and nor do the entries that list problems with the input or the params.

**[location.failed_items]** An `item` entry in `failures`, of a check's row or of an `$applies` row, has `locations`: where the item sits, like `/pull_requests/1`, and for an item `distinct` kept, every copy, in the order the walk reads them. Its `value` is the item, or what its alias stands for. What was read inside it, like the title in `every pull_requests.title as t`, or the sort key that tied in `first of owners sorted by name`, is one of its `inputs`, with its own `locations`, which stop where the read stopped as [location.read](#where-a-value-was-read) says, like `/pull_requests/1/title` or `/teams/0/owners/0/name`. A walk that stopped before it walked anything gives where it stopped. An alias holds the value it was read as, so `m.commits` after `every prs.meta as m` starts at `/prs/0/meta`. An `option` and an `assertion` entry have `locations` in the policy, as [row.parts](#what-a-row-shows) says.

## `present`

`present` takes a path and asks whether the field is there.

**[present.pass]** It passes when its path ends `found`. Any value counts, `""`, `false`, `0`, `[]` and `{}` included.

**[present.missing]** It fails with cause `value` when its path ends `absent` or `null`. Whether the field is there is the question it asks, so "it isn't" is a sound answer, and the cause says so.

**[present.no_params]** On a path into the params, it fails with cause `absent` instead when there are no params. Then the params weren't given at all, so Ergo can't tell whether the field would be there, and a policy run without its params fails instead of ruling every subject out. When the params are an object without the field, it fails with `value` as usual.

**[present.other]** It fails with the outcome as its cause when its path ends any other way: `not_an_object` or `unusable`. A ref step whose ref can't be read keeps the ref's cause too, even `absent` or `null`, because then the field it looks for is unknown, not missing.

**[present.filter]** A `present` filter that fails with cause `value` rules the subject out, whatever the other filters give. Its `$applies` row fails with cause `value`, and the subject gets no other rows. Any other cause fails the requirement, as it does for every filter. **[applies.inputs]** The `$applies` row lists each path its filters read once, sorted by name.

## `missing`

`missing` takes a path and asks whether the field is missing. It's the opposite of `present`.

**[missing.pass]** It passes where `present` would fail with cause `value`: when its path ends `absent` or `null`.

**[missing.fail]** It fails with cause `value` where `present` would pass, so a field that's there fails it whatever it holds, `false` and `""` included. Everywhere else, it fails with the cause `present` would give, so with no params a `missing` check on a path into the params fails as `absent` instead of passing.

**[missing.filter]** As a filter, it rules out a subject whose field is there, with cause `value`, as any filter does.

## `equals`

`equals` takes a path and a value, and asks whether the field equals the value.

**[equals.pass]** It passes when its path ends `found` or `null` and the value read [equals](#values) the value. So a `null` value passes on a field that's there and `null`.

**[equals.fail]** It fails with the path's outcome as its cause when the path ends anything but `found` or `null`, a missing field included, even when the value is `null`. It fails with `null` when the field is `null` and the value isn't. When the field was read, it fails with `unusable` when the field and the value have different types, so `"5"` against `5` can't rule a subject out, and with `value` otherwise. Against a `null` value, a field that was read fails with `value`.

## `in`

`in` takes a path and a list of values, and asks whether the field is one of them.

**[in.values]** The values are a list whose items are values, or a ref to a list. The values all have one type, leaving `null` aside. When the ref reads something other than a list, or the values read through refs have more than one type, the check fails as `unusable`. A list read through a ref is data, so an object in it that looks like a ref is compared as an object.

**[in.pass]** It passes when its path ends `found` and the value read [equals](#values) one of the values.

**[in.fail]** It fails with the path's outcome as its cause when the path ends anything but `found`, so a missing or `null` field fails even when the values hold `null`. When the field was read, it fails with `unusable` when its type isn't the type of the values, and with `value` otherwise, an empty list of values included.

## `has_type`

`has_type` takes a path and a `type`, one of `list`, `string`, `number`, `boolean` and `object`, and asks whether the field has that JSON type. It's what the sentence `is a <type>` reads into, see [sentence.phrase.type](syntax.md#phrases).

**[has_type.pass]** It passes when its path ends `found` and the value has the type.

**[has_type.fail]** It fails with the path's outcome as its cause when the path ends anything but `found`. A value of any other type fails with `value`, because checking the type is what it's for.

## `lacks_type`

`lacks_type` takes a path and a `type`, like `has_type`, and asks whether the field has another JSON type. It's what the sentence `is not a <type>` reads into, see [sentence.phrase.type](syntax.md#phrases).

**[lacks_type.pass]** It passes when its path ends `found` and the value doesn't have the type.

**[lacks_type.fail]** It fails with the path's outcome as its cause when the path ends anything but `found`, so a missing or `null` field fails it, as it fails `has_type`. A value of the type fails with `value`.

## `not_in`

`not_in` takes a path and a list of values, written like the values of [`in`](#in), and asks whether the field is none of them. It's what the sentences `is not one of` and `is not in` read into, see [sentence.phrase.one_of](syntax.md#phrases).

**[not_in.pass]** It passes when its path ends `found`, the value read has the type of the values, and it [equals](#values) none of them. Any value passes when the list is empty.

**[not_in.fail]** It fails with the path's outcome as its cause when the path ends anything but `found`, so a missing or `null` field fails even when the values hold `null`. When the values can't be used, as [in.values](#in) says, or the field has another type than the values, it fails as `unusable`, as `in` does. When the field equals one of the values, it fails with `value`.

## `non_empty_string`

`non_empty_string` takes a path and asks whether the field is a string with something in it.

**[non_empty_string.pass]** It passes when its path ends `found` and the value is a string other than `""`. A string of spaces passes.

**[non_empty_string.fail]** It fails with the path's outcome as its cause when the path ends anything but `found`. When the field was read, it fails with `value`, whatever its type, because checking the type is what it's for.

## `not_non_empty_string`

`not_non_empty_string` takes a path and asks whether the field is anything but a string with something in it. It's what the sentence `is not a non-empty string` reads into.

**[not_non_empty_string.pass]** It passes when its path ends `found` and the value isn't a string with a character in it, so `""` passes, and so does a number, a list or an object.

**[not_non_empty_string.fail]** It fails with the path's outcome as its cause when the path ends anything but `found`. A string other than `""` fails with `value`.

## `empty_string_or_list` and `not_empty_string_or_list`

`empty_string_or_list` takes a path and asks whether the field is `""` or `[]`. `not_empty_string_or_list` asks whether it's a string or a list with something in it. They're what the sentences `is empty` and `is not empty` read into, see [sentence.phrase.empty](syntax.md#phrases).

**[empty_string_or_list.pass]** `empty_string_or_list` passes when its path ends `found` and the value is `""` or `[]`. `not_empty_string_or_list` passes when its path ends `found` and the value is a string with at least one character or a list with at least one item.

**[empty_string_or_list.fail]** Both fail with the path's outcome as their cause when the path ends anything but `found`. A value that's neither a string nor a list, like a number, a boolean or an object, fails with `unusable`. Otherwise they fail with `value`.

## `range`

`range` takes a path, a `min` and a `max`, and asks whether the field is a number between them, both included.

**[range.pass]** It passes when its path ends `found`, the value is a number, and `min <= value <= max`, compared by value.

**[range.fail]** It fails with the path's outcome as its cause when the path ends anything but `found`, and with `unusable` when the value isn't a number. A number outside the range fails with `value`.

## `outside_range`

`outside_range` takes a path, a `min` and a `max`, like `range`, and asks whether the field is a number below `min` or above `max`. It's what the sentence `is not between` reads into.

**[outside_range.pass]** It passes when its path ends `found`, the value is a number, and `value < min` or `value > max`, compared by value.

**[outside_range.fail]** It fails with the path's outcome as its cause when the path ends anything but `found`, and with `unusable` when the value isn't a number, as `range` does. A number from `min` to `max` fails with `value`.

## `matches_any` and `not_matches_any`

`matches_any` takes a path and a list of patterns, and asks whether the field is a string that at least one of them matches. `not_matches_any` asks whether it's a string that none of them match.

**[patterns.syntax]** A pattern is a regular expression in [RE2 syntax](https://github.com/google/re2/wiki/Syntax), run on code points. So there's no lookahead and no backreference. `.` doesn't match a newline, `$` only matches at the very end of the string, and `(?i)` turns on case-insensitive matching. `\d`, `\w`, `\s` and `\b` only know ASCII, as in RE2: `\d` is `0` to `9`, `\w` is those, `A` to `Z`, `a` to `z` and `_`, `\s` is tab, line feed, form feed, carriage return and space, and `\b` is where a `\w` character meets a character that isn't one, or the start or end of the string. `\D`, `\W`, `\S` and `\B` are the opposites. So `^\d$` doesn't match `٣`, and `^a\b` matches `aé`. `(?i)` still folds case, so `(?i)^\w$` matches `ſ`, a long s. A pattern isn't anchored: `svc_` matches `my_svc_account`.

**[patterns.list]** The patterns are a list whose items are strings or refs, or a ref to a list. When a ref reads something other than a list, or a pattern that isn't a string or isn't valid, the check fails with `unusable`.

**[patterns.pass]** `matches_any` passes when its path ends `found`, the value is a string, and at least one pattern matches it. `not_matches_any` passes when its path ends `found`, the value is a string, and no pattern matches it. So with no patterns, `matches_any` always fails and `not_matches_any` passes on any string.

**[patterns.fail]** Both fail with the path's outcome as their cause when the path ends anything but `found`, and with `unusable` when the value isn't a string. Otherwise they fail with `value`.

## `includes` and `excludes`

`includes` takes a path and either one value or a list of values. With one value, it asks whether the field is a list that contains it, and with a list, whether it contains every one of them. `excludes` asks whether the field is a list that contains none of them.

**[contains.value]** One value is one value, so a list given as the value is looked for as a list inside the field. A path to the value is read as any path is and never walks a list ([walk.right](#compare)): a list it ends at is one value, so `pairs contains pair` with `pairs` `[["a", "b"], ["c", "d"]]` and `pair` `["a", "b"]` passes, and a list it meets on the way fails as [path.unusable](#reading-a-path) says, so `labels contains x.name` with `x` `[{"name": "a"}]` fails as `unusable` with `x is [{"name": "a"}], which isn't an object`. A path from `$input` whose first step is a key fails as `not_an_object` on an input that is a list, with or without a `named by` after it, with `$input is [...], which isn't an object`, said once with no item inside a relative clause ([message.items](#messages)). One whose first step is a position reads that item, and `$input` on its own is the input, one value. The path is in the check's `$refs` under the name it is written with, like `$input.x.name`, with the value `null` and the location where the read stopped when it can't be read. To look for each value of a list, write `contains all of`, `contains some of` or `contains none of`. A list of values has at least one item, and its items are values. It can be a ref, and when the ref reads something other than a non-empty list, the check fails as `unusable`, because an empty list would pass every field. The values all have one type, leaving `null` aside, and so do the field's items and the values together, so `1` is never looked for in a list of strings. When values read through refs have more than one type, the check fails as `unusable`.

**[contains.pass]** `includes` passes when its path ends `found`, the value is a list, and an item [equals](#values) the value, or with a list of values, when each of them equals an item. `excludes` passes when its path ends `found`, the value is a list, and no item equals the value, or any of the values. So an empty list fails `includes` and passes `excludes`.

**[contains.fail]** Both fail with the path's outcome as their cause when the path ends anything but `found`, and with `unusable` when the value isn't a list, a string or an object included, or when its items and the values have more than one type, leaving `null` aside. Otherwise they fail with `value`. An empty list holds no type, so it fails `includes` with `value`.

## `includes_some` and `not_includes_all`

`includes_some` takes a path and a list of values, and asks whether the field is a list that contains at least one of them. `not_includes_all` asks whether it's a list that lacks at least one of them. They're what the sentences `contains some of` and `does not contain all of` read into.

**[contains_some.values]** The values are as [contains.value](#includes-and-excludes) says for a list of values: at least one item, all of one type, and read through a ref when it's a ref.

**[contains_some.pass]** `includes_some` passes when its path ends `found`, the value is a list, and some item [equals](#values) one of the values. `not_includes_all` passes when its path ends `found`, the value is a list, and one of the values equals no item. So an empty list fails `includes_some` and passes `not_includes_all`.

**[contains_some.fail]** Both fail as [contains.fail](#includes-and-excludes) says for `includes` and `excludes`: with the path's outcome as their cause when the path ends anything but `found`, with `unusable` when the value isn't a list or its items and the values have more than one type, leaving `null` aside, and with `value` otherwise.

## `compare`

`compare` takes two sides, `left` and `right`, and a comparison: `eq`, `ne`, `gt`, `gte`, `lt` or `lte`. A side is a path, so it compares two fields of the same subject. [Counts and sums in sentences](#counts-and-sums-in-sentences) says what else a side can be.

**[compare.pass]** It passes when both paths end `found`, the two values have the same type, and `left cmp right` holds. `eq` and `ne` use [equality](#values) and work on any type. `gt`, `gte`, `lt` and `lte` only work on two numbers, compared by value. Two strings aren't ordered, because a number held as a string, like `"9"`, would come after `"80"` as text. [compare.alphabetical](#compare) orders strings, and [compare_time](#compare_time) orders times.

**[compare.fail]** It fails with the worse of the two paths' outcomes when either ends anything but `found`, so two `null` fields fail as `null`, even with `eq`. When both were read, it fails with `unusable` when their types differ, even with `ne`, and when `gt`, `gte`, `lt` or `lte` is used on anything but two numbers, two strings included. Otherwise it fails with `value`.

**[compare.within]** A `compare` with `ne` can have a `within`, a number of 0 or more. `eq` passes when the two values are numbers and no further apart than `within`, and `ne` when they are numbers and further apart than that, with the gap worked out exactly, as [sentence.phrase.within](syntax.md#phrases) says. `ne` with `within` fails as `eq` with `within` does when a side is missing, `null` or not a number, and as `unusable` when the gap can't be worked out exactly. Otherwise it fails with `value`.

**[compare.join]** A side of `compare` can also be `join`, a list of pieces, each a path or a written value, and `text`, the words that wrote it. It's what the sentence `followed by` reads into, see [sentence.operand.followed_by](syntax.md#phrases). The side is the string made by putting the pieces next to each other in the order of the list. Every piece must be a string. A piece that is a path with a field step lists the field right after it, as [path.field_step](#reading-a-path) says. The first piece, from the first, that can't be read decides the side: its outcome, `absent` or `null`, or `unusable` when it was read and isn't a string, so the first of two pieces that fail is the one that counts. This order wins over [value.ref](#values), so `w is v followed by $params.n`, with `v` missing and `$params.n` `null`, fails as `absent` with `v is missing`, not as `null`. When the side fails, the row fails with that cause whatever the left side is, so a left side that is missing or `null` doesn't change it. Only when every piece was read does the left side's own outcome count, and then the two sides are compared as [compare.pass](#compare), [compare.text](#compare) and [contains.pass](#includes-and-excludes) say for a string on the right, with `includes` and `excludes` reading a list on the left that holds the joined string. A piece that is a written string has no entry in the row's `inputs`. The row has the left side's entry, then an entry for each piece that is a path, in order, and none for the joined text. A piece from `$params` or `$input` is in the check's `$refs` too ([value.refs](#values)), and a `for` line's row lists each piece that doesn't start at an alias, as [for.inputs](#for) says. A piece that is a path from `$input` whose first step is a key fails as `not_an_object` on an input that is a list, with `$input is [...], which isn't an object`, as a path on its own does. The message of a row that fails as `unusable` names each piece that stopped the read, as [path.unusable](#reading-a-path) says, and each piece that was read and isn't text, as `o.team is 1, which isn't text`, and never the joined text. After `includes` and `excludes` it names the left side too when it was read and isn't a list, as `p is 5, which isn't a list`, or holds items that aren't strings, leaving `null` items aside, as `l is [1, 2], which isn't a list of text`, whether every piece was read or not. A piece whose read stopped comes before the left side, as `owner is "ops", which isn't an object, and labels is 5, which isn't a list`, and a piece that was read and isn't text comes after it, as `labels is [["a"]], which isn't a list of text, and owner.team is 1, which isn't text`.

**[compare.inputs]** Its row has two entries in `inputs`, `left` then `right`.

**[compare.text]** Four more comparisons, `starts_with`, `ends_with`, `not_starts_with` and `not_ends_with`, are what the sentences `starts with`, `ends with`, `does not start with` and `does not end with` read into, see [sentence.phrase.starts](syntax.md#phrases). They pass when both values are strings and the left one starts, or ends, with the right one, code point by code point, and for the last two when it doesn't. Anything but two strings, two numbers included, fails with `unusable`, and the rest is as [compare.fail](#compare) says.

**[compare.alphabetical]** Four more comparisons, `alphabetically_before`, `alphabetically_after`, `alphabetically_lte` and `alphabetically_gte`, are what the sentences `is alphabetically before`, `is alphabetically after`, `is alphabetically on or before` and `is alphabetically on or after` read into, see [sentence.phrase.alphabetical](syntax.md#phrases). They pass when both values are strings and the left one comes before, or after, the right one, or for the last two is the same or comes before, or after, compared code point by code point, so `"Z"` comes before `"a"` and `"！"` (U+FF01) before `"😀"` (U+1F600). Equal strings fail the first two and pass the last two. Anything but two strings, two numbers included, fails with `unusable`, and the rest is as [compare.fail](#compare) says.

**[compare.list]** Ten more comparisons, `in`, `not_in`, `includes`, `excludes`, `includes_all`, `excludes_all`, `includes_some`, `not_includes_all`, `matches_any` and `not_matches_any`, are what the sentences `is one of`, `is not one of`, `contains`, `does not contain`, `contains all of`, `contains none of`, `contains some of`, `does not contain all of`, `matches` and `does not match` read into when what follows is a field, see [sentence.phrase.field](syntax.md#phrases). Each means what [`in`](#in), [`not_in`](#not_in), [`includes` and `excludes`](#includes-and-excludes), [`includes_some` and `not_includes_all`](#includes_some-and-not_includes_all) and [`matches_any` and `not_matches_any`](#matches_any-and-not_matches_any) say, with the right side's value as their value, values or patterns, and the check as a whole passes and fails as they say, so `compare.pass` and `compare.fail` don't apply to them. The right side decides first. When it ends anything but `found`, the row fails with that outcome, whatever the left side is. When it was read but can't be used, it fails with `unusable`, again whatever the left side is: a value that isn't a list after `in`, `not_in`, `includes_all`, `excludes_all`, `includes_some`, `not_includes_all`, `matches_any` or `not_matches_any`, a list whose values have more than one type after `in`, `not_in`, `includes_all`, `excludes_all`, `includes_some` or `not_includes_all`, an empty list after `includes_all`, `excludes_all`, `includes_some` or `not_includes_all`, and patterns that aren't all valid regular expressions. Anything that was read is usable after `includes` and `excludes`. Only then are the left side's outcome and type looked at, as the rules named above say. The row has the two entries of [compare.inputs](#compare).

**[walk.right]** The path after `is one of`, `is not one of`, `contains all of`, `contains none of`, `contains some of`, `does not contain all of`, `matches` and `does not match` walks lists the way a path after `every` does ([walk.lists](#every-and-some)), wherever it starts, at the input, at the params, at the subject, at a parent, a grandparent, a part or an alias, and has no `named by` step, and plain reading can't end `found` because a key meets a list, the value the path starts at included, as [walk.start](#every-and-some) says. The root of the params is always an object, so it is never walked. The value on the right is then the list of what the path ends at in each item, in order, and the phrase compares with it as it does with any list: `pin is in $input.sbom.components.name` compares `pin` with the names of the components. A path that meets no list is read as before, so a `null` or missing list, text and an object fail as `null`, `absent` and `unusable` as [path.unusable](#reading-a-path) says. After the last step a list is a value and isn't walked, so a path that ends at a list, like `$input.deep.names`, reads that list as before. The path of a phrase that takes one value, like `is`, `starts with`, `contains` or `does not contain`, is not read this way ([contains.value](#includes-and-excludes)). It holds in a `whose` too, including the `whose` of a `count of`, a `sum of`, an `every` and a `some`, and in the sentence of a `for` line.

**[walk.right.fail]** The right side fails the row when it can't be read from every item, whatever the left side is, and no item is left out: an item that has no value at the end of the path makes the row fail as `absent`, even for the items that have one, because Ergo can't tell whether the list is complete, one that has `null` as `null`, a list that is missing, `null` or not a list as `walk.lists` says, one that holds an item that isn't an object, or that reads past something that isn't an object, as `unusable`, and a list that is empty as `value`, after `is not one of` too, because it holds nothing to compare with. When several fail, the worst cause in the order of [causes](#causes) is the row's. Values that can't be used after the phrase, like names of more than one type after `is one of`, fail as `unusable` as [compare.list](#compare) says. The row's `message` says what failed in the words an `every` uses, `item 2 of $input.sbom.components: name is missing` or `$input.sbom.components is []`. It names the value where the read stopped, even when another item holds a list there: `id is in $input.o[0]` on `[{"id": "a", "o": [["a"]]}, {"id": "b", "o": {"x": 1}}]` says `item 2 of $input: o is {"x": 1}, which isn't a list`. When the names were read, it says `x is "attrs", and $input.sbom.components[].name is ["click", "jinja2"]`.

**[walk.right.inputs]** The right side is named after the path with `[]` after each list walked, like `$input.sbom.components[].name`, and holds what each item's path ended at, `null` where it ended missing, with the location of each, as [walk.inputs](#every-and-some) says. A path from the input or the params is an entry of the row's `inputs` after the left side's ([path.right_inputs](#what-a-row-shows)), and is in the check's `$refs` ([value.refs](#values)) too, and a path from the subject is an entry of the row's `inputs`, after the left side's. When the walk can't be completed the entry holds what was read, `[]` when nothing was. A path that starts with a dot reads the subject's field, and keeps the dot in the entry's name and in the message when a part, a parent subject or an alias has the same first name, like `.lock.pkgs[].name` and `item 2 of .lock.pkgs: name is missing`. Without such a name the dot is left out, like `lock.pkgs[].name`.

**[walk.right.plain]** A path that meets no list on the way is read as before, whatever its steps: one that ends at a list, or reads into something that is `null` or missing, gives the entry and the message it always gave. A ref that reads into something that can't hold the next step, like text, fails as `unusable` and says which value it is, as a path from the subject does: `$input.sbom.components is "x", which isn't an object`.

## Text ignoring case and surrounding spaces

**[text.ignoring]** `is`, `equals`, `is equal to`, `is not`, `does not equal`, `is one of`, `is not one of`, `is in` and `is not in` can end with `ignoring case`, `ignoring surrounding spaces` or `ignoring case and surrounding spaces`, as [sentence.phrase.ignoring](syntax.md#phrases) writes them, whether the values are written out or read from a path. Both sides are prepared before they are compared: the field, the written values, a field on the right, each part of a `followed by` on the right, a root like `$params.p`, `$input.r`, a part or a parent on the right, and each item of a list read from a path of one step, a field of the subject, `$params` or `$input`, which walks the subject or `$input` when it is a list, as [walk.start](#every-and-some) says. A list read from a path of more than one step, like `$input.cs.name`, is written wrong for now, as [sentence.phrase.ignoring](syntax.md#phrases) says. A part of a `followed by` that isn't text fails as `unusable`, and one that is `null` as `null`, like any other side, so `t is "a" followed by u ignoring case and surrounding spaces` passes on `" AB "` when `u` is `"b"`. `status is one of "in progress", "done" ignoring case and surrounding spaces` passes on `"  IN Progress "`, and so does `status is in $params.states ignoring case and surrounding spaces` with the params `{"states": ["In progress", "done "]}`. Messages and `inputs` show each value as it is in the input, never prepared, so the same check on `"  Blocked "` fails as `value` with `status is "  Blocked "`.

**[text.case]** `ignoring case` lowercases each code point on its own, with Unicode's simple lowercase mapping, which is what OPA's `lower` does. `İ` (U+0130) becomes `i`, a final `Σ` becomes `σ`, never `ς`, `ẞ` becomes `ß` and the Kelvin sign becomes `k`. There is no full case folding, so `"STRASSE"` and `"straße"` stay different. The Unicode version isn't pinned, see [OPEN.md](OPEN.md#where-ergorego-and-the-rust-engine-differ).

**[text.surrounding_spaces]** `ignoring surrounding spaces` drops every character with Unicode's `White_Space` property at the start and at the end, the characters [sentence.ends](syntax.md#the-grammar) lists, which is what OPA's `trim_space` does. So a no-break space (U+00A0), a next line (U+0085), an ideographic space (U+3000) and a line separator (U+2028) are dropped, and a zero-width space (U+200B) and a byte order mark (U+FEFF) stay. Spaces inside the text stay, so `"in  progress"` is not `"in progress"`.

**[text.not_text]** A value that is missing fails the check as `absent`, and `null` as `null`, as without the words. A value that is there but isn't text, a number, `true` or `false`, a list or an object, fails it as `unusable` with `x is 3, which isn't text`, on either side. A written value that isn't text, `null` included, is written wrong, as [sentence.phrase.ignoring](syntax.md#phrases) says, so every written value the check compares is text. The `not` forms fail the same way and never pass on a value that can't be compared. Each item of a list read from a path is a value on the right, and it isn't left aside when it is `null`, as [in.values](#in) leaves it aside without the words. An item that is `null` fails the check as `null`, and one that is there but isn't text as `unusable`, whatever the field holds, so the field matching another item doesn't save it: with the params `{"types": ["Bug", null]}`, `type is in $params.types ignoring case` fails as `null` on `"bug"` with `item 2 of $params.types is null`. Such items are named once and in list order, three at most and then `and N more`, as [message.items](#messages) says, after what the field itself can't give, and the worst cause of all of them wins ([problems.all_said](#which-problems-a-message-says), [problems.item_order](#which-problems-a-message-says)): with `["Bug", null, 3]` it fails as `unusable` with `item 2 of $params.types is null; item 3 of $params.types is 3, which isn't text`, and with `["Bug", null]` and no `type` as `absent` with `type is missing, and item 2 of $params.types is null`. A list that only holds `null` names each item too. A list read from each item of a subject that is a list names its items as [walk.right.fail](#compare) does: with the params `{"v": "a"}` and the subject `thing` holding `[{"states": ["A"]}, {"states": ["b", 3]}]`, `$params.v is in states ignoring case` fails as `unusable` with `item 2 of thing: item 2 of states is 3, which isn't text`. Such a list can't be used whatever the field holds, so after `every`, `some`, `count of` and `sum of`, and in a `whose`, it is a root on which no item can pass, read before any item ([tally.walk](#counts-and-sums-in-sentences), [walk.flaws](#every-and-some)): it fails the check with the worst cause of its items even when the list walked is empty or a `whose` leaves no item, with `if any` too, and its problem is said once, before any item, as [problems.same_path](#which-problems-a-message-says) and [problems.where_said](#which-problems-a-message-says) say. Each item whose own value the phrase can't compare is said after it, in list order, as [message.items](#messages) says: with the params `{"l": ["A", 3]}` and `xs` holding `[{"v": "a"}, {"v": 5}, {}]`, `every xs.v is in $params.l ignoring case` and `count of xs whose v is in $params.l ignoring case is 1` fail as `unusable` with `item 2 of $params.l is 3, which isn't text; item 2 of xs: v is 5, which isn't text; item 3 of xs: v is missing`, and with `xs` holding `[]`, `every xs.v, if any, is in $params.l ignoring case` fails the same way with `item 2 of $params.l is 3, which isn't text`.

## Counts and sums in sentences

A side of `compare` can also be `count_of` or `sum_of`, each with a path, `whose`, a list of basic checks, and `text`, the words that wrote it, or an `elapsed` side, see [tally.elapsed](#counts-and-sums-in-sentences). `add` can take `text` too, and `count_of`, `sum_of` and `elapsed` among the sides it adds up. They're what `count of`, `sum of` and `plus` read into, see [sentence.derived.count](syntax.md#derived-values).

**[tally.walk]** The path is walked as [walk.lists](#every-and-some) says, except that an empty list adds nothing instead of failing. A list that's missing, `null` or not a list fails the side as `absent`, `null` or `unusable`, and so does a path where no step walks a list, as [walk.lists](#every-and-some) says. On a subject that isn't an object or a list, with a path that starts at the subject, it fails as `not_an_object`, and so does an item that isn't an object when the path goes on into it, as [walk.flaws](#every-and-some) says for `every`. A `null` at the end of the path is a value and counts as [tally.count](#counts-and-sums-in-sentences) says; a `null` before the end fails the side as `null`, naming that step, as [path.null](#reading-a-path) says: `sum of items.m.n is 3` with `items` `[{"m": null}]` says `item 1 of items: m is null`. A subject that is a list is walked, as [walk.start](#every-and-some) says. A ref the side reads that can't be used, in its path or its `whose` checks, fails it as `unusable`, and one that's missing or `null` fails it as `absent` or `null`, even when the list is empty. So does a root name in a `whose` that the phrase reads as a list, like `pr.z` in `count of xs whose v is in pr.z is 0`, when it isn't one: the list it looks in is read before any item, so with `pr.z` `"s"` the side fails as `unusable` with `pr.z is "s", which isn't a list`, on an empty `xs` too, and a root of the wrong type for any other phrase does the same, like `pr.z is "s", which isn't a number` after `is at least`. The roots come worst cause first and then by name, as [problems.item_order](#which-problems-a-message-says) says: `count of xs whose w is in pr.l and whose v is in $params.l is 0` with neither there says `$params.l is missing; pr.l is missing`. A list that is missing, `null` or not a list is said after the roots, whatever its cause, and the side takes the worst cause of them all: with no `l` in the params and `xs` `null`, `count of xs whose v is in $params.l is 0` fails as `absent` with `$params.l is missing; xs is null`, and with `pr.l` holding `"s"` and no `xs`, `count of xs whose v is in pr.l is 0` fails as `unusable` with `pr.l is "s", which isn't a list; xs is missing`. A root on the other side of the comparison doesn't hide the list either: with no `k` in the input and no `zzs`, `count of zzs is m named by $input.k` fails as `absent` with `$input.k is missing, and zzs is missing`. The list has its `list` entry under the assertion in both ([row.parts](#what-a-row-shows)). A root that the phrase walks as a list, like `pos.name` in `count of rows whose v is in pos.name is 0` with the part `pos`, fails a check that would otherwise pass when it is empty, as `value` as [walk.right.fail](#every-and-some) says, when an item of it can't be read or when its values can't be used, on an empty `rows` too, and when a `whose` leaves no item of `rows`: with `pos` holding `[{"name": "bob"}, {}]` and `rows` `[]`, the row fails as `absent` with `item 2 of pos: name is missing`, said once, with no item of `rows` in front. The same goes for every root [for.roots](#for) names, a part, a parent, a parent's part, an alias of an earlier `for` line, a field of the subject written with a leading dot, `$params` and `$input`, wherever the check reads it: an `every` or `some` phrase, a `whose`, a `count of … that`, and a `for` line's own `whose` and its sentences.

**[tally.whose]** The `whose` checks read from the value the path ends at in each item of the innermost list walked, the focus, as [walk.items](#every-and-some) says. An item is left out when one of them fails with `value`, or when a `present` check finds the field missing. An item one of them can't decide fails the side with its cause, and its path isn't read, so only that cause counts. A name one of them reads from a root, like `$params`, `$input`, a part, a parent, an alias or the subject's own name, is read once, up front, whether or not an item needs it, and so is a name on the right of the phrase after `every` or `some`. A problem with it fails the row with its cause, said once with no item named, even when the list is empty: `count of xs whose v equals $params.q is 0`, `count of xs whose v equals pr.z is 0` and `count of xs whose v equals $params.m named by $params.k is 0` fail as `absent` on an empty list, with `$params.q is missing`, `pr.z is missing` and `$params.k is missing`. A `named by` key that is missing or `null` is read once too, and it is always said, once and before any item, even beside an item that fails worse. It sits on the assertion's inputs with its own outcome, each item takes the cause of its own paths, and the row takes the worst of all: `count of rs whose zz is m named by $input.k is 1` with `$input.k` `null` and no `zz` on the items fails as `absent` with `$input.k is null; item 1 of rs: zz is missing; item 2 of rs: zz is missing`, and with a `zz` on each item, or with no items, it fails as `null` with `$input.k is null`. A key that holds anything but text fails the row as `unusable`, and an empty list doesn't excuse it, because the key is read before any item: with `es` `[]` and `$input.k` `3`, `count of es whose zz is m named by $input.k is 0` says `$input.k is 3, which isn't text`. The same goes for a `that`, like `count of es.v that is m named by $input.k is 0`, and for a list that is missing or `null`, since `unusable` is worse than `absent` and `null`: with no `es`, both say `$input.k is 3, which isn't text`. A path read from a root ends with the key's outcome too. Both engines name the key first when the root is `$input`, the key is read from `$input` and one condition of the `whose` reads it: `count of rs whose zz is $input.m named by $input.k is 1` fails as `absent` with `$input.k is null; item 1 of rs: zz is missing; item 2 of rs: zz is missing`. With a key read from `$params`, or with two conditions that read the same key, the engines differ ([OPEN.md](OPEN.md#where-ergorego-and-the-rust-engine-differ)). A phrase that reads the path as a list, like `is in`, reads it before any item, as [tally.walk](#counts-and-sums-in-sentences) says, so the key decides when the list can be read: `count of rs whose zz is in m named by $input.k is 1` fails as `null` with `rs` there, and as `absent` with `rs is missing` with no `rs` and the key `null`. It doesn't matter which side of the phrase the name is on: with `q` holding `"s"`, `count of xs whose $params.q is at least v is 0` fails as `unusable` with `$params.q is "s", which isn't a number` on an empty list, as `count of xs whose v is at most $params.q is 0` does. A `from` line's conditions read them the same way. A name read against the focus is read for each item, and not at all when there are none. A `count of` or `sum of` in a `whose` reads its path as it does on its own ([tally.walk](#counts-and-sums)), whatever it starts at, `$input`, `$params`, the subject, a part or a parent, so a list along the path is walked and not read as a root: `count of rows whose n is count of $input.lst.name is 1` counts the names of the items of `$input.lst`, and its row lists `$input.lst[].name` as the count on its own does. Like any name read from a root, it is read once, before any item, even when the list is empty, and a problem it has on its own fails the row with its own cause and message, said once with no item named: with `$input.lst` holding `[{"name": "bob"}, {}]`, `count of rows whose n is count of $input.lst.name is 0` fails as `absent` with `item 2 of $input.lst: name is missing`, with `rows` empty or not. The same goes for a `whose` on a `for` line or under one.

**[tally.member]** `count of member of <path>` and `sum of member of <path>` read the members of the object the path ends at as [walk.member](#every-and-some) says, and count or add them as the items of a list: `count of member of` counts the members that pass the `whose`, so "exactly one" is `count of member of evidence whose kind is "approval" is 1`. A member the `whose` can't read, or one `sum of` can't add, is named `member <key> of <list>`, like `member z of evidence is 3, which isn't an object`.

**[tally.count]** `count_of` is the number of values the path ends at in the items left in, `null` included. A value that's missing fails the side as `absent`.

**[tally.distinct]** With `distinct`, `count_of` and `sum_of` take each value once among the items left in: a value the same as one taken already, as [walk.distinct](#every-and-some) says, is left out before the values are counted or added. So `count of distinct commits.author` is the number of different authors, and `sum of distinct stages.usd` adds each different amount once. A value that's missing still fails the side, and the list's entry in `inputs` holds every value, copies included.

**[tally.sum]** `sum_of` adds up the values the path ends at in the items left in, and is 0 over none. A value that's missing fails the side as `absent`, `null` as `null`, and anything else that isn't a number as `unusable`. Numbers are added as decimals, so `0.1` and `0.2` add up to `0.3`, and so are the sides of an `add` with `text`. Take every number added, a count, a sum or an elapsed number included, and the result, and let p be the most decimal places any of them has, counted on the value, so `1.50` has 1, `1e2` has 0 and `1e-7` has 7. p must be at most 15, and each of them times 10^p must be a whole number below 10^15 in absolute value, the result included. If not, the side fails as `unusable` and its entry is `null`. That's stricter than 15 significant digits for big round numbers: `1e20` plus `1e20` fails, though the result has one significant digit. It fails closed, and every implementation can decide it exactly.

**[tally.elapsed]** An `elapsed` side has `unit`, which is `seconds`, `minutes`, `hours`, `days` or `weeks`, two paths, `elapsed_from` and `elapsed_to`, and `text`. It's the time from the first path to the second, in that unit: the nanoseconds between them divided by 1, 60, 3600, 86400 or 604800 times 10^9, rounded down to 6 decimal places. Working in whole nanoseconds and rounding down keeps the number the same in every runtime. Both paths must end `found` as [time.format](#compare_time) says, both RFC 3339 strings, compared as the instants they name, both dates, read as midnight UTC on that day so that the time between them is whole days, or both numbers from -9000000000 to 9000000000, read as seconds and rounded to the nearest microsecond. Two times in different formats fail the side as `unusable`, as [time.fail](#compare_time) says, and so does anything else. A path that ends anything but `found` fails the side as [tally.fail](#counts-and-sums-in-sentences) says. When `elapsed_to` is before `elapsed_from` the side has no number and the check fails as `value`. Its row shows the entry named after `text`, then one for each path, `elapsed_from` first, each filled as a path in `compare` is. An `elapsed` side can be a side of `compare`, among the sides of an `add`, or in the `whose` checks of a `count_of`, a `sum_of` or an `every`, where an item it fails for with `value` is left out.

**[tally.between]** `is between` after a `count_of`, `sum_of`, `add` or `elapsed` side reads the number the side works out, and passes when `min <= number <= max`, compared by value, as [range.pass](#range) says for a field. Outside the range it fails with `value`, and the bounds are as [range.bounds](#range) says. A side that fails gives the check its cause, as [tally.fail](#counts-and-sums-in-sentences) says, and the row shows what [tally.inputs](#counts-and-sums-in-sentences) says.

**[tally.not_between]** `is not between` after a `count_of`, `sum_of`, `add` or `elapsed` side passes when the number the side works out is below `min` or above `max`, compared by value, and fails with `value` from `min` to `max`. A side that fails gives the check its cause, as [tally.fail](#counts-and-sums-in-sentences) says.

**[tally.fail]** A side that fails gives the check its cause, as a path that ends anything but `found` does in [compare.fail](#compare), and the worst one when both sides fail. An `add` fails as its worst operand does.

**[tally.inputs]** For each side that's worked out, the row shows an entry named after its `text`, holding the number, or `null` when the side failed. For a `count_of` or a `sum_of`, the list it walked comes next, named and filled as [walk.inputs](#every-and-some) says. For an `add`, each side it adds up comes next, as if it stood alone. The left side's entries come before the right side's, and an entry already shown isn't shown again ([row.inputs_once](#what-a-row-shows)), so in `count of findings whose severity is "high" is at most count of findings` the right side shows only its number. The paths a `whose` reads from outside the item, a parent's, `$input`'s or the subject's own part, come after those two, sorted by name, as [walk.inputs](#every-and-some) says. A path among them whose `named by` reads a field of the item shows the part before the name and not the path it names, like `artifact.nums` for `count of rows whose n is at least artifact.nums named by key`, as [walk.inputs](#every-and-some) says.

## `compare_time`

`compare_time` takes the same parameters as `compare`, and compares two times.

**[time.format]** A time is a number, an RFC 3339 string or a date. A date is a string `YYYY-MM-DD` with nothing after it, and the date and year follow the same rules as in an RFC 3339 string. An RFC 3339 string has the form `YYYY-MM-DDTHH:MM:SS`, then optionally `.` and one or more digits, then `Z` or an offset `+HH:MM` or `-HH:MM`. The `T` and `Z` are uppercase. The date must exist, so `2024-02-30` and `1900-02-29` don't. The hour is 00 to 23, minutes and seconds 00 to 59, and the offset 00:00 to 23:59. The year, as written, is 1678 to 2261. Only the first nine digits of the fraction count. Any other string isn't a time.

**[time.pass]** It passes when both paths end `found`, both values are RFC 3339 strings, both are dates or both are numbers, and `left cmp right` holds. RFC 3339 strings are compared as the instants they name, so `2024-01-01T01:00:00+01:00` equals `2024-01-01T00:00:00Z`. Dates are compared as days, so `2024-01-31` is before `2024-02-01`. Numbers are compared by value, with no unit attached.

**[time.fail]** It fails with the worse of the two paths' outcomes when either ends anything but `found`, and with `unusable` when the values aren't two times in the same format, a number and a string included, and a date and an RFC 3339 string too, even one at midnight, because a date doesn't say in which time zone it starts. Otherwise it fails with `value`.

## `any_of`

`any_of` takes named options, each a list of checks that must all pass, and passes when one of its options does.

**[any_of.pass]** It passes when every check of at least one option passes.

**[any_of.cause]** Each option that fails has a cause: `value` when one of its `present` checks found its field missing, and otherwise the first, in the order of [causes](#causes), among its checks, or `value`. The row takes the first among its options.

**[any_of.refs]** A ref that ends anything but `found`, as [value.ref](#values) says, fails the checks that read it, and so their option, but not the others: when another option passes, so does the row. A ref that reads the wrong kind of value for its check, like a `values` ref that isn't a list, fails the row as `unusable`, even when another option passes.

**[any_of.inputs]** The row shows every path any option reads, once each, sorted by name. For an `every` or `some` in an option, that's its list, with the whole items, and the names it reads.

## `all_of`

`all_of` takes `checks`, a list of basic checks, and `assertions`, the text of each one. It's what a check written as several sentences reads into, joined with `and` or listed under `assert`, see [sentence.assert.list](syntax.md#the-shape-of-a-sentence). It's one check, with one row per subject, because its sentences say one thing together, and a policy that wants a row for each writes them as separate checks.

**[all_of.pass]** It passes when every one of its checks passes.

**[all_of.cause]** When it fails, its cause is the first, in the order of [causes](#causes), among the checks that failed.

**[all_of.inputs]** The row shows every path any of its checks reads, once each, sorted by name.

**[all_of.failed_assertions]** The row's `failures` has an `assertion` entry for each sentence that failed, in the order they were written, with its own `cause`, `inputs`, `message` and `locations` in the policy, and has none when the check passes. A sentence that walks a list has its items under it. When a ref one of them reads can't be used, that one is listed with cause `unusable` and the others with their own causes.

## `every` and `some`

`every` and `some` take a path, a basic check, `whose`, a list of basic checks, `if_any`, and `distinct` when the sentence has it. They're what the sentences `every <path> …` and `some <path> …` read into, see [sentence.every.walk](syntax.md#every-some-and-whose).

**[walk.lists]** The path is read one step at a time. At a step where at least one value read so far is a list, and the step isn't a position, every one of those values is walked: each of its items goes on along the path in its place. At that step, a value that's missing, `null` or not a list fails as `absent`, `null` or `unusable`, and an empty list fails as `value`, unless `if_any` is true, when it's skipped. After the last step, a value that's a list is walked the same way. A path where no step walks a list fails at the first value along it that isn't an object, with `absent` when it's missing, `null` when it's `null`, and `unusable` otherwise, or at the value the path ends at, as `unusable`, when every value along it is an object. That place is the one `list` entry in `failures`, so a lone list that's `null` fails as `null`, as it does when another item's list is walked.

**[walk.start]** The value a path starts at is walked too when it is a list: the subject, a part, a `for` alias or `$input`. This holds after `every`, `some`, `count of` and `sum of`, for an item of a `for` line that has no position, and on the right of the phrases [walk.right](#compare) names, and a subject and an alias read the same way. A path that starts at the subject is then named after the subject's name, as `count of t` is: with the subject `t` holding `[{"name": "a"}, {"name": "b"}]`, `every name is "a"` fails as `value`, its `inputs` entry is `t[].name`, its message `item 2 of t: name is "b"`, and the input of its `item` entry is `t[1].name`. An alias is named after itself, like `item 1 of d`. A part at the start of the path is written out in the name, because the list walked is the subject: `every pl.name is "a"` with the part `pl` at `c` is named `t[].c.name`, and has no `part` tag. Only that first list is walked. An empty one fails as `value` and a `null` start as `not_an_object` ([walk.flaws](#every-and-some)), and a list directly inside it isn't walked again: its item isn't an object, so it fails as `not_an_object` when the path goes on into it, as it does in the middle of a path, so `every n is 1` on `[[{"n": 1}]]` fails `item 1 of t`, as `every rows.n is 1` with `rows` `[[{"n": 1}]]` does. A check that also reads a field of the subject in a place that doesn't read each item, a key with `named by`, like `every age_days is less than $params.max_days named by severity`, a bare name on the right of the phrase after `every` or `some`, like `every name is other`, a name read from the subject in a `whose`, or a field read by a sentence of a `for` line, like `o is boss` after `for: every owner as o`, other than on the right of the phrases [walk.right](#compare) names, can't read that field from a list, so it fails as `not_an_object` as a whole, says `t is [...], which isn't an object` once, and reads no item. On the right of those phrases the subject is walked, so `r.v is in name` after `for: every rows as r` reads `name` in each item of `t`, as `every rows.v is in name` does, while `r.v is name` still fails as `not_an_object`. A position read from the subject, like `t[0].y` in a `whose`, reads the list and doesn't count. A path anywhere else that starts at a list fails as `not_an_object`, as [path.not_an_object](#reading-a-path) says, and a parent that is a list is one value, which gives its child no subjects ([subjects.chain.not_an_object](#requirements)). The root of `$params` is never walked, because it is always an object.

**[walk.items]** The items of the innermost list walked are what the check is about. Each one is checked on its own: the basic check reads the rest of the path, after the item, as its own, and the `whose` checks read their paths from the value the path ends at, the focus ([sentence.resolve.focus](syntax.md#where-a-name-resolves)), which is the item itself when the path ends at the list. A focus that isn't an object fails a check that reads a field of it as `not_an_object`, one that is missing fails it as `absent`, and one the path couldn't reach fails it as the path does. The other names of the basic check, on the right side of its phrase, resolve from their root, so a bare name is the subject's field ([sentence.resolve.root](syntax.md#where-a-name-resolves)). An item is undecided when a `whose` check fails with any cause but `value`, even when another one fails with `value`, as a filter that can't decide fails the requirement (see [scope.unreadable](#scope)). Otherwise it's left out when a `whose` check fails with `value`.

**[walk.every]** `every` passes when nothing failed while walking, no item is undecided, every item left in passes, and at least one item is left in, or `if_any` is true. Otherwise it fails with the first, in the order of [causes](#causes), among what failed, or with `value` when the only problem is that no item was left in.

**[walk.some]** `some` passes when at least one item left in passes. Otherwise it fails with the first, in the order of [causes](#causes), among what failed while walking, the undecided items and the items that failed, or with `value` when there were none.

**[walk.distinct]** With `distinct`, an item left in whose value at the end of the path is the same as an earlier item's left in is dropped, so it isn't checked again, and the earlier item's `item` entry in `failures` lists the location of every copy, in the order the walk reads them. Two values are the same when they're equal as JSON: the same type, strings with the same characters, numbers with the same value, so `1` and `1.0` are the same, lists with the same items in the same order, and objects with the same keys holding the same values, whatever order the keys are written in. An item a `whose` check can't decide isn't left in, and a value that's missing or can't be read is never the same as another, so both still fail with their cause. The basic check reads only the value, its own data and what lies outside the item, because a basic check that reads another field of the item is written wrong ([sentence.distinct.place](syntax.md#every-some-and-whose)). So copies pass or fail together, and `distinct` changes only how many `item` entries `failures` has. The row's `inputs` still list every item, copies included, as [walk.inputs](#every-and-some) says.

**[walk.flaws]** When a ref the check reads, in its path, its `whose` checks or its phrase, can't be used, or the input or params hold something JSON can't, the check fails as `unusable` and its assertion has no `item` entries, as a plain check does. A `named by` key from outside the items that a `whose` reads is said once, before any item and with no item in front, and each item whose value before the key can't take a key says so after it, with an `item` entry whose input is that value: with no `k` in the params and `xs` holding `[{"v": 1}, {"v": 1, "m": null}]`, `every xs whose v is m named by $params.k exists` says `$params.k is missing; item 1 of xs: m is missing; item 2 of xs: m is null`, and so do `some`, `count of` and a `for` line's `whose`. With `k` holding `3` they say `$params.k is 3, which isn't text` and then the same items, and an item whose `m` is an object gets no entry. An item that also fails on another field says that too, as it would with a key it can read: with `k` holding `3` and `xs` holding `[{"v": 1}]`, `every xs whose zz is m named by $params.k exists` says `$params.k is 3, which isn't text; item 1 of xs: zz is missing, and m is missing`. Its message names what can't be used, and never a list along the path, which the walk reads as a list: `every xs.v, if any, is not in $params.q` with `q` `"s"` says `$params.q is "s", which isn't a list` whatever `xs` holds, and `count of rows.w named by p is 1` with `p` `3` says `p is 3, which isn't text`, as `every rows.w named by p is 1` does. A `named by` key read from `$params` or `$input` in a `whose` or in the phrase is read the same way, before any item: with `es` `[]`, `every es whose zz is m named by $input.k, if any, exists` and `every es.v, if any, is m named by $input.k` fail as `absent` with `$input.k is missing` when the key is missing, as `null` when it is `null`, and as `unusable` with `$input.k is 3, which isn't text` when it holds `3`. A `from` line's condition reads it the same way, so `things whose every es.v, if any, is m named by $input.k` fails `$applies` as `unusable` for a thing whose `es` is `[]`. Every key that can't be read is said, worst cause first and then by name, and the worst cause wins, as it does for any two paths: `every es whose zz is m named by $input.k and whose v is m named by $input.j, if any, exists` with no `k` and `j` holding `3` fails as `unusable` with `$input.j is 3, which isn't text; $input.k is missing`, and with `k` and `j` both holding `3` it says `$input.j is 3, which isn't text; $input.k is 3, which isn't text`, and so does a `count of` with the same `whose`, on an empty list and on one that is missing, `null` or text. Params that aren't an object fail the check as `unusable`, and on an empty list the keys are said the same way: with the params `3`, `es` `[]`, no `k` and `j` holding `3` in the input, `every es whose zz is m named by $input.k and whose v is m named by $input.j, if any, exists` still says `$input.j is 3, which isn't text; $input.k is missing`. On a subject that isn't an object or a list, `null` included, with a path that starts at the subject, it fails as `not_an_object`. A subject that is a list is walked, as [walk.start](#every-and-some) says. A root name that the phrase or a `whose` reads as a list and that isn't one fails it as `unusable` the same way, on an empty list too: `every xs.v, if any, is not in pl.z` with the part's `z` `"s"` says `pl.z is "s", which isn't a list` when `xs` is `[]`, and so does a `for` item `every xs whose v is in pl.z as m`. A root of the wrong type for any other phrase fails it the same way, before any item and with no item in front: `every xs.v, if any, is at least z` with `z` `"s"` says `z is "s", which isn't a number` on an empty list too, `starts with` says `isn't text` and `is before` says `isn't a time`. Each root that fails is named once, worst cause first and then by name, as [problems.item_order](#which-problems-a-message-says) says. When a ref step in its path can't be read, it fails with the ref's cause, its `inputs` hold `[]`, and its message names the path, then each root the phrase can't read, whatever its cause: `every xs named by $params.k, if any, equals q` with neither there says `xs named by $params.k is missing; q is missing`. When the list itself is missing, `null`, the wrong type, or empty in a check that fails on an empty list, in an `every`, a `some`, a `count of` or a `sum of`, each root that a `whose` or a `that` reads and that can't be read, `$params`, `$input`, a field of the subject, a part, a parent's part, a grandparent's part or an alias, is named first, then a root on the right of the phrase that can't be used, then the list, as [problems.all_said](#which-problems-a-message-says) says, in an option of an `any_of` too, and the check takes the worst cause of all of them, while the `item` entries stay what they would be without the list's problem: with the parent's part `art.cov` `null` and no `ys`, `every ys whose n is at least art.cov.z, if any, exists` fails as `absent` with `art.cov is null; ys is missing`, with no `z` in the params and `es` `null`, `every es whose v is in $params.z, if any, exists` and `count of es whose v is in $params.z is 0` fail as `absent` with `$params.z is missing; es is null`, and with the part's `z` `"s"` and no `es`, `some es whose v is in pl.z exists` fails as `unusable` with `pl.z is "s", which isn't a list; es is missing`. On a `for` line, a root read through the alias of an earlier list goes with its item: `every es whose v is in w.z, if any, exists` under `for: every ws as w` with no `z` in the item and `es` `null` says `item 1 of ws: w.z is missing, and es is null`. With the params `{"y": "s"}` and no `es`, `some es whose v is in $params.z is in $params.y` fails as `unusable` with `$params.y is "s", which isn't a list; $params.z is missing; es is missing`. When the params aren't an object, the list isn't named ([OPEN.md](OPEN.md#differs-from-the-general-rules)). Two roots in a `whose` that fail in different ways take the worst cause on a list that can be read too: with `$params.z` `null`, no `y` in the input and `es` holding `[{"v": 1}]`, `some es whose v is in $params.z and whose v is in $input.y exists` fails as `absent` with `$input.y is missing; $params.z is null`.

**[walk.inputs]** The row's `inputs` has one entry, named after the path with `[]` after each list walked, like `pull_requests[].commits[].signed`, holding the value each item's path ended at, in order, `null` where it ended missing. The items `whose` leaves out are there too. Where the walk stopped early, `[]` only follows the lists it walked. The row also lists each path its check or its `whose` reads from outside the item, as a plain check does, once each: a parent's like `artifact.owner`, one of `$input`, the list or patterns after a phrase like `is in`, `contains all of` or `matches` included ([path.right_inputs](#what-a-row-shows)), and the subject's own part, named like the plain form names it, `w`, with its `part` tag ([parts.tag](#parts)). Such a path that walks a list, at its start like `name` on a subject that is a list, or in the middle like `os.name` with `os` a list, on the right of a phrase [walk.right](#compare) names or after a `count of` or `sum of`, is listed as a plain check lists it, with `[]` after each list walked, the value of each item, `null` where an item stopped, one location for each, and the same `part` tag. So with the subject `t` holding `[{"name": "ann", "rows": [{"v": "ann"}]}, {"name": "bob", "rows": [{"v": "bob"}]}]`, `every rows.v is in name` lists `t[].name` holding `["ann", "bob"]`, as `$params.who is in name` does. The walk's own entry is sorted with these, by name, so a parent that sorts before the list comes first. A path with a `named by` is listed as a plain check lists it, like `artifact.map named by artifact.key`. A `for` alias's value is never listed. A path whose `named by` reads a field of the item, in a `whose`, or an alias isn't listed as a whole, since it changes with each item, but the part before the name is, like `artifact.nums` for `count of rows whose n is at least artifact.nums named by key`, once each, whether the check is on a `for` line or in a `from` line's conditions. When that part walks a list, like `artifact.ls.m` in `every artifact.ls.m named by k` with `k` a `for` alias, nothing of it is listed, as [for.inputs](#for) says. On the right of the phrase after `every` or `some`, a `named by` reads the subject's field whatever the path starts at ([path.field_step](#reading-a-path)), so the path is listed as a plain check lists it: `some rows.n is at least artifact.nums named by key` lists `artifact.nums named by key` and `key`, and `every xs.v equals $params.m named by k` lists `$params.m named by k` and `k`, as `v equals $params.m named by k` does. The same goes for a path in a `whose` whose key is the subject's, like `$params.m named by pr.k`: it lists the path and `k`, and a path that starts at the item or an alias lists only `k`. A `$params` path isn't an entry of `inputs`, and stays in the check's `$refs` where it already is ([value.refs](#values)). A bare name on the right that isn't a part's alias, and a name written with a dot like `.w`, is the subject's field, and is listed as a plain check lists it, a field it is `named by` included, like `m named by k` and `k`.

**[walk.failed_items]** When the check fails, the row's `failures` has one `assertion` entry, named by the sentence as written, and under it, in path order: each item that failed the basic check, as an `item` entry named like `item 2 of commits`, with `value` the item and `locations` where it sits, and its `inputs` holding what the path read inside it, like `commits[1].signed`; each undecided item, as an `item` entry whose inputs hold the field of the first `whose` check that couldn't decide, or `null`; and each list that failed while walking, as a `list` entry named by the list. A list walked inside an item goes under that item. An item that `whose` left out isn't listed. A row that passes has no `failures`.

**[walk.failed_items.side]** A `whose` check that compares two sides puts one of them in the item's `inputs`: the side that wasn't read, or the left side when neither was read or both were. A side is read when its path ends `found`, so a path that ends `absent`, `null`, `unusable` or `not_an_object` isn't. A `count of` or `sum of` side has the path of its list, and is read only when that path ends `found` on a list, so with `{"kids": 5}` the side in the inputs is `count of kids`, with path `kids`. An `add` or `elapsed` side has the first of its paths that wasn't read, or its first path when all were, and a `count of` or `sum of` inside an `add` is read only when its list is a list, as on its own. A side that reads outside the item, a `$params` or `$input` path, a part of the subject or a field of a parent subject, is named by its own path, written as in `inputs`, like `$params.min`, `w` or `art.q`, with its own location, not as a path inside the item. So `whose lo is at least hi` names `hi` for `{"lo": 1}`, `lo` for `{"hi": 1}` and for `{}`, and `lo` for `{"lo": "x", "hi": 1}`, and `whose count of kids is at least min` names `min` for `{"kids": [1]}` and `kids` for `{"min": 1}`.

**[walk.member]** `every member of <path>`, `some member of <path>`, and `member of` on a `for` line, walk the path as `every` does, lists along it included, but read no list at the value it ends at: each member of each object it ends at is one item, in key order, which is code point order, and from there an item is handled as an item of a list ([walk.items](#every-and-some)). An object with no members is an empty list. A failed member is named `member <key> of <list>` wherever a list item is named `item N of <list>`, in the message and in `failures`, with the key written as a path writes it ([sentence.path.string](syntax.md#paths)) and the list named as [message.items](#what-a-row-shows) names it: with `{"statuses": {"build": "DONE", "sign-off": "FAILED"}}`, `every member of statuses is "DONE"` fails as `value` with `member sign-off of statuses is "FAILED"`, and keys like `"a; b"`, `""` and `"1"` give `member "a; b" of statuses`, `member "" of statuses` and `member "1" of statuses`. A member read by its key, like `statuses.sign-off`, is the name of its input. The row's input for the object is named as the path is written, like `statuses`, with the members' values in key order and each member's location. On a `for` line the member is named with the alias's list, like `item 1 of records: member x of r.evidence: e.status is "NO"`. After three members the message ends with `and N more`, as for items. A sentence that reads only the alias names the member as the value, like `member a of ms is 0` for `m is 1` under `for: every member of ms as m`, as [message.alias](#what-a-row-shows) names an item.

**[walk.member.not_an_object]** A value the path of `member of` ends at that is there but isn't an object, a list, text, a number or true or false, fails as `unusable`, named with the message a check gives where it needs an object, like `statuses is ["DONE"], which isn't an object`, and has a `list` entry in `failures`. A value that is missing or `null` gives `absent` or `null` as any path does. The row's input for the object then has the `outcome` `unusable`, `absent` or `null`, as [row.parts](#what-a-row-shows) says. This holds on a `count of` or a `sum of` whose path has no list along it, and on a `for` line's second list. When an `every member of` sentence walks a list on the way and no object is found at any of its ends, the input takes the worst of what the ends hold, in the order [Causes](#causes) gives, whatever the order of the items: `every member of rs.statuses is "DONE"` with `rs` holding `[{"statuses": null}, {"statuses": 3}]` has the input `rs[].statuses` with the `outcome` `unusable`.

## `for`

`for` takes `items`, one or two, each with `every` or `some`, a path, `whose`, `if_any`, an alias and, when the item has it, `distinct` or `member`, and `checks` and `assertions`, as `all_of` does. It's what a check with a `for` line reads into, see [sentence.for.line](syntax.md#the-for-line).

**[for.walk]** Each item's path is walked as an `every` or `some` path is, see [walk.lists](#every-and-some), and its alias stands for the value the path ends at in each item of the innermost list walked. The `whose` checks read from that value, the focus, and an item is undecided or left out as [walk.items](#every-and-some) says. An item `whose` keeps, whose path ends at a value that's missing or that can't be read, fails as `absent` or `unusable`, or as `not_an_object` when the item isn't an object, `null` included, and the path goes on into it, without its checks being run. The second item's path and its `whose` checks can start at the first item's alias, and then it's walked again for each item of the first list. An alias that holds a list is read item by item there, as [walk.start](#every-and-some) says: with `deps` `[[{"name": "a"}, {"name": "b"}]]`, `for: every deps as d, every d.name as n` with `n is "a"` fails `item 2 of d` as `value`. An item with `member of` reads each member of the object its path ends at as one item, as [walk.member](#every-and-some) says, and its alias stands for the member's value.

**[for.pick]** An item with a position walks its path as [for.walk](#for) says, with an empty list allowed along the way, and keeps the items its `whose` keeps. An item the `whose` can't decide fails the check with its cause, and nothing is picked. With `sorted by`, the field is read on the value each item kept stands for, the focus: numbers are ordered by value, RFC 3339 times by the moment they name, and dates by day, as [time.pass](#compare_time) says. With `alphabetically`, the field has to be a string, and strings are ordered code point by code point, as [compare.alphabetical](#compare) says. A field that's missing fails its item as `absent`, a `null` one as `null`, one on an item that isn't an object as `not_an_object`, and anything else, without `alphabetically` a string that isn't a time or a date included, as `unusable`. When the fields mix numbers, RFC 3339 times and dates, the items of the first kind in that order are kept and the others fail as `unusable`, so with numbers and times the times fail. When any item fails, nothing is picked. The position counts from 1, from the start of that order or from its end with `last of` and `from last`. Without `sorted by`, the order is the order the walk reads the items. A position past the end, an empty list included, fails the check as `absent`, and there's no item to list in `failures`. When another item's field equals the picked item's, it fails as `ambiguous`, and each item with that value fails as `ambiguous` too, with the value as its `value`. Otherwise the alias stands for the picked item and it is tried as [for.try](#for) says, as an `every` over that one item. A picked item that doesn't start at the first item's alias fails the check the same way whether it's written first or second. When its `whose` or its `sorted by` reads the first item's alias, like `first of es sorted by m named by x` under `every xs as x`, it's picked again for each item of the first list, so with no item of the first list nothing is picked. An item of the first list that picks nothing fails the check as `absent` and isn't listed in `failures`, and one whose pick fails another way is listed, with that failure under it.

**[for.try]** The checks read the subject, with each alias standing for its item. With one item, an item passes when all the checks pass. With two, an item of the first list passes when the second item passes for it, as [walk.every](#every-and-some) or [walk.some](#every-and-some) says, where an item of the second list passes when all the checks pass. A failed item's cause is the first, in the order of [causes](#causes), among the checks that failed, or what failed in the second item's walk.

**[for.if_any]** When an item's list is empty with `, if any,`, or its `whose` leaves no item in it, the checks that don't read that item's alias still run, as they do when the list fails ([for.pass](#for)), and a check that reads it, as [for.second_items](#for) says, has nothing to check and is left out. When the second item's list is like that, an item of the first list is tried with the checks that don't read the second item's alias, as [for.try](#for) says for one item, and passes when they all pass, so when every check reads that alias, the item passes, as [walk.every](#every-and-some) says. This holds whether the first item has `every` or `some`, and for an item of the first list that isn't an object too, apart from an alias read whole, as [for.roots](#for) says. With `for: some approvers as ap, every commits, if any, as c`, `ap.state is "APPROVED"`, approvers `[{"u": "ada"}, {"u": "g", "state": "REJECTED"}]` and `commits` holding `[]`, the check fails as `absent` with `item 1 of approvers: ap.state is missing; item 2 of approvers: ap.state is "REJECTED"`, and `failures` lists both approvers under that sentence, as it would with commits. With `c.author is ap.u` instead, it passes. When the first item's list is like that, the check reads as a `for` line with only the second item and the checks that don't read the first item's alias would: `for: every commits, if any, as c, some approvers as ap` with the same approvers, sentence and `commits` fails as `absent` with `item 1 of approvers: state is missing; item 2 of approvers: state is "REJECTED"`. The second list still fails as [for.walk](#for) says when it's empty without `, if any,`, missing, `null` or not a list, so approvers `[]` fail as `value` with `approvers is []`. When every check reads the first item's alias, nothing is left to check and the check passes, whatever the second list holds. A second item whose path, `whose` or `sorted by` reads the first item's alias is left out with it. With no item left, the checks that read no alias run once, the row names what they read with no item in front, as [for.roots](#for) does, and the sentence has no items: `for: every xs, if any, as m` with `z is 1`, `z` holding `3` and `xs` holding `[]` fails as `value` with `z is 3`. In every case the row's `inputs` are those of the whole `for` line, as [for.inputs](#for) says.

**[for.named_by]** A path with a `named_by` step reads the key that the step's alias holds for the item being tried, as a ref step reads a key from the params. When the alias holds `null`, the check fails as `null`, and when it holds anything else that isn't a string, a number included, as `unusable`. The alias has to be given before it's used: in the `assert` lines, or in a later item's path or `whose`. Sentences write such a step as `<path> named by <alias>`.

**[for.distinct]** An item with `distinct` drops the items its `whose` keeps whose value is the same as an earlier one's, as [walk.distinct](#every-and-some) says, and its alias stands for the first of them. Its `item` entry in `failures` lists the location of every copy, in the order the walk reads them. What the sentences read through the alias, in the entries under it, is what they read on the first copy. A second item is walked for the first copy only, so what lies under the other copies isn't read or shown.

**[for.pass]** The check passes or fails as the first item does, by [walk.every](#every-and-some) or [walk.some](#every-and-some), with its items judged as [for.try](#for) says. A sentence that reads no alias, like `z is 3` under `for: every xs as x`, doesn't depend on the item, so it is run and judged on its own whatever the walk does, and fails the check when it fails: when the list is missing, `null`, not a list or empty, and when a `named by` key on the line can't be read, as much as when the items are fine. So does a sentence that reads the first alias but not the second, for an item of the first list whose second list fails. The message says such sentences first, in the order they're written, and then what the walk broke: with `z` holding `2`, `x is 1` and `z is 3` say `z is 2; xs is missing` with no `xs`, `z is 2; xs is []` when `xs` holds `[]`, and `z is 2; $params.k is missing` under `for: every o named by $params.k as x` with no `k`. Each such sentence has its own `assertion` entry, with the message `z is 2`, beside the walk's `list` entry on the row, or beside the key in the row's `inputs` ([row.parts](#what-a-row-shows)). A sentence that reads the alias isn't run when the walk breaks. An item of the first list that is an object, where what a later line or a sentence reads through its alias is missing, `null` or of the wrong type, as [for.roots](#for) says, fails for that item, even when nothing is checked for it because the second list is empty with `, if any,` or its `whose` leaves nothing, and every check reads the second item's alias, as [for.if_any](#for) says. An item that isn't an object is judged only as [for.try](#for) and [for.if_any](#for) say, apart from an alias read whole, as [for.roots](#for) says, so when nothing is checked for it, it passes. So with `some` first, the check passes when one item passes, whatever item comes after it, and then what the other items' aliases hold isn't named. With `some approvers as approver, every commits, if any, as commit`, `commit.author is approver.u` and `commits` holding `[]`, approvers `[{"username": "ada"}, {"username": "grace", "u": "grace"}]` pass, through grace, `["str", {"username": "b"}]` pass, through `"str"`, and `[{"username": "ada"}]` fail as `absent` with `item 1 of approvers: approver.u is missing`. When no item passes, each of those problems is named with its item in front.

**[for.inputs]** The row shows each item's list once, named after its path with `[]` after each list walked, holding the values its alias stands for, and the inputs the checks would show on their own, a list or patterns read from `$params` or `$input` included, like `$params.l` for `x.n is in $params.l` ([path.right_inputs](#what-a-row-shows)), a list an `every` or `some` walks from `$params`, like `$params.q[]` for `every $params.q is 1`, a piece of a `followed by`, like `$params.x` for `i.tags contains i.v followed by $params.x` ([compare.join](#compare)), and a list a phrase walks, like `t[].name` for `r.v is in name` on a subject `t` that is a list, as [walk.inputs](#every-and-some) says, in the line's own `whose` too, like `pos[].name` with its `part` tag for `every rows whose v is in pos.name as r`, leaving out paths that start at an alias, once each, even when no check was run, all sorted by name. A second item that starts at the first item's alias is named with that alias, like `pr.approvers[]`, and one that starts at a parent's name is named with that name, like `artifact.map named by k[]`, and both hold, in order, the items of every list they walked under the items the first item kept. What lies under an item the first item's `whose` leaves out, or can't decide, was never read, so it isn't shown. The first item's own entry still holds every item of its list, those its `whose` leaves out included, as [walk.inputs](#every-and-some) lists them. A picked item is named where it is in the input, like `item 1 of commits`, and holds the item. When nothing is picked, the list is shown as for any item, and so is the second item's list when the first list is empty, even when its `whose` or its `sorted by` reads the first item's alias. Paths that start at an alias aren't shown, but a path that starts at a parent's name is, like `t.x`, with the parent's value, as a check without a `for` line shows it. A path that reads through an alias further on, like `shas named by persona`, shows the part before the name, `shas`. A field a `named by` reads from the subject is shown too, like `k` for `row.w named by k`, sorted with the rest by name. An `every`, `some`, `count of` or `sum of` through an alias doesn't show the values it reads through the alias, or a count's number, but does show the part before the name, like `artifact.map` in `some artifact.map named by k is at least 1`, unless that part walks a list, like `artifact.ls.m` in `every artifact.ls.m named by k is at least 1`, where nothing of it is shown because it would hold a value for each item, and the parent values its check, its right side or its `whose` reads, also when it reads them through an alias, like `artifact.nums` in `some rows.n is at least artifact.nums named by k`, and a `count of` or `sum of` whose own list doesn't start at an alias shows that list, like `artifact.people[]` in `count of artifact.people whose name is c.author is at least 1`.

**[for.failed_items]** When the check fails, `failures` has an `assertion` entry for each sentence that failed, named by the sentence as written, with the items of the first list it failed for under it, in list order, each an `item` entry named like `item 2 of pull_requests`, with `value` what its alias stands for, or `null` when that's missing or can't be read, and `locations` where it sits. With two items, an item's cause is the first, in the order of [causes](#causes), among the causes it failed with for the second list's items, and the items of the second list that the sentence failed for sit under it, as [for.second_items](#for) says. A sentence that doesn't read the alias is an entry of its own, with no item of the `for` line in front: its `failures` hold its own items, as it would hold them as a check of its own, and are `[]` when it walks none, and its `message` is the one it would give as a check of its own. What the `for` line's own walk breaks, before any sentence is checked, sits on the row, as [for.shared_failures](#for) says. An item of the first list isn't listed when the second item's position picks nothing for it.

**[for.second_items]** With two items, a sentence that reads the second item's alias has, under each item of the first list it failed for, the items of the second list that it failed for, in path order, each an `item` entry with its own `cause`, named like `item 2 of commits`, or with the first item's alias when the second item starts at it, like `item 1 of pr.approvers`, and holding the inputs that pair read. An item of the second list that failed before any sentence was checked for it isn't under a sentence, as [for.second_failures](#for) says. A sentence reads the alias when a path in it starts at the alias, a `whose` included, or has a step `named by` it. A quoted string, like `"$commit"`, doesn't.

**[for.failure_inputs]** An `item` entry under a sentence has `inputs`, and so does an `assertion` entry that has no items. When the sentence walks a list under the item, or a `count of` or a `sum of` on it can't read an item, the item holds the items of that list as entries, as [row.parts](#what-a-row-shows) says, and its own `inputs` hold only what the sentence read through the alias outside them and the value a `count of` or a `sum of` works out. Otherwise they are the entries the sentence would show in its own row's `inputs` on that item, or on that pair of items for an item of the second list, but never the list it walks, as [row.parts](#what-a-row-shows) says: the same `name`, `value`, `locations` and, where a row has it, `part`, as [path.inputs](#what-a-row-shows), [compare.inputs](#compare) and [tally.inputs](#counts-and-sums-in-sentences) say, with each alias named as the sentence writes it, like `approver.timestamp` or `commit.files[]`. The entries of any other sentence with two sides, like a comparison, `is in`, `contains` or a count, keep the order of its own row, its left side and then its right side ([compare.inputs](#compare), [tally.inputs](#counts-and-sums-in-sentences)), and aren't sorted by name. An `every` or a `some` lists the entries that start at an alias first, sorted by name, and then the rest, sorted by name as [walk.inputs](#every-and-some) says. So `some rows.n is at least x.v` lists `x.v` before `rows[].n`, and `count of rows is at least m` lists `count of rows`, `rows[]` and then `m`. That holds when a `whose` reads something outside the item too: `every rows.n whose z is at least $input.q is at least x.v` lists `x.v`, then `$input.q`, then `rows[].n`, and a parent's field, like `t.x`, is sorted among the rest in the same way. A value the sentence reads twice is listed once, and entries with the same name are ordered as [row.inputs_once](#what-a-row-shows) and [location.merged](#where-a-value-was-read) say. A path that starts at an alias starts at the location that alias was read at, as [location.failed_items](#where-a-value-was-read) says, and goes as far as its read went, as [location.read](#where-a-value-was-read) says, so a read that stops early has `value: null` and the location where it stopped. A path that starts at an alias holding a list and walks it on the right of a phrase [walk.right](#compare) names, or in a `whose`, like `d.name` in `every rows.v is in d.name` with `d` holding `[{"name": "ann"}, {"name": "bob"}]`, is listed as `$params.w is in d.name` lists it, as `d[].name` holding `["ann", "bob"]`, `null` where an item stopped, with one location for each ([walk.inputs](#every-and-some)). A `count of` on an empty list gives the count `0`, the list `[]` and no locations. A sentence that doesn't read the second item's alias reads the same for every item of the second list, so its entry shows what it read on the item of the first list that the entry belongs to. A `named by` that names an alias adds no entry for it, because the item's `value` holds it. Every sentence that failed has `inputs`, however many items failed, and they never change `passed`, `cause` or an item's name.

**[for.second_failures]** With two items, a failed item of the first list has under it what failed in the second item when it failed for it before any sentence was checked, and nothing otherwise. That is an `item` entry for an item a `whose` couldn't decide or can't read, or whose path ended at a value that's missing or can't be read, named as in [for.second_items](#for) with `value` what its alias stands for, or `null`, and a `list` entry for a list that failed while walking, missing, `null`, not a list or empty. A path whose ref step can't be read is not an entry of either kind: it is a root, said once, as [row.parts](#what-a-row-shows) says of a `named by` key. An item of the second list that its `whose` can't read is reported like that, also when the second item starts at the first item's alias: `for: every envs as e, every deploys whose env is e as d` with `d.ok is true` says `item 1 of envs: item 1 of deploys: d.ok is false; item 1 of envs: item 2 of deploys: env is missing`.

**[for.shared_failures]** When the second item doesn't start at the first item's alias, some of what [for.second_failures](#for) lists is the same for every item of the first list: a list that failed while walking, and, when none of the second item's `whose` checks reads the first item's alias, the items that can't be read or that a `whose` couldn't decide. A first list that fails is a `list` entry on the row, like `xs`. A second list that fails for an item is an `item` entry on the row, like `item 2 of ws` with the message `""`, holding the `list` entry, like `w2.ys` with the message `w2.ys is null`. They sit on the row once, after the assertion entries, instead of under each sentence that reads the alias or under each item of the first list, because that would say it twice and break [problems.all_said](#which-problems-a-message-says). This is the one exception to the order of levels in [row.parts](#what-a-row-shows): on a `for` line, an item can sit directly under the row when the `for` line's walk broke there before any sentence ran. An item that failed a sentence still sits under that sentence. An item of the first list that failed only because of them isn't listed, and one that is listed has as its cause the first, in the order of [causes](#causes), among the causes of its sentences and of what's still under it. The row's cause doesn't change.

**[for.flaws]** When a ref the check reads can't be used, or the input or params hold something JSON can't, it fails as `unusable` and its assertion has no `item` entries, as [walk.flaws](#every-and-some) says. On a subject that isn't an object, with an item's path that starts at the subject, it fails as `not_an_object`, unless the subject is a list and the item has no position: then the item walks it, as [walk.start](#every-and-some) says. With the subject `[{"stage": "build", "owner": "ana"}, {"stage": "test", "owner": "bo"}]` and the params `{"allowed": ["ana"]}`, `for: every owner as o` with `o is in $params.allowed` passes the first stage and fails the second as `value`. An item with a position reads a list subject as it reads any subject that isn't an object. An item whose path can't go on into it, because it isn't an object, is named by its value in the message, `item 2 of t is 3, which isn't an object`, and its `value` in `failures` is `null`. An item of the innermost list walked that isn't an object, `null` included, fails as `not_an_object` when the item's path goes on into it, as `every` does: with `t` holding `["a"]`, `for: every t.k as x` fails `item 1 of t` as `not_an_object`. That holds with a position, with `some`, and for a second item whose path reads into the first item's name. When a ref step in the first item's path can't be read, it fails with the ref's cause, it has no `item` entries, and that path's input holds `[]`. In the second item's path, the first list's item fails with the ref's cause instead, and the path is listed as [for.second_failures](#for) and [for.shared_failures](#for) say. A root a sentence under the line reads is named once, with no item in front, like `$params.p is missing`. A root of a second item's `whose` that reads the first item's alias, like `m.q` in `every ys as m, every xs whose v is in m.q, if any, as n`, is read for each first item before any item of the second list, on an empty list too, and is named under its first item, as `item 1 of ys: m.q is "s", which isn't a list`, after the roots that don't read an alias.

**[for.roots]** A name under a `for` line whose value doesn't depend on the item is a root: a field of the subject or of a part, `$params` or `$input` with or without a path after it, and an alias of an earlier line, in the line's own `whose` as much as in its sentences. Each root is read once, before any item. A root that a compare or `is in` phrase reads as a value, like `z` in `m.v is at least z`, `$params.q` in `m.v is in $params.q`, `z` in `z is 1` or `z` in `z is at least 1`, a root that `count of` or `sum of` reads, like `z` in `count of z is 1`, and a `named by` key, like `z` in `m.t named by z is 1`, fails the check when it is missing, `null` or of the wrong type, even when the list is empty, with or without `, if any,`, and the row names it as [problems.where_said](#which-problems-a-message-says) says. The wrong type is what the phrase can't read: `z is "s", which isn't a number` for `z is 1`, `z is not 1`, `z is 1 within 1` and `z is at least 1`, with `xs` empty and `, if any,` as much as with items, `z is 3, which isn't true or false` for `z is not true`, `z is "s", which isn't a list or an object` for `count of z` and `sum of z`, `z is {"a": 1}, which isn't a list` for an object, with or without a `whose`, as with items, and `z is 3, which isn't text` for a key. In `count of w.z`, the first step that can't be read is named, like `w is missing`, an object at the end is named as `w.z is {"a": 1}, which isn't a list`, and a list along the path is walked as usual. When a sentence reads two roots that can't be read, each is named once and the sentence isn't said again after them: `count of zb is count of za` with `zb` holding `"s"` and `za` holding `3` says `za is 3, which isn't a list or an object; zb is "s", which isn't a list or an object`, with items or without. Every root of one sentence is named once, worst cause first and then by name, whatever the phrase that reads it: `za is at least zb` with `za` `null` and `zb` holding `"s"` says `zb is "s", which isn't a number; za is null`, because `unusable` is worse than `null`, and the two `count of` roots above tie, so `za` comes first. A root of the right type that doesn't match, like `z` holding `3` in `z is 1`, can still be read, so it isn't named here, but on an empty list with `, if any,` the check still runs, as [for.if_any](#for) says, and fails with `z is 3`. On the left, this covers `is`, `equals`, `is not`, `does not equal`, the number compares (`is at least`, `is at most`, `is more than`, `is less than`), the text compares (`starts with`, `ends with`, their `does not` forms and `is alphabetically …`), the time compares (`is before`, `is after`, `is on or before`, `is on or after`) when the value isn't a time at all, and `is … within` and `is not … within`. On the right it covers the compares and `is in`. A root read any other way, like `every z` or `z exists`, is read for each item, and once when there's no item, as [for.pass](#for) and [for.if_any](#for) say, so on an empty list `z exists` with no `z` says `z is missing; xs is []`. A root that depends on the item keeps the item in front, because it can differ for each: the line's own alias, and a `named by` key read from the item. An alias of an earlier line is named with that line's item in front, like `item 1 of approvers: approver.state is missing`, and fails only that item, so with `some` first the check still passes when another item passes, as [for.pass](#for) says. This holds, for an alias read through a field, for an item that is an object. For an alias read through a field, an item that isn't an object isn't named here, and is judged as [for.try](#for) says. An alias read whole, not through a field, like `k` in `named by k`, doesn't need its item to be an object: it fails like any other root when its value can't be read, as `k is 3, which isn't text` does for `ks` holding `[3]`. An item that is a list is walked by a field read like any list: `d.name` reads each member, and a member that can't be read fails the item as [walk.right.fail](#compare) says, even when nothing is checked for it. The message says them in the order [problems.all_said](#which-problems-a-message-says) gives, and an item doesn't say the roots again, like `item 1 of xs: m.v is 1`. The sentences that read no alias come first, as [for.pass](#for) says, each with its own roots: under `for: every xs as x`, `w exists`, `y is at least 1` and `z is 1` with `y` holding `"s"`, `z` holding `3` and `xs` holding `[]` say `w is missing; y is "s", which isn't a number; z is 3; xs is []`. After the sentences that read no alias, the roots of the line's own `whose` come first, then the roots of each other sentence in the order the sentences are written, and in each group the worst cause comes first and then the name. With the params `{"a": "s"}`, `for: every xs whose v is at least $params.min as x` with `x.w is at least $params.a` and `xs` holding `[{"v": 1, "w": 1}]` says `$params.min is missing; $params.a is "s", which isn't a number` and fails as `unusable`, the line's root first though `$params.a` has the worse cause. A list on a later line that doesn't depend on the item is a root too, so `every xs as m, every $params.q as x` with no `q` says `$params.q is missing; item 2 of xs: m.v is "x", which isn't a number`. A root that a later line's `whose` reads is said once too, with no item of that line's list: `every ws as w, every ys whose n is at least art.z as x` with `art.z` missing says `art.z is missing`, and `art.z is "s", which isn't a number` when it holds `"s"`, with `some`, `first of` and `last of` as much as with `every`. An item of `ys` that can't be read on its own still comes after it, like `art.z is missing; item 1 of ys: n is missing`. When that root is the first line's alias, like `w.z`, it is named for each item of `ws`, `item 1 of ws: w.z is missing; item 2 of ws: w.z is missing`, with no item of `ys`. A `whose` that reads both is said the same way: `whose n is at least art.z and whose n is at most w.z` with `art.z` missing and no `z` in the second item of `ws` says `art.z is missing; item 2 of ws: w.z is missing`. A root in a relative clause doesn't hide what the item says on its own, whichever clause comes first: `every xs whose k is in pr.z and whose v is 1 as m` says `pr.z is "s", which isn't a list; item 2 of xs: v is "x", which isn't a number`. The cause is the worst of all of them, the roots' too, as [problems.all_said](#which-problems-a-message-says) says: `m.v is 2` and `m.v is at least z` with `z` holding `"s"` and `xs` holding `[{"v": null}]` say `z is "s", which isn't a number; item 1 of xs: m.v is null` and fail as `unusable`, not `null`. `failures` lists every item that failed under its sentence, also when the message names a root once. With the params `{"q": "s"}` and `z` holding `"s"`, `for: every xs as m` with `m.v is at least $params.q` fails as `unusable` with `$params.q is "s", which isn't a number`, with `[{"v": 1}, {"v": 2}]` or with `[]` and `, if any,`, and with `[]` and no `, if any,` it says `$params.q is "s", which isn't a number; xs is []`. A `$params` or `$input` read alone is a root too: with the params `null`, `$params is 3` fails as `absent` with `$params is missing; xs is []` on an empty list. When the params aren't an object, a check under a `for` line that reads `$params` says only `$params is 3, which isn't an object`, naming the params once, and a check that doesn't read `$params` gives its usual message and still fails as `unusable`, also when an item isn't an object, where the item alone would say `not_an_object`. Only `ambiguous` ranks above `unusable` here: with `first of xs whose k is p.k sorted by v as m` picking items that tie, a check that doesn't read `$params` says `item 1 of xs: item 1 and item 2 of xs tie on v; item 2 of xs: item 1 and item 2 of xs tie on v` and fails as `ambiguous`, and one that reads `$params` says `$params is 3, which isn't an object` first and then the tie, as `ambiguous`. A part or a parent's name that holds a list is walked on the right of the phrases [walk.right](#compare) names, as it is without a `for` line: `m.v is in pl.z` with `pl` holding `[{"z": 1}]` compares `m.v` with `[1]` and lists `pl[].z`, and with `pl` holding `[]` it fails as `value`. A `null` item under a `named by` key read from the item, like `m.k named by m.k is 1`, says `item 1 of xs: m is null` once.

## Requirements

A policy has two sections. `subjects` defines each kind of subject once, and `requirements` says what must be true of them. A subject definition has a way to find its subjects (`from`), which can end with filters after `whose`, and a path to each subject's id (`identified_by`). A requirement names one subject definition with `subject`, and has `require`, `min_subjects` and checks. It can also have a `description` and `meta`, which Ergo copies into the report and never reads, and so can the policy.

**[requirement.subject]** A requirement checks the subjects of the definition it names, with its own rows. Several requirements can name the same definition. A requirement that names none, or one that isn't in `subjects`, is written wrong, so its `$well_formed` row fails. The name of the definition is the `type` in each row's `subject`.

**[subjects.from]** A subject definition's `from` is a path into the input. When it ends `found` on a list, each item is a subject, in list order, unless the path has more than one name ([subjects.from.list](#requirements)). When it ends `found` on an object, that object is the only subject, and when it ends on text, a number or true or false, that value is the only subject ([subjects.from.value](#requirements)). With no steps, it reads the whole input, which may be a list, and steps that start with a position, like `$input[0]` or `first of $input`, read that list as `things[0]` reads a list in a field. A path that ends missing or `null`, or that can't be read, gives no subjects, and the requirement's `$min_subjects` row fails with the path's outcome, `absent`, `null` or `unusable`. That holds even with `min_subjects: 0`, because that's what a typo in `from` looks like. A `from` line with `named by each of` still makes a subject of each key when its path can't be read, as [subjects.sentence](#requirements) says, unless it's a child subject whose parent isn't an object ([subjects.chain.not_an_object](#requirements)). A `from` line with `every` whose `named by` reads a param or an input value that can't be used reads no subjects the same way, and its requirement stays in the report.

**[subjects.from.names]** The names of a `from` line are `$input`, the name of another subject it starts at, each field, and each key a `named by` reads. A dot in front of the first name isn't a name, so `.deployments` is one name, like `deployments`, and a position, like `[0]` or `first of`, isn't one either, because it picks one item. So `deployments` is one name, and `$input.deployments`, `build.tests`, `build named by $params.k` and `builds[0].tests` are two.

**[subjects.from.list]** A `from` line with more than one name and no `every` meets a list when a name along it, or the value it starts at when that is `$input` or another subject, holds a list and isn't followed by a position, or when it ends at a list. Then it gives no subjects, and `$min_subjects` fails as `unusable`, even with `min_subjects: 0`, with a message that names the list and the fix: `trails is a list: write every trails.r.prs to read each item`. When the list is the parent subject itself, it fails as `not_an_object`, as [subjects.chain.not_an_object](#requirements) says, with the same message, like `batch is a list: write every batch.owner to read each item`. The data decides whether a value is a list, so the line isn't written wrong. A list read through a position, like `builds[0].tests[0]`, isn't met.

**[subjects.from.value]** A `from` line that ends at text, a number or true or false gives that value as one subject, whatever the number of names, and a check reads it by the subject's name: with `{"version": "1.2.0"}`, `from: version` gives one subject, and `version is "1.2.0"` passes. A `from` line that reads the whole input, when the input is itself text, a number or true or false, still gives no subject and fails `$min_subjects` as `unusable`.

**[subjects.one_type]** Every subject a `from` line gives must be of the same type: an object, a list, text, a number or true or false, so `1` and `1.5` are both numbers. An item that is `null` is still a subject and has no type here. When the types differ, `$min_subjects` fails as `unusable`, even with `min_subjects: 0`, and its message names the first value of each type, like `item 1 of builds: version is text, item 2 of builds: version is an object`, and `item 1 of xs[0] is text, item 2 of xs[0] is an object` for `from: xs[0]`, with the path as written. Its `failures` has an `item` entry for each value it names ([subjects.failed_items](#requirements)). The subjects are still listed and checked. A child subject's subjects are counted per parent, so the types only have to match within each parent.

**[subjects.one_type.children]** A line whose subjects mix types still has its child subjects read one parent at a time, as [subjects.chain](#requirements) says: the failure shows on the `$min_subjects` row of the line that mixes them, and nowhere else. With `d` read from `ds`, `m` from `d.m`, and `{"ds": [{"m": {"up": false}}, "x"]}`, the requirements on `m` get a `$min_subjects` row for each `d`, one that passes under `{"d": {"m": {"up": false}}}` and one that fails as `not_an_object` under `{"d": "x"}` with `d is "x", which isn't an object`, and `m`'s own rows.

**[subjects.failed_items]** A failing `$min_subjects` row whose message names items has an `item` entry in `failures` for each item it names, in list order, as [subjects.every.broken](#requirements) says. That holds for [subjects.one_type](#requirements), which names the first value of each type, and for [subjects.every.same](#requirements), which names each item where the name is a list and where it isn't. Each entry has `unusable` as its cause, the clause the message says about that item as its `message`, and the value it read as its input, with the outcome `usable`, because the value itself reads fine: `every builds.tags` on `{"builds": [{"tags": ["a", "b"]}, {"tags": "c"}]}` gives `item 1 of builds` with the message `tags is a list` and the input `builds[0].tags` holding `["a", "b"]`, and `item 2 of builds` with `tags is text` and `builds[1].tags` holding `"c"`. A value that is itself an item of the list keeps its name in its `message`, like `item 1 of xs is an object` with the input `xs[0]`. An item inside an item's list, like `item 1 of commits` in `item 1 of $input: item 1 of commits is an object`, is an entry under that item's entry. An item that both rules name has one entry, and a clause both rules give is said once, the first time ([message.join](#messages)): `every $input.commits` on `[{"commits": [{"x": 1}]}, {"commits": 5}]` says `item 1 of $input: commits is a list, item 2 of $input: commits is a number; item 1 of $input: item 1 of commits is an object`, and `item 2 of $input` has one entry. Every failed `$min_subjects` row has `failures`, `[]` when it has no entries, whatever its `from` line, and a row that fails only for too few subjects too. A line without `every` walks nothing, so a path it can't read is no entry: the read is one of the row's `inputs` after the count, named as written, with its `outcome` and the `locations` where it stopped, like `artifacts named by $params.name` with `absent` on `{"artifacts": {"api": {}}}` and the params `{"name": "web"}`, and so is a key it reads with `named by` that can't be read.

**[subjects.no_from]** A subject definition without `from`, or with nothing at all, `null` in YAML, reads the input field named like the subject, as `from: <name>` would. So `artifact:` alone reads `artifact`. `from: $input` reads the whole input.

**[subjects.sentence]** `from` is a string, read as a `from` line (see [sentence.subject.from](syntax.md#subjects)), and `identified_by` a string, read as a path. A `from` or an `identified_by` written any other way, like a list, is written wrong (see [policy.old_fields](syntax.md#policies)). A `from` line's path reads into the input, `named by` reads a key the way a ref step does, and `named by each of` makes each key in the list a subject. Each key is a subject even when the object doesn't have it, with the object as its location, so a missing attestation fails its own checks instead of being skipped. When the path before it doesn't end `found` on an object, each key is still a subject, unless it's a child subject whose parent isn't an object, as [subjects.chain.not_an_object](#requirements) says, and `$min_subjects` fails with the path's outcome, or with `unusable` when it read something that isn't an object, a list included, so the requirement is never met, even when every check passes. The list must be a list of strings, or there are no subjects and `$min_subjects` fails as `unusable`, as a ref that reads the wrong kind of value does ([value.ref](#values)), and as `absent` or `null` when the ref reads nothing. The path is read before the list, left to right, so a ref in the path that is missing, `null` or not a string decides that cause, `absent`, `null` or `unusable`, whatever the list holds: `scans named by $params.env named by each of $params.k` with `env` set to `1` fails as `unusable` even when `k` is missing. Only when every ref in the path reads a string does the list decide. Its `whose` conditions are the subject's filters, in the order written, so the `$applies` row joins them with ` and ` in that order, each printed in the report's spelling. A path that starts at `$input` reads into the input as one without it does, and `$input` alone reads the whole input. A path can't start at `$params`. One whose path is another subject's name and nothing more narrows that subject: its subjects are that subject's, kept when they pass that subject's filters and its own, and the `$applies` row prints the conditions of from lines along the chain outermost first. A position after the name, like `p[1]`, `first of p` or `item 2 of p`, is more than the name, so the line isn't narrowing: it is a child subject that reads that position inside each parent, as [subjects.chain.not_an_object](#requirements) says, and the position is never dropped. A loop in that chain is named after `from`. A `from` line that starts at a subject whose name is blank, like `" "`, is written wrong, with `" " isn't a subject name`, because no requirement can name that subject either. One that goes on into another subject is a chain, see [subjects.chain](#requirements).

**[subjects.narrow.id]** A subject that narrows another has the id of the one it narrows, so it can't have its own `identified_by`. One that does is written wrong, and `$well_formed` lists `not allowed on a subject that narrows another` under `subjects.<name>.identified_by`.

**[subjects.chain]** A `from` line whose path starts at another subject's name and goes on, like `artifact.pull_requests`, or ends there and goes on with `named by each of`, like `artifact named by each of $params.keys`, makes a child subject: it reads the rest of its path from each subject of that one, the parent. The parent's own `from` and conditions pick its subjects first, and the child's subjects are read from each of them in turn, in the order the parent's are. Every row of the requirement but `$well_formed` carries the id of the parent it was read from under `in`, like `"in": {"artifact": "sha-1"}`, and `$well_formed` has no `in`, since it's about the requirement as written. A check written as a sentence reads the parent by its name, `artifact.name`, and a bare first key that's the parent's name is the parent, not a field, wherever it is in the sentence. A first key written with a dot, like `.artifact.pull_requests` or `.artifact named by each of $params.keys`, is the input field and never the parent ([sentence.path.start](syntax.md#paths)), so that `from` line isn't a child subject. `artifact.x named by each of …` reads the keys inside `x` of each parent. A parent that's written wrong makes the requirement written wrong too, and its problems are listed in `$well_formed`. A parent can itself be a child subject, see [subjects.chain.levels](#requirements). A subject that narrows a child subject, like `open job` with `from: job whose state is "open"` where `job` reads `every record.jobs`, narrows it as it would narrow a subject read from the input: its subjects are the child's that pass the child's conditions and its own, with the child's id and the same `in`, like `"in": {"record": "r1"}`, they are counted per parent as the child's are ([subjects.chain.count](#requirements)), and a check reads the child's parent by its name. It can be narrowed in turn. Every subject in a chain that comes back to a subject already in it, through child subjects or through children and subjects that narrow, is written wrong, with `leads to a loop` under its `from`, however deep the chain looks. A `from` or `identified_by` string that can't be read is written wrong, and `$well_formed` lists its problems under `subjects.<name>.from` or `subjects.<name>.identified_by`.

**[subjects.chain.count]** A child subject is counted per parent: each parent gets its own `$min_subjects` and `$unique_ids` rows, with its `in`, so a parent with fewer subjects than `min_subjects` fails on its own row, and ids only need to be unique within each parent, so `pr/7` under two artifacts is fine. With no parent subject at all, there's one `$min_subjects` row and one `$unique_ids` row, with no `in`, and `$min_subjects` fails with `value`, or passes with `min_subjects: 0`, as it does for any subject that finds none. When the parent's `from` can't be read, `$min_subjects` fails with that cause, on one row with no `in`.

**[subjects.chain.scope]** A parent its own conditions leave out gives no rows at all: its child subjects aren't subjects of the requirement, so nothing in them is read, not even their ids. A parent whose conditions can't be decided, like `environment is "prod"` on an artifact without `environment`, gets one `$min_subjects` row, with its `in`, that fails with the condition's cause, even with `min_subjects: 0`, and its child subjects aren't read or checked, so it has no `$unique_ids` row. A parent left out by its own conditions hides no doubt about identity ([unique_ids](#requirements)), because the ids of the subjects it holds are only compared within one parent.

**[subjects.chain.not_an_object]** A child subject whose parent isn't an object, `null` included, can't read its `from` path from it, so its `$min_subjects` row fails as `not_an_object`, with `in` up to the parent, as [subjects.chain.levels](#requirements) says, even with `min_subjects: 0`. Nothing below such a parent is read, so a `named by each of` in the child's `from` line makes no subject of its keys, unlike [subjects.sentence](#requirements). This holds for a child of a child and for a child of a subject that narrows another. A parent that is an object without the field still gives `absent`, and one whose field is `null` or isn't a list or an object still gives `null` or `unusable`, as [subjects.from](#requirements) says. A `from` path whose first step is a position reads the parent as a list, as [path.not_an_object](#reading-a-path) says, so it keeps the cause [subjects.from](#requirements) gives. That holds for a position after the parent's name, like `artifact[0].pulls`, `artifact[0] named by each of $params.keys` and `first of artifact named by each of $params.keys`, and for one further in, like `artifact.x[0] named by each of $params.keys`: the position is read, and never dropped. The keys of such a `named by each of` are still subjects, as [subjects.sentence](#requirements) says, and `$min_subjects` fails as `unusable`.

**[subjects.chain.levels]** A chain can be three subjects deep, like artifact, pull request and commit, with `from: '"pull request".commits'`. Each level picks its subjects within each subject of the level above, so a subject out of scope at any level leaves out everything below it. Every row but `$well_formed` carries the id of every ancestor under `in`, like `"in": {"artifact": "sha-1", "pull request": "pr/7"}`. `$min_subjects` and `$unique_ids` count per direct parent, so each pull request gets its own rows. An ancestor whose conditions can't be decided, or whose child subjects' `from` can't be read, gets one `$min_subjects` row that fails with that cause, with `in` up to that ancestor, and nothing below it is read. With no direct parent at all, across every ancestor, there's one `$min_subjects` row with no `in`, as [subjects.chain.count](#requirements) says. A check reads any ancestor, and its parts, by the ancestor's name, like `artifact.name`, `"pull request".title` or `artifact.pr_attestation.approvers`, and a part's alias can't be the name of any ancestor. A subject that narrows another is at the level of the subject it narrows, so narrowing doesn't count as a level: with `open job` narrowing `job`, read from `record`, `every "open job".tasks` is the third level, and its rows carry `"in": {"open job": "k1", "record": "r1"}`. Each level is written out in Rego, which can't recurse, so a fourth subject is written wrong, with `a chain of more than three subjects isn't supported yet`.

**[subjects.every]** A `from` line with `every` (see [sentence.subject.every](syntax.md#subjects)) reads one list at the value its path starts at and one at each name along it that isn't followed by a position, the last one included. Where a value there is a list, each of its items goes on along the path in its place, and where it isn't, the value goes on as it is. Every value it reaches at the end is a subject, in the order it reaches them: an object, text, a number, true or false, or a list that is an item of the last list read ([subjects.every.lists](#requirements)). A line that starts at the input reads the input. The subjects don't belong to the items it went through: their rows have no `in`, and a check can't read those items.

**[subjects.every.lists]** A list directly inside a list is an item like any other, and `every` doesn't read into it. So with `{"batches": [[{"owner": {"name": "ann"}}], [{"owner": {"name": "cy"}}]]}`, `every batches` gives two subjects, each a list, and `every batches.owner` fails `$min_subjects` as `not_an_object`, because a name can't be read in a list, with `item 1 of batches is [{"owner": {"name": "ann"}}], which isn't an object`. Where `every` needs an object to read a name and finds text, a number or true or false, it fails as `unusable` instead, with the message a check gives for the same path, which names the value where the read stopped: `every builds.version.x` on `{"builds": [{"version": "1.0"}]}` says `item 1 of builds: version is "1.0", which isn't an object`. A policy that wants the owners names each level as a subject: `batch` read from `batches`, and `every batch.owner`.

**[subjects.every.same]** A name that `every` reads as a list in one item must be a list in every item. When it is a list in some and text, a number, true or false or an object in others, `$min_subjects` fails as `unusable`, with a message that says the kind in each item it names, in list order, like `item 1 of builds: tags is a list, item 2 of builds: tags is text`, and the values are still subjects, listed and checked: with `{"builds": [{"tags": ["a", "b"]}, {"tags": "c"}]}`, `every builds.tags` gives `a`, `b` and `c`. Where the name is missing or `null`, it fails as [subjects.every.broken](#requirements) says.

**[subjects.every.child]** A `from` line with `every` can start at another subject's name: `every deployment.monitors` reads the monitors of each deployment, one parent at a time, as a child subject does ([subjects.chain](#requirements)). Each row carries the parent under `in`, and each parent gets its own `$min_subjects` and `$unique_ids` rows ([subjects.chain.count](#requirements)). A parent that is a list is read with `every` too: with `batch` read from `batches`, `every batch.owner` gives the owners of each batch, with the batch under `in`. A parent that isn't an object or a list, `null` included, fails as [subjects.chain.not_an_object](#requirements) says, and its `failures` is `[]`, because nothing below it is read.

**[subjects.every.subject_name]** A subject's name at the start of a `from` line stands for one subject at a time, never a list, so `every` never applies to the name itself. With `deployment` defined by `from: deployments`, `from: every deployment` and `from: every deployment whose env is "prod"` are written wrong, with `deployment is a subject: write deployment whose … to narrow it, without every`, and `from: deployment whose env is "prod"` narrows it ([subjects.sentence](#requirements)). A subject's own name at the start of its own `from` line is the input field.

**[subjects.every_narrowed]** A subject that narrows a subject read with `every` (see [sentence.subject.narrow](syntax.md#subjects)), directly or through other narrowed subjects, takes that subject's flat list of subjects, as [subjects.every] makes it, and filters it with its own `whose`. So it has the same subjects and the same `total`, and its `$min_subjects` and `$unique_ids` expressions start with `every`, like the parent's.

**[subjects.every.count]** Subjects read with `every` are counted once, across every list, so there's one `$min_subjects` row and one `$unique_ids` row, and ids must be unique across all of them. A child subject read with `every` is counted once per parent instead ([subjects.every.child](#requirements)). An empty list adds no subject and fails nothing, so a path whose lists are all empty finds none, and `$min_subjects` fails with `value`, or passes with `min_subjects: 0`.

**[subjects.every.broken]** A place where the read breaks, a value that's missing or `null` where a name is read, a name read as a list that's missing or `null` in an item, a name read in an item that isn't an object ([subjects.every.lists](#requirements)), or a path where no list was read at all, fails `$min_subjects` with the worst cause found, even with `min_subjects: 0`, and the subjects that could be read are still checked. A path where no list is read fails at the first value along it that isn't an object, with `absent` when it's missing, `null` when it's `null`, and `unusable` otherwise, or at the value the path ends at, as `unusable`, when every value along it is an object: `every deps` on `{"deps": {"id": 1}}` fails with `deps is {"id": 1}, which isn't a list`. The `$min_subjects` row of a subject read with `every` has `failures`, as [row.parts](#what-a-row-shows) says: one entry for each place the read broke, the list first and then the items in list order. A list that failed while walking is a `list` entry named as the message names it, like `sbom.components`. A place inside an item is an `item` entry named like `item 2 of builds`, with the item as its `value`, where it sits as its `locations`, the clause the message says about it, without the item's name, as its `message`, and the read as its input, named by the path, like `builds[1].version`, with the `value` it read, or `null` when it's missing or can't be read, the `locations` where the read stopped and its `outcome`. An item that isn't an object keeps its name in its `message`, like `item 1 of xs is "a", which isn't an object`. A failed row's `failures` is `[]` when nothing broke, and it also holds the items [subjects.failed_items](#requirements) names. When the read breaks on the input itself, like an object or `null` for `every $input`, the place is named `$input`. A path from the input starts at `$input`, like `$input[1].commits`, or `item 2 of $input` when the item itself is the place it broke. For a child subject, a path starts at the parent's name. A list the line walks that can't be read, for any reason, is a `list` entry named as the message names it, holding the list's own read with its `outcome` and the `locations` where the read stopped, and the row's `inputs` hold the same read after the count. That holds for a position that isn't there too: `every $input[0].y` on `[]` says `item 1 of $input is missing`, and its `list` entry `item 1 of $input` holds the read named as written, `$input[0].y`, with the `outcome` `absent`. A key the line reads with `named by` that can't be read, like `$params.k` in `every x named by $params.k` with no `k`, is a root: it is one of the row's `inputs` after the count, with its `outcome`, and `failures` is `[]` unless the list fails too.

**[subjects.every.member]** A `from` line with `every member of` (see [sentence.subject.member](syntax.md#subjects)) reads its path as `every` does ([subjects.every](#requirements)), but reads no list at the value the path ends at. Each member of each object it ends at is one item, in key order, which is code point order, since the members of an object have no order of their own, and the item's location ends with the key, like `/records/0/evidence/sign-off`. From there an item is handled as an item of a list that `every` reads: its `whose` and its `$applies` row, `$min_subjects`, where `{}` is an empty list, `$unique_ids`, the causes along the path ([subjects.every.broken](#requirements)), and [subjects.one_type](#requirements) for members of different types. With `record` read from `records` and `{"records": [{"id": "r1", "evidence": {"build-7": {"kind": "scan", "status": "DONE"}, "sign-off": {"kind": "approval", "status": "COMPLETE"}}}]}`, `from: every member of record.evidence whose kind is "approval"` gives one subject, `sign-off`, under `"in": {"record": "r1"}`, and `build-7` is out of scope. A line that starts at another subject's name is a child subject, as [subjects.every.child](#requirements) says, and `every member of record` reads the members of each record: a record that isn't an object, a list included, fails as [subjects.chain.not_an_object](#requirements) says. `every member of $input` reads the members of the input. When no list is read along the path and the read stops before the value the path ends at, `$min_subjects` fails as it does for `every` on the same path, like `p is null` for `every member of p.q` on `{"p": null}`. The `$min_subjects` and `$unique_ids` expressions say `every member of`, like `count(matching(every member of record.evidence)) >= 1`, and so do those of a subject that narrows it.

**[subjects.every.member.not_an_object]** A value the path of `every member of` ends at that is there but isn't an object, a list, text, a number or true or false, fails `$min_subjects` as `unusable`, even with `min_subjects: 0`, and so does a value that is an object in one record and a list in another. Each such value is named in the message with the message a check gives where it needs an object, like `item 3 of records: evidence is [{"kind": "approval"}], which isn't an object`, or `$input is [1], which isn't an object` for `every member of $input` on a list input, and each has an entry in `failures`, sorted by path, as [subjects.every.broken](#requirements) says. The members of the values that are objects are still subjects and still checked. A value that is missing or `null` gives `absent` or `null`, as for any path.

**[subjects.every.member.id]** The id of a subject read with `every member of` is its key. When the subject has `identified_by`, the id is the value at that path inside the member instead, as for an item of a list ([subjects.id](#requirements)). So `every member of records.evidence` with `sign-off` in two records fails `$unique_ids` with `repeated evidence ids is ["sign-off"]`, and with `identified_by: attestation_id` the two have the ids `a-11` and `a-12`. A member whose `identified_by` is missing or `null` has no id and fails `$unique_ids` ([unique_ids](#requirements)).

**[subjects.keyed.list_before]** A `from` line whose path meets a list before `named by each of`, like `build.test_runs named by each of $params.kinds` with `test_runs` a list, or `builds.test_runs` with `builds` a list, fails `$min_subjects` as `unusable`, as [subjects.sentence](#requirements) says, and its keys are still subjects. The message names the list and points to a child subject: `build.test_runs is a list, but named by each of reads the keys of one object: make each item a subject and read the keys in it`. The list can be the value the line starts at, when that is `$input` or another subject: `$input named by each of $params.kinds` on a list input says `$input is a list, but …`. A parent subject that is a list fails as `not_an_object`, as [subjects.chain.not_an_object](#requirements) says, with the same message, like `artifact is a list, but …`. `every` can't go with `named by each of`, so the way to read the keys in each item is a child subject, like `test run` with `from: build.test_runs named by each of $params.kinds` and `build` read from `builds`.

**[subjects.distinct]** A `from` line with `every distinct` makes one subject of the values at the end of its walk that are the same, as [walk.distinct](#every-and-some) says, before its conditions are read: the first one, in the order the walk reaches them. Each location that a row of that subject, its `$applies` row or a row of one of its child and grandchild subjects reads through the subject, its parts or a child subject is listed once for each copy, in the walk's order: with copies at `/sbom/components/0` and `/sbom/components/2`, `version exists` lists `/sbom/components/0/version` and `/sbom/components/2/version`. A path that starts at `$input` lists only the location it names, so `version is $input.sbom.components[2].version` lists `/sbom/components/2/version` once for the `$input` path. `$min_subjects` lists the location of every copy, and `$unique_ids` the location of every copy's id, so subjects that share an id but differ in anything else are all kept and still fail it. Ergo never picks one of two pieces of evidence that disagree. The `$min_subjects` and `$unique_ids` expressions say `every distinct`, and so do those of a subject that narrows it ([subjects.every_narrowed](#requirements)).

**[subjects.keyed.list]** The list after `named by each of` is a list of keys read from `$params` or `$input`, like `$params.required_scans`. Its path is read as any path is and never walks a list, so a list on the way, like `$input.a` in `$input.a.k`, fails `$min_subjects` as `unusable`, and so does text, a number or true or false, with a message that names the value where the read stopped, like `$input.a is [{"k": "x"}], which isn't an object`, and no subject is read. The `$refs` of `$min_subjects` and `$unique_ids` list the path as written, like `$input.a.k`, with the value `null`. A path that starts anywhere else, like `artifact.keys`, `keys` or `.keys`, is written wrong, so a parent's field, or the parent itself, can't list the keys of its children. `$well_formed` lists `named by each of takes a list from $params or $input, so it can't start at a field or a subject` under `subjects.<name>.from`, and nothing is read from that path, so the subject has no other rows.

**[subjects.keyed.id]** A subject whose `from` line uses `named by each of` takes its key as its id, because the key is what names a subject the object doesn't have. So it can't have an `identified_by`. One that does is written wrong, and `$well_formed` lists `not allowed with named by each of: the key is the id` under `subjects.<name>.identified_by`, with any other problem with that `identified_by`, like `not a string`. A subject whose parent is a keyed one can have its own `identified_by`.

**[subjects.id]** A subject definition's `identified_by` is a path inside each subject, except for a subject listed by `named by each of` ([subjects.keyed.id](#requirements)), so one that starts at `$input` or `$params`, like `$input.x`, is written wrong, with `identified_by is a path, like "id" or "build.number"`. Its value is the subject's id, or `null` when the path doesn't end `found`. A subject that isn't an object is its own id, whatever the path, and so is every subject when there's no `identified_by`. So with `identified_by: id`, the items of `["a", null, {"id": 3}, {}]` have the ids `"a"`, `null`, `3` and `null`. A subject without an id still gets its rows, and fails `$unique_ids` ([unique_ids](#requirements)).

**[subjects.not_an_object]** An item that isn't an object is still a subject, and its checks fail as the [paths](#reading-a-path) they read say, usually `not_an_object`.

**[require]** `require` is `every` or `some`, and `every` by default. Under `every`, every subject in scope must pass every check. Under `some`, at least one subject in scope must pass every check by itself, so two subjects that each pass half the checks don't meet it.

**[require.some.parent]** Under `some`, a child subject ([subjects.chain](#requirements)) needs a passing subject under each parent: every parent that has a subject in scope must have at least one that passes every check by itself, and the requirement isn't met when one has none. The parent is the direct parent, the one whose id is the last in `in` ([subjects.chain.levels](#requirements)), so with release, artifact and signature, each artifact needs a passing signature. A parent with no subject in scope isn't decided here: it fails its own `$min_subjects` row, or passes it with `min_subjects: 0`, and then it is skipped. The rows under a parent that has a passing subject aren't violations and aren't counted in `causes`, and every failing row under a parent that has none is, with the parent under `in`. Ergo adds no row of its own for a parent. Subjects that have no `in`, the ones of a subject that isn't a child subject, a subject that narrows one of those, and a `from` line with `every` that reads from the input like `every commits.pull_requests`, are one group, as [require] says.

**[min_subjects]** `min_subjects` is a whole number from 0 to 1,000,000, and 1 by default. The `$min_subjects` row passes when `from` could be read and at least that many subjects are left after the subject's filters. Its input is the number left. Otherwise it fails with `value`, or with the cause in [subjects.from].

**[unique_ids]** Every subject has an id, and no two subjects share one. A missing id and `null` aren't ids: the report writes both as `"id": null`, so its rows couldn't say which subject they are about. So the `$unique_ids` row fails for each subject whose `identified_by` doesn't end `found` ([subjects.id](#requirements)), and for each subject that is `null` and so is its own id, with or without `identified_by`. A subject listed by `named by each of` has its key as its id, so it always has one, and any other value, `""`, `0`, `false`, `[]` and `{}` included, is an id. A filter never hides a doubt about identity, so the subjects the filters leave out count too: two records with one id that disagree could be the same thing, and Ergo doesn't pick one, and a record without an id could be another record of one in scope. Records that are snapshots of one thing are read through a parent subject ([subjects.chain.count](#requirements)), so their ids only need to be unique within it. The row's input lists each id more than one subject has, once, sorted by its JSON text as shown in [syntax.md](syntax.md#expressions), so `"b"` comes before `10`, and `10` before `3`, and a subject without an id is never one of them. The row fails with `value` when an id repeats, and with the cause of reading each missing id: `absent` when it's missing, `null` when it's `null` or the subject is, and the read's own cause otherwise, like `unusable` for `identified_by: meta.id` on `{"meta": 3}`. The row takes the worst of them ([Causes](#causes)). Its message says the repeated ids first, because they are worked out across all the subjects ([problems.where_said](#which-problems-a-message-says)), and then each subject without an id, in the order of the subjects, named by its place as [message.items](#messages) names an item, with what `<identified_by> exists` says on it: with `from: ds`, `identified_by: id` and `ds` holding `[{"id": "a"}, {}, {"id": null}, {"id": "a"}]`, it fails as `absent` with `repeated d ids is ["a"]; item 2 of ds: id is missing; item 3 of ds: id is null`. A subject that is `null` says `item 3 of ds is null`. Each one is an `item` entry in the row's `failures` ([row.parts](#what-a-row-shows)), with the read of its id as its input, like `ds[1].id` with `outcome` `absent`, and a subject read from a list in a list sits under the outer item. A subject read from inside an item, like one of `every xs.meta`, is named by that item, which is its entry: `item 1 of xs: meta.id is missing`, with the input `xs[0].meta.id`. A subject that isn't in a list, like one read from `artifact`, isn't an item, so it has no entry: the read of its id is added to the row's `inputs`, and the message names it from where the subject was read, like `artifact.fingerprint is missing`, or `$input.id is missing` for the whole input.

**[unique_ids.ancestors]** A requirement on a child subject ([subjects.chain](#requirements)) checks the ids of every ancestor too, the parent and the grandparent, on `$unique_ancestor_ids` rows whose `subject` is the ancestor, like `{"type": "commit", "id": null}`. They follow [unique_ids]: an ancestor whose id is missing or `null` fails the row and is named from where it was read, like `item 2 of commits: sha is missing`, the subjects the ancestor's filters leave out count too, and an ancestor without `identified_by` is its own id. Each level is counted the way `$unique_ids` is, once for each of its own parents, with them under `in`: with artifact, pull request and commit, a requirement on `commit` gets one row for `artifact`, with no `in`, then one for `pull request` under each artifact in scope, outermost first. The row's input is named like `repeated commit ids`, and the row fails when an id repeats or an ancestor has none, so the requirement isn't met, and every other row stays. An ancestor whose `from` can't be read gets a row with no ids, which passes, and like an ancestor whose conditions can't be decided, the levels below it get none. So two commits with the sha `a` fail a requirement on their pull requests, under `some` too, even though `$unique_ids` counts both commits' pull requests under one `"in": {"commit": "a"}`. A requirement on a subject that has no parent has no `$unique_ancestor_ids` row, and its `checks` has no entry for it. The entry's `description` and `expression` join each level's with ` and `, outermost first, like `Every artifact has a unique id and every pull request has a unique id` and `count(missing(ids(artifacts))) + count(repeated(ids(artifacts))) == 0 and count(missing(ids(every artifact.pull_requests))) + count(repeated(ids(every artifact.pull_requests))) == 0`.

**[well_formed]** The `$well_formed` row passes when the requirement can be read into the model, names a subject definition that can be read too, and has at least one check. Otherwise it fails with `value`, and the requirement is never met. Its inputs start with `count(checks)` and `require`, and `require` stays second when it is what's wrong, listing its problem. A requirement that's written wrong gets only that row: Ergo doesn't read its subjects, so it has no `$min_subjects`, `$unique_ids`, `$unique_ancestor_ids`, `$applies` or check rows, and its `subjects` counts are 0. The policy alone decides whether it's written wrong, so it fails on every input, and any other row would be checked against a policy Ergo couldn't read as written. Its entry in `requirements` still lists every check, the ones Ergo adds included, so the report shows what the policy wrote. Other requirements of the policy still get their rows.

**[names.dollar]** A name written in a policy that starts with `$` is written wrong, with `a name can't start with $`, so a name can't be mistaken for one of Ergo's own, like `$well_formed`, `$refs` or `$policy`. Only `$input` and `$params` can also be read, and a sentence path that starts with `$policy` is written wrong. That holds for the name of a subject, a requirement, a check, an `any_of` option and a part, and `$input` and `$params` aren't names, so they keep working at the start of a path. The problem is listed under `subjects.<name>`, `checks.<name>`, `subjects.<subject>.has.<alias>`, or `requirement name` for a requirement, and `option <name>: a name can't start with $` for an option, in the `$well_formed` row of each requirement it touches. A `$` after the first character, like `a$b`, is fine. A check with such a name has no entry of its own in `requirements`, so no name ever stands for two checks. A `for` alias can't be written with a `$`, because the line doesn't parse.

**[names.edge]** A name of the kinds [names.dollar](#requirements) lists is also written wrong when its first or last character is a space or an invisible character: one that Unicode gives the property White_Space, which is U+0009 to U+000D, U+0020, U+0085, U+00A0, U+1680, U+2000 to U+200A, U+2028, U+2029, U+202F, U+205F and U+3000, or the general category Cf, which is U+00AD, U+0600 to U+0605, U+061C, U+06DD, U+070F, U+0890 and U+0891, U+08E2, U+180E, U+200B to U+200F, U+202A to U+202E, U+2060 to U+2064, U+2066 to U+206F, U+FEFF, U+FFF9 to U+FFFB, U+110BD, U+110CD, U+13430 to U+1343F, U+1BCA0 to U+1BCA3, U+1D173 to U+1D17A, U+E0001 and U+E0020 to U+E007F. So `" $well_formed"`, `"approved "` and U+200B followed by `$x` are refused, and a name that is only spaces is too. The problem is `a name can't start or end with a space or an invisible character`, listed where [names.dollar] lists its own, and for an `any_of` option as `option <name>: a name can't start or end with a space or an invisible character`. A name with both problems lists both, sorted by their text, so the one about spaces comes first. For a part it comes in place of `invalid alias`, as the problem about `$` does. Spaces inside a name, like `x y`, are fine, and so is a full-width `＄x`, which doesn't start with `$`. A `for` alias can't start or end with a space either, because the line doesn't parse.

**[names.empty]** An empty name, `""`, is written wrong, with `a name can't be empty`, for the name of a requirement, a check, an `any_of` option and a part, listed where [names.dollar](#requirements) lists its own, and for an `any_of` option as `option : a name can't be empty`. For a part it comes in place of `invalid alias`. A subject named `""` can't be named by a requirement, because a requirement whose `subject` is `""` is written wrong with `empty or not a string` under `subject`, so such a subject is never read and adds no problem of its own, as a subject starting with `$` that no requirement names adds none. A `for` alias can't be empty, because the line doesn't parse.

## Parts

A subject can have parts: named paths inside itself, each with an alias, written as [syntax.md](syntax.md#parts) says. A part is a short name for a long path, so a policy that reads the same attestation in six checks writes where it is once.

**[parts.swap]** A part's alias stands for its path inside the subject. A check that starts a path with the alias gives exactly the rows that the same check gives with the path written out in its place: the same `passed`, the same `cause` and the same values. A part that is missing, `null` or the wrong type fails the check as the full path would, with `absent`, `null`, `unusable`, or `not_an_object` when the subject isn't an object, and a `named by` in the path that can't be read fails it as it would there. Only the names differ. A row's `expression`, its `inputs` and the names of its `failures` keep the alias, see [name.part](syntax.md#naming-a-path).

**[parts.tag]** An entry in a row's `inputs` that was read through a part has `part`, `{"name": ..., "id": ...}`, besides its `name` and `value`. `name` is the alias as the check writes it, so it is also a key of the subject's `parts` in the report. For a part of a child subject's parent it is the parent's name and the alias, like `artifact.pr_attestation`, with the parent's name written as a check writes it, so a parent named like a word of the grammar is quoted, like `"empty".pa`. `id` is the value at the part's `identified_by`, read inside the part for the row's subject (the parent's, for a parent's part), as it is: any JSON value. It is `null` when the part has no `identified_by`, or when it leads nowhere or to `null`. An entry that reads through two parts in one value, like the sum of a `count of` one and a field of another, has no `part`, and neither has an entry that doesn't go through a part, so a policy without parts gives the same inputs as before. The tag is for readers and tools: it never changes `passed`, `cause` or a value. It is on `inputs`, so on the inputs of a violation, and on the `inputs` of an entry in `failures`, see [for.failure_inputs](#for). A walk that goes through a list inside the part names the entry with the full path, and the entry keeps its tag. A `count of` or `sum of` entry has the tag only when the list it counts or sums starts at the part, because that is where its value comes from: `count of pa.items whose w is pa.w` has it, and `count of items whose w is pa.w` doesn't, since its `whose` only picks which of the subject's own items to count. The entry for `pa.w`, which the `whose` reads, has the tag in both.

**[parts.where]** An alias is read wherever a bare first key reads the subject (see [sentence.path.start](syntax.md#paths)): in the subject's checks, in the assertions of a `for` line and in a later item of it whose path starts at the subject, in the conditions of the subject's own `from` line unless the key is written with a dot, like `.cov`, and in the conditions of a subject that narrows it. Inside a relative clause, where a bare first key reads the focus instead, an alias is read on the right side, as a `for` alias is (see [sentence.for.scope](syntax.md#the-for-line)), and never right after `whose`: `whose cov is at least 5` reads the item's `cov`. On the right side of a one-line `every` or `some`, which resolves from the root, it reads the part too: `every lst.x is at least cov.x` reads the part's `cov.x`, and `.cov` there is the subject's field. So does every term of a `plus` on the right side, and each path of an elapsed time there: `whose lo is at least cov.x plus hi` reads the part's `cov.x` and the item's `hi`, and `whose lo is at least days elapsed from cov.t to hi` reads the part's `cov.t`. A parent's name in a term of a `plus` or the path of an elapsed time there reads the parent in the same way. The focus's own field on the right of a `whose` is written `.cov`. A `count of` or `sum of` counts as a side here: `every lst.x whose n is count of cov.z is 1` counts the part's `cov.z`, and `whose count of cov.z is 1` counts the item's own `cov.z`. After `that` it's the same whatever the items are: `count of xs that is count of cov.z is 1` counts the part's `cov.z` even when each x is a number, and so does the subject's own name, as in `count of xs that is count of pr.coverage.z is 1`. A parent's name is read the same way in a `count of` or a `sum of` on the right side of a `whose`, in every, some, count of and sum of, and for a `for` item: with a parent `fam`, `count of items whose n is count of fam.z is 1` counts the parent's `z`, `count of items whose count of fam.z is 1 is 3` counts each item's own `fam.z`, and `.fam.z` on the right counts the item's. A parent whose field is missing, `null` or not a list fails the check as `absent`, `null` or `unusable`, as [path.not_an_object](#reading-a-path) and [tally.walk](#counts-and-sums-in-sentences) say.

**[parts.shadow]** An alias shadows a field of the subject with the same name, so `cov.x` reads the part and not the field `cov`. The dot in front of a first key, like `.cov`, reads the field: `.cov.x` reads the subject's field `cov`, as it reads a field named like a word of the grammar (see [sentence.path.start](syntax.md#paths)).

**[parts.narrow]** A subject that narrows another keeps its parts, and can add its own. Its checks and its conditions read them like parts of its own, and the report lists them (see [report.subjects](#statuses)).

**[parts.chain]** The alias of a child subject's parent gives everything the parent has, its fields and its parts, so `artifact.pr_attestation.approvers` reads the part `pr_attestation` of `artifact`, and a `from` line can start from one: `from: artifact.pr_attestation.pull_requests`. A part is only reached through its subject. A bare `pr_attestation` in a check of the child subject is its own field, and a part of the child subject isn't one of the parent's.

## Scope

**[scope.filters]** A subject is in scope when it passes every filter in its definition's `from` line. Each subject gets one `$applies` row when the definition has filters, and a subject that's out of scope gets no other rows, but its `$applies` row stays.

**[scope.out]** A subject is out of scope only when every filter it fails fails with `value`, or one of them is a `present` filter that found its field missing ([present.filter]). Then its `$applies` row fails with `value`.

**[scope.unreadable]** When a filter fails with any other cause, Ergo can't tell whether the subject is in scope. Its `$applies` row fails with the first such cause, in the order of [causes](#causes), even when another filter would rule it out, and the requirement isn't met, even with `min_subjects: 0`.

**[scope.failures]** An `$applies` row has the `failures` the check row would have if its conditions were the assertions of a check: an `assertion` entry for each condition that failed, in the order written, with its own `cause`, `inputs`, `message` and `locations` like `$policy:/subjects/t/from#2`, and under a `some` or an `every` condition the items it walks, as [walk.failed_items](#every-and-some) says, and under a `count of` or a `sum of` the items it can't read, as [row.parts](#what-a-row-shows) says, whether the condition is alone or not. A row that passes has none. A single condition that isn't a `some` or an `every`, like `environment is "prod"`, has one assertion entry, as a plain check does. The row's own `cause` is the one [scope.out](#scope) and [scope.unreadable](#scope) give, so the `cause` of an entry can be `absent` or `null` where the row's is `value`, as when a `present` filter rules the subject out.

## Statuses

**[status]** Each requirement has a `status`:

- `not_met` when its `$well_formed`, `$min_subjects`, `$unique_ids` or `$unique_ancestor_ids` row fails, when an `$applies` row fails with anything but `value`, or when its checks fail under `require`
- `not_applicable` when it would otherwise be met but no subject is in scope, which only happens with `min_subjects: 0`
- `met` otherwise

**[compliant]** The report is `compliant` when it has at least one requirement and none is `not_met`. A policy with no requirements is never compliant, because it doesn't check anything, and its report has Ergo's own requirement `$policy`, which is never met ([policy.no_requirements](syntax.md#policy)).

**[report.requirements]** The report has an entry for each requirement, with its `description` and `meta`, or `""` and `{}` when it has none, its `require`, `subject`, the name of the subject it checks, or `null` when it names none or one that isn't in the policy's subjects, its `status`, `subjects` with `total`, the number found by `from`, and `matching`, the number in scope, `checks`, each check as written with its `description`, `meta` and `expression`, plus the checks Ergo adds, and `causes`. All the filters share one `$applies` entry.

**[report.policy]** The report has the policy's `description` and `meta` at its top, next to `compliant`, or `""` and `{}` when the policy has none. `null` counts as none. A `description` that isn't a string, or a `meta` that isn't an object or holds something JSON can't, a number out of range or one with more than 15 significant digits ([sentence.value.scalar](syntax.md#values)), makes the `$well_formed` row of every requirement fail, because the policy belongs to all of them, and the report shows `""` or `{}` in its place. A `meta` of a requirement or of a check that holds such a number makes the `$well_formed` row of its requirement fail, with `number out of range` or `number with more than 15 significant digits`.

**[report.keys]** Every object in the report, `meta` and values copied from the input included, has its keys sorted by code point, whatever order the policy or the input wrote them in.

**[report.version]** The report has `ergo` at its top, the version of the spec it follows, like `"ergo": "v0.7-dev"`. That's the version the implementation follows, even when the policy names another or none.

**[report.engine]** The report has `engine` at its top, saying which implementation made it: its `name` and `version`, both strings, like `{"name": "ergo-rego", "version": "0.1.0"}`, and nothing else. A name is `ergo-` and the engine, like `ergo-rego` or `ergo-rust`, so the name and version match the engine's release tag, like `rego-v0.3.0` or `rust-v0.1.0`. Apart from `engine`, a report depends only on the policy, the input and the params, so it says nothing about the machine that made it, like the version of OPA, and an implementation reads nothing from that machine: no clock, randomness, network or environment variables.

**[report.hash]** The hash of a report is the SHA-256, in lowercase hex, of the report without `engine`, written as [RFC 8785](https://www.rfc-editor.org/rfc/rfc8785) says. So the same policy, input, params and spec version give the same hash whichever engine made the report, apart from numbers that a 64-bit float doesn't keep (see [OPEN.md](OPEN.md#numbers-in-a-reports-hash)). An implementation doesn't have to compute it.

**[report.subjects]** The report has `subjects` at its top, with an entry for each subject a requirement uses, by name. That's the subject it names, the subjects that one narrows or reads from, and so on all the way back. A subject no requirement uses isn't listed. An entry has:

- `description`, the subject's description, or `""` when it has none or it isn't a string
- `from`, how the subject is found, written as a `from` line: the line itself, printed the same way whatever spaces it was written with. A subject without `from` reads the input field named like it. A `from` that is written wrong, or isn't a string, is `<invalid from>`, even when the line reads and has only a problem like `values of mixed types`. So is the `from` of a subject with `applies_to` or `of`, because those fields said how it was found.
- `identified_by`, the path of the subject's id, or `null` when it has none, because the whole subject is its id. A subject that narrows another has the id of the subject at the top of its chain, the one that narrows nothing, also when its `from` is written wrong, even with an `identified_by` of its own. An id that is written wrong is `<invalid identified_by>`. In a loop of subjects that narrow each other no subject is at the top, so a subject in it has `null`, or `<invalid identified_by>` when it has an `identified_by` of its own, which is written wrong on a subject that narrows another.
- `parts`, every part the subject has, including the ones it keeps from a subject it narrows, by alias. Each is `{"from": ..., "identified_by": ...}`: `from` is the part's path written the way a sentence writes it, so `  dd.b ` is `dd.b` and `x[$params.k]` is `x named by $params.k`, and `identified_by` is the path of the part's id, or `null` when it has none. A part written as one line has no id. A part written wrong is listed as best it can be: `<invalid from>` for a path that can't be read and `<invalid identified_by>` for an id that can't, and a part that is neither a string nor an object has `<invalid from>` and `null`.

A subject that is written wrong still has its entry. A subject whose `from` starts at another subject lists that subject even when the line is written wrong. A `from` that doesn't parse, or isn't a string, lists no other subject.

**[report.causes]** `causes` lists the causes of the rows that would be [violations](#violations) of the requirement, each with `rows`, the number of rows that have it. It counts rows, not subjects, and lists the causes in the order of [causes](#causes), worst first. A requirement that's `met` or `not_applicable` has an empty list.

## Row order

**[order]** Rows come in this order, whatever order the policy was written in:

1. all the `$well_formed` rows, then all the `$min_subjects` rows, then all the `$unique_ids` rows, then all the `$unique_ancestor_ids` rows, then all the `$applies` rows, then the requirements' own checks
2. within each of those, requirements in name order
3. within a requirement, subjects in the order the subject's `from` found them, and `$unique_ancestor_ids` rows outermost ancestor first
4. within a subject, checks in name order

Names are sorted by code point.

## Violations

**[violations]** The violations of a report are its rows that are real problems, in the order of `results`, each with its check's `description` and `expression` added and its `$refs` added at the end of its `inputs`, each entry once: one the row lists already isn't added again. Each keeps its row's `message` ([messages](#messages)). A violation keeps its row's `failures`, a `$min_subjects` row's included, and so does an `$applies` row that has them ([scope.failures](#scope)). The violations leave out rows that passed, `$applies` rows that failed with `value`, and every row of a requirement that's `met` or `not_applicable`, so under `require: some` the subjects that failed aren't violations when another one passed, or, for a child subject, when another one passed under the same parent ([require.some.parent](#requirements)). They're worked out from the report alone.

## Examples

Experimental. These rules say what the outcome of an example means, written as [syntax.md](syntax.md#examples) says, and what a runner does with it. A runner builds the report for the example's input, its params and the policy, and checks the outcome against it.

**[outcome.match]** Each line must agree with the report. `compliant` and `not compliant` agree with `compliant`. A requirement line, or a heading with a status, agrees when the requirement has that `status`: `is met` is `met`, `is not met` is `not_met` and `is not applicable` is `not_applicable`. A check line agrees with the row of the heading's requirement for that check and that subject, by its type and id, and for a child subject by the id of each subject its `in` names too, when the row passed for `passes` and failed for `fails`. So `artifact web in deployment d1` and `artifact web in deployment d2` are two rows. An id that is a number matches an id that is a number of the same value, however either is written, so `7`, `7.0` and `7e0` all match the id `7.0`, and `"7"`, a string, matches none of them. Any other id matches an equal JSON value, and the ids after `in` match the same way. When several rows share that check, subject type and id, and the same ids after `in`, every one of them must agree with the line. With `because`, the message after it must equal the row's whole `message`, so `because missing` doesn't agree with `approver is missing`. A check line with no such row doesn't agree. A line with no id ([outcome.lines](syntax.md#examples)) matches a row whose `id` is `null`, of the line's subject or, with no subject written, of the requirement's own subject, and with the same ids after `in`, or no `in` when the line has none. A scope line matches the `$applies` row of its subject: `is in scope` agrees when the row passed, and `is out of scope` when it failed with `value` ([scope.out](#scope)), so it never agrees with a row that failed with another cause ([scope.unreadable](#scope)). An example passes when every line agrees and no failure is left out under [outcome.coverage](#examples).

**[outcome.coverage]** Each line covers a part of the report, and every row that failed inside what the lines cover must be named by a `fails` line. `compliant` and `not compliant` cover the whole report. A requirement line, and a heading with a status, cover the whole requirement. A check line covers its check in its requirement, and a heading without a status covers only the checks its lines name. Outside what the lines cover, nothing is checked. With `deployments` holding `[{"id": "d1"}, {"id": "d2", "approver": ""}]` and `approver_set: approver is a non-empty string`, the outcome `[{"approved": ["deployment d1 fails approver_set because approver is missing"]}]` fails, because `d2` fails `approver_set` too and no line names it. A scope line covers `$applies` in its requirement. An `$applies` row that failed with `value`, for a subject out of scope, isn't a failure, so it needs no line, even under a heading with a status, and it is checked only where a line names it. A row that failed and that the form can't name yet, like an `$applies` row that failed with `absent`, fails the example when the lines cover it. A failed `$well_formed` row fails every example, whatever its lines say.

**[outcome.warnings]** After running every example, a runner warns about each check of the policy that no check line shows failing, and each one no check line shows passing, like `warning: no example shows approver_set of approved passing`. It counts check lines, not requirement lines, and only those of the examples that passed, so a failed example never hides a warning. It counts per check, not per cause. A runner can offer to fail on a warning, like `ergo test --strict`.

**[outcome.print]** The outcome of a report is `compliant` or `not compliant`, then each requirement in name order as a heading with its status and a line for each row of its own checks, in the order of `results`. A requirement with no such row is a requirement line on its own. A row of a check Ergo adds that passed has no line, and one that failed has the line [outcome.lines](syntax.md#examples) gives it. An `$applies` row has a line only when it failed with `value`, `<subject> <id> is out of scope because <message>`, and one that failed with another cause can't be written. A report with a failed `$well_formed` row has no outcome, and neither has a report with two rows of one check and one subject, by type, id and the ids after `in`, whose lines differ, because no line agrees with both: with two deployments `d1`, one that passes `approver_set` and one that fails it. An id is written as [outcome.ids](syntax.md#examples) says, a number as the report writes it, like `7` for an input id `7.0`. A child subject's line names each subject of its row's `in` after its id, parent first, as [outcome.lines](syntax.md#examples) says, and a row whose `in` doesn't name the subjects its `from` line is read inside can't be written, apart from a row of a check Ergo adds with no `in` at all, which a child subject with no parent has ([subjects.chain.count](#requirements)) and whose line names no parent. A line must read back as its row, so when a longer subject name or check name of the policy starts the same way, the line quotes every string id, its own and those after `in`, or leaves out `because` and the message, or both, taking the first of those that reads back as the row: with subjects `pull` and `pull request`, the `pull` whose id is `request` is `pull "request"`, and with checks `c` and `c because d`, a row of `c` that failed with the message `d` is `t 1 fails c`. A row that no such line reads back as, like a row whose number id would read as part of a longer subject name, can't be written, so the report has no outcome. A heading that could name two requirements ([outcome.lines](syntax.md#examples)) can't be written either, so with requirements `x` and `x is met`, a report where `x` is met and has lines has no outcome. An implementation that prints it as YAML quotes a line or a heading only when YAML would read it as something else, like a line that holds `: `, and writes a character YAML can't hold as it is, like U+007F, a C1 control character, U+2028 or U+2029, as an escape inside double quotes, like `\u007F`. A report with a row the form can't name yet ([outcome.lines](syntax.md#examples)) has no outcome.
