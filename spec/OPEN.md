# Open questions

Things the spec doesn't settle yet, because they need a decision first. Open questions about the spec live here, not in issues.

## Custom operators

0.1 has no custom operators, because a sentence can't call one and no policy downstream defined one (see [#1](https://github.com/kosli-dev/ergo/issues/1)). They come back once the definition below is built.

Decided on 2026-10-16: the spec will take the definition the Rust engine uses, on the `core/conformance-suite` branch: a plain JSON object that users and auditors can read, with the name, each parameter's kind (`path`, `paths`, `value`, `number`, `string`) and type, an expression template and a version. The body stays up to each implementation: a Rego rule in `ergo.rego`, CEL or anything else in a port. Ergo then checks for missing, `null` and wrong-typed values in one place instead of trusting every operator to, checks don't repeat `expression` and `inputs`, and a report says which definitions produced it, with a SHA-256 of each. The parameters' names and kinds are also what a sentence needs to call an operator, because they say whether a word after it is a path or a value. Two implementations can still give the same definition different bodies, and the report can't show that.

It's put off until a control needs logic that no phrase covers. On 2026-10-16, pr-reviewer was the only known policy with custom operators, and all seven of them can be written as sentences that Ergo runs. The last one, `contains_all`, is `contains all of` with a field of the subject, and so is DEV-0406's `does not contain`, both since #224. The deadlines DEV-0401, 0402, 0705 and 0802 work out in Rego can be sentences too since #232 and #234, with `days elapsed from X to Y` and a limit looked up by a field of the subject. Allowing one inside `every` and `some` is a separate question for Rego, which can't recurse.

### Where sentences fall short

When a policy needs something no sentence can say, the first question is whether it should be a phrase. On 2026-10-21 every MUST line of Kosli's 23 SDLC controls (sdlc.kosli.com) was written against the evidence Kosli records: the CLI's attestation types, the test data in kosli-dev/sdlc-policies and the server's models. Each sentence was run on a passing and a failing input. Of 105 lines, 37 can be written today, 15 in part, 6 are human judgement or a promise about the future, and 46 need evidence Kosli doesn't record. Only a few lines are short of words:

| Gap                      | Example                                                                | Needed by      | Where it belongs                                                                                                                   |
| ------------------------ | ---------------------------------------------------------------------- | -------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| Pick by order            | the author of the last commit                                          | SDLC-CTRL-0007 | a `for` item, [sentence.for.pick](syntax.md#the-for-line), runs                                                                    |
| A sentence in `any_of`   | the declared licence, else the one the params give for the name        | SDLC-CTRL-0004 | an `any_of` of sentences, [sentence.any_of](syntax.md#the-shape-of-a-sentence), runs                                               |
| Parsing and decoding     | lockfile and Dockerfile lines, SPDX expressions, base64, signed tokens | SDLC-CTRL-0004 | before Ergo, when the evidence is attested, so the report still shows the facts                                                    |
| Calendar time            | renewed every 12 months                                                | none           | `months` and `years elapsed`, once a control needs them. Fixed units run (#234)                                                    |
| Arithmetic beyond `plus` | coverage as `covered / total`, an average                              | none           | more derived values next to `count of`, `sum of` and `plus`                                                                        |
| Orderings of one domain  | version order, a network range, a glob                                 | none           | a custom operator, because each has its own rules                                                                                  |
| Recursion                | dependencies of dependencies                                           | none           | before Ergo. Rego can't recurse, so a custom operator can't either                                                                 |
| Rules across subjects    | at most 5% of deployments failed                                       | none           | something on the requirement, since a check sees one subject at a time                                                             |

"Needed by" lists the SDLC controls that hit the gap. The rows marked "none" were guesses before that check, and no SDLC line needed them.

A gap that many controls share becomes a phrase or a derived value, which stays readable, runs the same everywhere and fails closed in one place. A gap that belongs to one domain becomes a custom operator, with a definition that says what it means. Parsing and decoding stay out of Ergo, because an operator that decodes hides the evidence from the report as much as Rego that runs before Ergo does.

The same check found two ways a check passes when it shouldn't. A sentence that compares a path with itself always passes, which happens when a `whose` or a one-line `every` reads a bare key that the writer meant as the subject's ([#273](https://github.com/kosli-dev/ergo/issues/273)). And numbers held as strings, as Sonar records them, are ordered as text, so `"9"` is at least `"80"` ([#274](https://github.com/kosli-dev/ergo/issues/274)).

## Parts

A subject's parts (`has`, see [syntax.md](syntax.md#parts)) leave a few things open:

- `named by` a bare word that is a part's alias is written wrong. It would have to read the part's value and use it as a key, as it does for a `for` alias, and nothing says yet whether a part that is a path with its own `named by` can be used that way.

## Time limits

`time.format` only takes years 1678 to 2261 and only counts the first nine digits of a fraction. Both limits come from OPA, which holds a time as nanoseconds since 1970 in a 64-bit integer. A port in another language would have to add them on purpose. Either they stay, and the spec keeps them as a rule every implementation follows, or the spec drops them and `ergo.rego` has to compare times some other way outside that range.

## Which steps a walk walks

`every` and `some` walk "into every list along the path" ([walk.lists](semantics.md#every-and-some)), and Ergo decides that from the data: a step is walked when at least one value there is a list, and then every value there must be one. So `every prs.commits.signed is true` on `{"prs": [{"commits": {"signed": true}}]}` passes, because `commits` is an object and nothing is walked at that step, but the same pull request fails as `unusable` when another one has a list of commits. It fails closed whenever the data shows a list, and only passes data shaped wrong when every item is shaped wrong the same way and the wrong shape still holds a field that passes.

Three ways to settle it:

- Keep it as it is, and say so in the spec.
- Have the author mark the lists, like `every prs[].commits[].signed`. That changes the grammar of [#174](https://github.com/kosli-dev/ergo/issues/174), and costs some of its plain reading.
- Give Ergo the shape of the input, as a schema, so a step is walked because the schema says it holds a list. [#191](https://github.com/kosli-dev/ergo/pull/191) already declares a schema for part of `input`.

## Sentences the spec doesn't say enough about yet

`ergo.rego` doesn't run these forms, and the spec doesn't pin down their rows, so there are no cases for them. A case for each can go in once the question is settled, and be listed in `known_differences` in `spec_test.rego` while `ergo.rego` fails it.

- A subject's name in double quotes on the right side of a phrase, like `x is "production deployment"`: it is a string value there, as any quoted string is, so a subject with a space in its name can't be read on the right side. A name that needs quotes has no other spelling there yet.
- `last of`: what a row's `inputs` name is. `first of xs` prints `item 1 of xs`, because the position is known when the sentence is read. The last position isn't, and an empty list has no item to number. It could print `last of xs`, or `item 3 of xs` for a list of three and something else for an empty one. The meaning is clear: the last item, absent on an empty list, `unusable` on something that isn't a list, as `first of` is.
- `count of`, `sum of` and `plus` in the phrase of an `every` or `some`, like `every xs is count of ys`, and an elapsed time there, like `every xs is days elapsed from started to ended`: [sentence.resolve.root](syntax.md#where-a-name-resolves) says their names resolve from the subject, but not what the row's `inputs` show for such a number.
- An elapsed time in the `whose` of a `count of`, a `sum of` or an `every`, when an item can't be decided: which path `failures` names when the check reads two, `started` or `ended`.
- An elapsed time in a subject's `from` line, like `vulns whose days elapsed from started to ended is 1`: what the `$applies` row shows for it, and which paths its `inputs` list.
- A `plus` in the `whose` of a `count of` or a `sum of`, like `count of xs whose a plus b is 3 is 1`: whether a `whose` condition can have `plus` on its left.

## Numbers in a report's hash

[report.hash](semantics.md#statuses) writes the report as RFC 8785 says, and RFC 8785 writes every number as a 64-bit float. Ergo copies numbers from the input into the report with every digit, so a report holding `1.00000000000000000001` hashes as if it held `1`. Two reports that differ only there get the same hash. A number too big or too small for a 64-bit float, like `1e400`, can't be written that way at all, and implementations already write it differently in the report (see [Values](semantics.md#values)). The open question is whether that's fine, or whether the hash should write numbers as the report does.

## Numbers with huge exponents

OPA 1.20.2 crashes when it compares a number whose exponent is beyond ±1e6 with any other number, from the input, the params or the policy, so `ergo.rego` gives no report at all. `size is at least 5` on this input stops OPA 1.20.2 with `panic: illegal value` in `ast.NumberCompare`. OPA 1.22.0 doesn't crash, but it refuses this input, and `1e1000000` too, with `invalid number: number too big` before `ergo.rego` runs, so there's still no report:

```json
{"items": [{"size": 1e1000001}]}
```

`1e-1000001` does the same, and so does `size is at least limit` on `{"items": [{"size": 1e1000000, "limit": 1e1000001}]}`. `1e1000000` against `5` is compared correctly, and so is `1e400` against `1e401`. The crash doesn't need a check that compares anything: OPA sorts subject ids, so `identified_by: id` on two subjects with ids `1e1000000` and `1e1000001` crashes too, whatever the check says.

[Values](semantics.md#values) allows a fix that fails such a check as `unusable`. That can't cover the sort of subject ids, because no check row reads them. Both wait for a real need, or for OPA to fix the crash.

## Where ergo.rego and the Rust engine differ

The spec doesn't settle these yet, because the two engines give different reports. Both still fail and pass the same checks.

- **A check with a field it doesn't take.** [sentence.print.written_wrong](syntax.md#printing-the-sentence) doesn't say how a check prints when its sentences read but it has an unknown field, a `for` that isn't a string, or `for` or `assert` next to `any_of`. `ergo.rego` prints it as written and Rust prints it from its parse, so `{"assert": " x  is  1", "zzz": 1}` gives `x  is  1` with one and `x is 1` with the other.
- **A path from an input that is a list whose `named by` key comes from the params, on a child subject.** [path.not_an_object](semantics.md#reading-a-path) settles a key read from `$input` in every sentence, but `$input.m named by $params.k` only in a check that doesn't go through a list item by item. On the input `[{"id": "t", "k": "a", "m": {"a": "a"}, "rs": [{"id": "r1", "tags": ["a"]}]}]` with no `k` in the params, the check `tags contains $input.m named by $params.k` of a child subject read from `every t.rs` fails as `absent` with `$params.k is missing` in `ergo.rego` and as `not_an_object` with `$input is [...], which isn't an object` in Rust.
- **A plain check whose `named by` key is read from an input that is a list, with a different message in each engine.** The cause is `not_an_object` in both, as [path.not_an_object](semantics.md#reading-a-path) says, but the message differs. A part with `has: {"pk": "m named by $input.k"}` and the check `k is pk` or `pk exists` gets the list message in `ergo.rego` and `k equals pk is false` or `pk exists is false` in Rust. `n plus $input.m named by $params.k is 2` says `... is false` in both.
- **A one-line `every` or `some` that doesn't read the params, when the params aren't an object.** [for.roots](semantics.md#for) says what a check under a `for` line says then, but no rule says it for a one-line `every`, `some` or `every … whose`. With the params `3` and the input `{"k": "a", "m": {"a": "a"}, "rs": [{"v": "a"}, {"v": "b"}]}`, `every rs.v is m named by $input.k` fails as `unusable` in both engines, with `every rs.v equals m named by $input.k is false` and `failures` `[]` in `ergo.rego`, and with `item 2 of rs: v is "b", and m named by $input.k is "a"` and item 2 in `failures` in Rust. On the same input in a list, `ergo.rego` says the same, and Rust says `$input is [...], which isn't an object` and lists each item as `not_an_object`.
- **`failures` of a `whose` with `is in` that can't decide.** `some rs whose v is in ls named by $input.k exists` on an input that is a list lists `rs[0].ls named by $input.k` with the value `null` in `ergo.rego` and `rs[0].v` with the value `"a"` in Rust. On an object input, `some rs whose v is in ls exists` with `ls` missing or `null` on the items does the same, `rs[0].ls` in `ergo.rego` and `rs[0].v` in Rust. The messages agree. Rust listing the right side only when it was read from the item would differ from `ergo.rego` when `ls` holds something that isn't a list, where both name the left side.
- **A walk whose `named by` key can't be read, on main.** `every rs.v is $input.m named by $params.k` and the same with `some`: with `k` missing, `ergo.rego` says `$params.k is missing` and Rust says `$input.m named by $params.k is missing`, and with `k` holding `3`, `ergo.rego` fails as `unusable` with the list message and Rust says `$params.k is 3, which isn't text`. With `for: every rs as r` and the check `r.v is m named by $input.k`, Rust adds `; the check is false` after the list message. With `k` holding `3`, `every rs.v is m named by $input.k` says `item 1 of rs: $input.k is 3, which isn't text; item 2 of rs: $input.k is 3, which isn't text` in `ergo.rego` and `$input.k is 3, which isn't text` in Rust. In the `whose` of a `for` line, like `every rs whose zz is m named by $input.k as r`, `ergo.rego` names a key that is missing or `null` once before the items and Rust names it in each item, or leaves it out when an item fails worse. The `whose` of a one-line `every` or `some` does the same: on `rs` holding `[{"v": "a"}, {"v": 4}]`, `every rs whose zz is m named by $input.k, if any, exists` says `$input.k is missing` in `ergo.rego` and `item 1 of rs: $input.k is missing; item 2 of rs: $input.k is missing` in Rust when the key is missing, and `$input.k is null; item 1 of rs: zz is missing; item 2 of rs: zz is missing` in `ergo.rego` and `item 1 of rs: zz is missing; item 2 of rs: zz is missing` in Rust when it is `null`.
- **A `count of` whose `whose` reads a key that can't be read, on main.** On the same `rs`, `count of rs whose v is m named by $input.k is 1` says `$input.k is missing; item 1 of rs: m is missing; item 2 of rs: m is missing` in both engines. `count of rs whose zz is m named by $input.k is 1` says `item 1 of rs: zz is missing` in `ergo.rego` and `item 1 of rs: zz is missing, and m is missing` in Rust after the key. With the key holding `3`, `count of zzs whose v is m named by $input.k is 1` with no `zzs` fails as `unusable` with `$input.k is 3, which isn't text; zzs is missing` in both engines, and `count of rs whose zz is m named by $input.k is 1` with `rs` holding `["a", {"v": 1}]` fails as `unusable` with `item 1 of rs: $input.k is 3, which isn't text; item 2 of rs: $input.k is 3, which isn't text` in `ergo.rego` and as `not_an_object` with `$input.k is 3, which isn't text; item 1 of rs is "a", which isn't an object; item 2 of rs: zz is missing, and m is missing` in Rust. A path read from a root, like `count of rs whose zz is $input.m named by $input.k is 1`, says `item 1 of rs: $input.k is 3, which isn't text; item 2 of rs: $input.k is 3, which isn't text` in `ergo.rego` and `$input.k is 3, which isn't text; item 1 of rs: zz is missing; item 2 of rs: zz is missing` in Rust when the key holds `3` and the input has an `m`. With no `m`, Rust says `$input.k is 3, which isn't text; $input.m is missing` before the items. The same goes for `is in $input.m named by $input.k`. With no `m` in the input, the same check with the key missing says `$input.k is missing` and then each item in `ergo.rego`, and `$input.k is missing; $input.m is missing` and then each item in Rust, and with the key `null` it starts with `$input.k is null` in `ergo.rego` and `$input.m is missing; $input.k is null` in Rust. With `is in $input.m named by $input.k`, `ergo.rego` says only the key, and fails as `null` when the key is `null`, and Rust says what it says for `is`, and fails as `absent`.
- **A key that can't be read beside a path that fails another way, on main.** `k is zz followed by m named by $input.k` with no `k` or `zz` on the subject and the key holding `3` fails as `unusable` with `$input.k is 3, which isn't text` in `ergo.rego` and as `absent` with `k is missing, and zz is missing` in Rust. `k is m named by n named by $input.k` with no `k` and `n` holding `{"b": "a"}` fails as `absent` in `ergo.rego`, with `$input.k is missing` when the key is missing and `k is missing, and m named by n named by $input.k is null` when it is `null`, and as `unusable` with `n is {"b": "a"}, which isn't text` in Rust.
- **A key read from `$params`, or read by two conditions of a `whose`, in a `count of`.** With `rs` holding `[{"v": "a"}, {"v": 4}]` and `m` holding `{"a": "a"}` in the params, `count of rs whose zz is $params.m named by $params.k is 1` with `$params.k` `null` fails as `absent` and says `item 1 of rs: zz is missing; item 2 of rs: zz is missing` in `ergo.rego` and `$params.k is null; item 1 of rs: zz is missing; item 2 of rs: zz is missing` in Rust. So do `$params.m named by $input.k` with `$input.k` `null` and `$params.m[$params.k]`. With `rs` holding `["a", {"v": 1}]` both fail as `not_an_object`, and `ergo.rego` again leaves out `$params.k is null; ` before `item 1 of rs is "a", which isn't an object`. Two conditions that read the same key do the same: `count of rs whose zz is $input.m named by $input.k and whose v is m named by $input.k is 1` with `$input.k` `null` says `item 1 of rs: zz is missing; item 2 of rs: zz is missing` in `ergo.rego` and starts with `$input.k is null; ` in Rust, and with `rs` holding `["a", {"v": 1}]` and the key missing or `null`, `ergo.rego` leaves the key out and Rust names it. With one condition and a key from `$input`, both engines name the key first.
- **An option of an `any_of` beside a side that is `null`, on main.** Rust names the `null` side in an option as it does in a plain check, and `ergo.rego` names only what is missing. `{"any_of": {"a": "zz is yn", "b": "zz is 1"}}` with `yn` `null` and no `zz` says `a: zz is missing; b: zz is missing` in `ergo.rego` and `a: zz is missing, and yn is null; b: zz is missing` in Rust. The same goes for a `named by` key: with `$input.k` `null` and no `k`, an option `a: k is m named by $input.k` says `a: k is missing` in `ergo.rego` and `a: k is missing, and m named by $input.k is null` in Rust.
- **A `plus` that reads the item, under a `for` line with a key that isn't text, on an input that is an object.** With `for: every xs as x`, the params `{"k": 3}`, an input that is an object, `from: things` and `xs` holding `[1]`, `x.n plus x.m named by $params.k is 2` fails as `unusable` in `ergo.rego` and as `not_an_object` in Rust, which says `$params.k is 3, which isn't text; item 1 of xs is 1, which isn't an object`, where `ergo.rego` says only `$params.k is 3, which isn't text`. The same happens with `$input.k`. With `from: things`, `for: every xs as x`, `x.n plus x.m named by $input.k is 2` and the input `{"k": 3, "things": [{"id": "t", "n": 1, "m": {"a": 1}, "xs": [1]}]}`, `ergo.rego` fails as `unusable` with `$input.k is 3, which isn't text`, and Rust fails as `not_an_object` with `$input.k is 3, which isn't text; item 1 of xs is 1, which isn't an object`. With `$input.k` `null` or missing, both engines agree.
- **A key on the empty list of a `from` line, with the params not an object.** With the params `3`, `es` `[]`, `$input.k` holding `3` and `from: things whose some es.v is m named by $input.k`, `$applies` fails as `unusable` in both engines. `ergo.rego` says `$input.k is 3, which isn't text` and Rust says `the check is false`. Rust names the key for `every es.v, if any, is m named by $input.k`, and not for `some`.
- **Keys that are missing or `null`, beside each other or beside the list, on an empty list.** With no params and `es` `[]`: with no `k` and `j` `null`, `every es whose zz is m named by $input.k and whose v is m named by $input.j, if any, exists` fails as `absent` and says `$input.k is missing; $input.j is null` in both engines. With `k` `null` and no `j`, `every es whose zz is m named by $input.k, if any, is m named by $input.j` fails as `null` in `ergo.rego`, with `$input.k is null`, and as `absent` in Rust, with `$input.j is missing; $input.k is null`, which is the worse cause first, so Rust is right. With neither key, the same check says `$input.k is missing` in `ergo.rego` and `$input.j is missing; $input.k is missing` in Rust. A `for` line on `es` `null` with no `$input.k`, like `every es whose zz is m named by $input.k as e`, fails as `absent` in `ergo.rego`, with `$input.k is missing; es is null`, and as `null` in Rust, with `es is null`.
- **A key that isn't text beside a root that isn't a number, on an empty list, when the params aren't an object.** With the params `3`, `es` `[]`, the input `{"things": [{"id": "t", "z": "s", "m": {"a": 2}, "es": []}], "k": 3, "z": "s"}` and `every es whose zz is m named by $input.k, if any, is at least z`, both engines fail as `unusable`. `ergo.rego` says only `$input.k is 3, which isn't text`, and Rust says `z is "s", which isn't a number`. With `$input.z` in place of `z`, Rust says `$input.z is "s", which isn't a number`.
- **`failures` of an item that fails because of a part or a field of the subject in its `whose`.** With the part's `z`, or `t.z`, `null`, no `y` in the input and `es` holding `[{"v": 1}]`, `every es whose v is in pl.z and whose v is in $input.y exists` fails as `absent` with `pl.z is null; $input.y is missing` in both engines, and `failures` lists item 1 of `es` with the path `pl.z` and the location `/ts/0/p/z` in `ergo.rego` (for `t.z`, the path `t.z` and the location `/ts/0/z`), and with the path `es[0].v` and the location `/ts/0/es/0/v` in Rust. A `$params` or `$input` root gives `es[0].v` in both. When the params aren't an object, the `cause` of such an item on a `for` line differs too: with the params `3`, `for: every ws as w` with `every es whose v is in pl.z, if any, exists` (and `$input.z`, `t.z`, `some es whose v is in w.z exists`) and `es` `null`, item 1 of `ws` has the cause `unusable` in `ergo.rego` and `absent` in Rust. With `pl.z` holding `"s"` and no `es`, `pl.z` gives `unusable` in both, and `$input.z`, `t.z` and `w.z` give `unusable` in `ergo.rego` and `absent` in Rust.
- **`ignoring case` on letters added to Unicode after version 12, in OPA's Wasm runtime.** [text.case](semantics.md#text-ignoring-case-and-surrounding-spaces) doesn't pin a Unicode version. `x is "\uA7C7" ignoring case` on `"\uA7C8"` (Latin letters added in Unicode 13) passes with `opa eval` and with the Rust engine, which lowercase U+A7C8 to U+A7C7, and fails in OPA's Wasm runtime, which doesn't lowercase it. So `x does not equal "\uA7C7" ignoring case` on `"\uA7C8"` fails with `opa eval` and with Rust, and passes in Wasm. A host that embeds OPA as a library uses the Unicode tables of its own build. The cases can't pin the Wasm result.
- **A `for` line's own path that meets `null` before its end.** [path.null](semantics.md#reading-a-path) says `null`, naming the step. With `m` `null` on an item of `items`, `every items.m.n as x` still fails as `absent` in both engines and says `m.n is missing`, and the item in `failures` says `m.n is missing` in `ergo.rego` and `item 1 of items: m.n is missing` in Rust. R5-6 pays it.
- **`m.n is null`, `every items.m.n is null` and `count of items whose m.n is null is 1` with `m` `null`.** `ergo.rego` fails them as `null` with `m is null`, as [path.null](semantics.md#reading-a-path) says, and Rust passes them. [equals.pass](semantics.md#compare) can be read either way, so [tally.walk](semantics.md#counts-and-sums-in-sentences) has to be settled first. The Rust engine pays it once that is decided.
- **An `any_of` or a multi-sentence check that holds one of the forms above.** Each of its sentences says what it says on its own, so the engines differ where that form does, and its plain options keep the key's cause, like `a: $params.k is 3, which isn't text`.

## Where both engines differ from a rule

- **A bad ref before `named by each of`, with a good list.** [subjects.sentence](semantics.md#requirements) says each key is a subject even when the path before `named by each of` doesn't end `found` on an object. With `from: scans named by $params.env named by each of $params.k`, `env` holding `1` and `k` holding `["a"]`, neither engine makes a subject of `a`: both give no subjects, and `$min_subjects` fails as `unusable`. The rule should either make the keys subjects there too, or say that a bad ref in the path gives none.

## Differs from the general rules

These shapes break one of the rules under [Which problems a message says](semantics.md#which-problems-a-message-says), in one engine or in both, on `main`. Each line says which rule. The last ones are about other rules, and are here because they were found with the rest.

- **The right side of `is in` with a part that is `null` says `absent` ([walk.right.fail](semantics.md#every-and-some)).** With the part `pl` `null`, `$params.w is in pl.name` fails as `absent` and says `item 1 of t: c.name is missing` in both engines, where the rule says `null`. Issue #712 pays it.
- **A `named by` key from outside the items in a `whose`, when an item also fails on its own ([problems.where_said](semantics.md#which-problems-a-message-says), [problems.all_said](semantics.md#which-problems-a-message-says)).** When every item reads its other fields fine, the key is said once and each item says only the value before the key, as [walk.flaws](semantics.md#every-and-some) says. When an item also fails on another field, or isn't an object, `ergo.rego` keeps the message `main` gives for the whole row, on a one-line `every`, `some` or `count of` and on a `for` line alike. With `k` holding `3` in the params and `rs` holding `[{"v": 1}, {"v": 2}]`, `every rs whose zz is m named by $params.k exists`, `count of rs whose zz is in m named by $params.k is 1` and `for: every rs whose zz is m named by $params.k as r` all say `item 1 of rs: $params.k is 3, which isn't text; item 2 of rs: $params.k is 3, which isn't text`, so the key is said in each item and `zz is missing` isn't said. With `k` `null` and `es` holding `[{"v": 2}, {"zz": 2, "m": null}]`, `every es whose zz is m named by $params.k exists` says `item 1 of es: zz is missing; $params.k is null`, and the `for` line says `$params.k is null; item 1 of es: zz is missing; item 2 of es: m is null`. With no `k`, `every rs whose zz is m named by $params.k exists` says only `$params.k is missing`. Each item the message names has an entry in `failures` with the same message and cause. The rule says the key once, then each item's own problems, `zz` and `m` alike. The Rust engine says that on a one-line `every`, `some` and `count of` and on a `for` line alike, a second line's `whose` that reads the key through the first alias included: with `k` holding `3`, `every rs whose zz is m named by $params.k exists` says `$params.k is 3, which isn't text; item 1 of rs: zz is missing, and m is missing; item 2 of rs: zz is missing, and m is missing`, and `for: every ms as m, every m.es whose zz is m named by $params.k as e` with `ms` holding `[{"es": [{"n": 2}]}]` says `$params.k is 3, which isn't text; item 1 of ms: item 1 of m.es: zz is missing`. On a `for` line it lists the key in the row's `inputs`, as [row.parts](semantics.md#what-a-row-shows) says, with no `list` entry for it, and each item's entry keeps its own cause. `ergo.rego` moves to the rule in G5 (#694).
- **A `named by` key read whole from the first line's alias in a second line's `whose`, in `ergo.rego` ([for.roots](semantics.md#for), [problems.all_said](semantics.md#which-problems-a-message-says)).** The key is a root of the first line's alias, so it is said once under its item of the first list, before any item of the second, on an empty list too. With `ms` holding `[{"q": 3, "es": [{"n": 2, "zz": 1}]}]`, `for: every ms as m, every m.es whose zz is q named by m as e` with `e.n is 2` says `item 1 of ms: m is {"es": [{"n": 2, "zz": 1}], "q": 3}, which isn't text; item 1 of ms: item 1 of m.es: q is missing` in the Rust engine, and `item 1 of ms: item 1 of m.es: m is {"es": [{"n": 2, "zz": 1}], "q": 3}, which isn't text` in `ergo.rego`, which says the key under the item of `m.es` and leaves out `q is missing`. With `ms` holding `[3]` and `es` `[]`, `every ms as m, every es whose zz is q named by m, if any, as e` fails as `unusable` with `item 1 of ms: m is 3, which isn't text` in the Rust engine and passes in `ergo.rego`, and without `, if any,` the Rust engine says `es is []; item 1 of ms: m is 3, which isn't text` and `ergo.rego` says `es is []` and fails as `value`. `ergo.rego` moves to the rule in G5 (#694).
- **A second line's `whose` with a `named by` key that is the first line's whole alias and can't be read, in the Rust engine ([problems.all_said](semantics.md#which-problems-a-message-says), [row.parts](semantics.md#what-a-row-shows)).** With `ms` holding `[{"q": 3, "es": []}]`, `for: every ms as m, every m.es whose zz is q named by m as e` with `e.n is 2` says only `item 1 of ms: m is {"es": [], "q": 3}, which isn't text` in the Rust engine, where it said `item 1 of ms: m.es is []` before, so it leaves out the empty list when the second list sits under the alias. In `failures`, the Rust engine gives the item entries the cause `absent` where it gave `unusable` before, which is still the cause of the row. With `ms` holding `[null]` and `named by m`, it says `m is null` twice. When each item has a key it can't read, it also cuts `and N more` sooner. R5-6 pays all four, because it builds the row from the clause tree, which says every problem once.
- **A key read from a field doesn't follow the same order as a key read through a ref ([problems.all_said](semantics.md#which-problems-a-message-says), [problems.item_order](semantics.md#which-problems-a-message-says)).** With `s` holding `"x"` and no `p`, `s named by p is 1` says only `p is missing` and fails as `absent`, where the rule says `s is "x", which isn't an object; p is missing` and `unusable`. With `p` holding `3` and `s` holding `{}`, `s.x named by p is 1` says `s.x named by p is missing` and fails as `absent`, so it never says that `p` isn't text. With `s` `null` and no `p`, it says `p is missing; s is null` but fails as `null`, where the worst cause is `absent`. [path.field_step](semantics.md#reading-a-path) still describes the old order.
- **Roots of a `for` line, said worst cause first in `ergo.rego` ([for.roots](semantics.md#for), [message.join](semantics.md#messages), [problems.item_order](semantics.md#which-problems-a-message-says)).** The rule says the roots of the line's own `whose` come first, then the roots of each sentence in the order the sentences are written, and in each group the worst cause first and then the name. The Rust engine does this. `ergo.rego` sorts all the roots of the line together, worst cause first. With the params `{"a": null}` and `xs` holding `[{"v": 1}]`, `for: every xs as x` with `x.v is $params.a` and `x.v is $params.b` says `$params.a is null; $params.b is missing` in Rust, as the sentences are written, and `$params.b is missing; $params.a is null` in `ergo.rego`. With the params `{"a": "s"}` and `xs` holding `[{"v": 1, "w": 1}]`, `for: every xs whose v is at least $params.min as x` with `x.w is at least $params.a` says `$params.min is missing; $params.a is "s", which isn't a number` in Rust, the line's root first, and `$params.a is "s", which isn't a number; $params.min is missing` in `ergo.rego`. Roots that tie on their cause differ too: with no params, `x.v is $params.b` and `x.v is $params.a` say `$params.b is missing; $params.a is missing` in Rust and `$params.a is missing; $params.b is missing` in `ergo.rego`, which sorts them by name across sentences. The second is a case in `cases/for` that `ergo.rego` fails.
- **Roots that tie on their cause are ordered by the text of their clause, not by the root's name ([problems.item_order](semantics.md#which-problems-a-message-says)).** With `$input.os` holding `[{"name": "a"}, {}]` and no `z` in the params, `every xs whose v is in $input.os.name and whose w is at least $params.z exists` says `$params.z is missing; item 2 of $input.os: name is missing`. By name, `$input.os.name` comes first, as on `main`.
- **A `count of` compared with a param of the wrong kind blames the count ([problems.same_path](semantics.md#which-problems-a-message-says)).** With the params `{"n": "s"}` and `xs` holding `[{"v": 1}]`, `count of xs whose v is 1 is $params.n` says `count of xs whose v is 1 is 1, which isn't text`, and `$params.n` has the outcome `usable`. `main` says the same.
- **A whole `$input.k` on an input that is a list, said once per item ([problems.where_said](semantics.md#which-problems-a-message-says)).** On the input `[{"id": "t", "k": "a", "rs": [{"v": "a"}, {"v": "b"}]}]`, `every rs.v is $input.k` fails as `not_an_object` and says `item 1 of rs: $input is [...], which isn't an object; item 2 of rs: $input is [...], which isn't an object` in both engines, where the rule says it once, before any item.
- **A key read from an input that is a list through an alias on a `for` line, said once per item ([problems.where_said](semantics.md#which-problems-a-message-says)).** On the input `[{"id": "t", "k": "a", "m": {"a": "a"}, "rs": [{"v": "a", "m": {"a": "a"}, "ls": {"a": ["a"]}}, {"v": "b", "m": {"a": "b"}, "ls": {"a": ["b"]}}], "xs": [{"v": "a"}]}]`, each of these fails as `not_an_object` and says something for each item of `rs`, where the rule says `$input is [...], which isn't an object` once, before any item. `for: every rs as r, every r.ls named by $input.k as g` (also `some` and `first of`) says `item 1 of rs: ls named by $input.k is null, which isn't an object; item 2 of rs: …` in `ergo.rego` and `item 1 of rs: $input is [...], which isn't an object; item 2 of rs: …` in Rust. `for: every rs as r, every xs whose v is r.m named by $input.k as x` says `item 1 of rs: $input is [...], which isn't an object; item 2 of rs: …` in both engines, after `$input is [...], which isn't an object` in `ergo.rego`. `for: every rs as r` with `every r.ls named by $input.k is "a"` says `item 1 of rs: $input is [...], which isn't an object; item 2 of rs: …` in both engines, and with the params `3`, `item 1 of rs: the check is false; …` in `ergo.rego`.
- **A `first of` or `last of` whose `whose` reads a key from an input that is a list ([problems.where_said](semantics.md#which-problems-a-message-says)).** On the same input, `for: first of rs whose v is m named by $input.k as r` (also `last of`, and with `sorted by v`) fails as `not_an_object` and says `item 1 of rs is {...}, which isn't an object; item 2 of rs is {...}, which isn't an object` in both engines, after `$input is [...], which isn't an object` in `ergo.rego`. Those items are objects, and the rule says the input once, with no item.
- **Params that aren't an object beside a key read from an input that is a list ([problems.all_said](semantics.md#which-problems-a-message-says)).** With the params `3` on the same input, a check that reads both fails as `unusable`, though `not_an_object` ranks higher, and the engines write the two problems differently. `count of`, `sum of` and `plus`, with or without `whose` or `that`, say `$input is [...], which isn't an object, and $params is 3, which isn't an object` in both. `v is $params.m named by $input.k` says `$params is 3, which isn't an object, and $input is [...], which isn't an object` in `ergo.rego`, and `some rs whose v is $params.m named by $input.k exists` says `$input is [...], which isn't an object; $params is 3, which isn't an object`, where Rust says only `$params is 3, which isn't an object` for both. `every rs.v is $params.m named by $input.k` says only the params in both engines, and so do the `for` lines that read both, like `for: every rs whose v is $params.m named by $input.k as r` (`cases/list_items`).
- **Items that aren't objects in a second `for` list whose `whose` reads a list input's key through an alias ([problems.all_said](semantics.md#which-problems-a-message-says)).** With `xs` holding `[{"v": "a", "n": 1, "m": {"a": 1}, "ns": [1]}, 1, null]` on the input above, `for: every rs as r, every xs whose v is r.m named by $input.k as x` says `$input is [...], which isn't an object; item 1 of rs: $input is [...], which isn't an object; item 2 of rs: $input is [...], which isn't an object` in `ergo.rego`, and Rust says the same without the first clause. `failures` lists items 2 and 3 of `xs` as `not_an_object` under each item of `rs`, but the message never says `item 2 of xs is 1, which isn't an object`.

- **A root whose key comes from the item, said in each item ([problems.where_said](semantics.md#which-problems-a-message-says)).** Both engines say the part before the key once and first in a one-line `every … exists`, `some … exists` or `count of` compared with a value, over a list that is one field of the subject, like `xs`, whose one `whose` is a field of the item that `contains` or `matches` such a root (`cases/derived`), and so does that `count of` when the field `is` such a root. - **A root repeated in an item of a second `for` list, and a root with an item that fails on its own ([problems.where_said](semantics.md#which-problems-a-message-says)).** `every ws as w, some ys whose n is at least $params.z and whose n is at most $params.q as y` with `assert: y.n exists`, `$params.z` holding `"s"`, no `q` in the params and `ys` holding `[{"n": "x", "u": 5}, {"n": 2, "u": 5}]`: `ergo.rego` says `$params.z is "s", which isn't a number; $params.q is missing; item 1 of ys: n is "x", which isn't a number, and $params.z is "s", which isn't a number`, which says the root again in the item, and Rust says `$params.z is "s", which isn't a number; $params.q is missing`.
- **Only the first failing condition of an item is said, after a root ([problems.all_said](semantics.md#which-problems-a-message-says)).** `every ws as w, some ys whose n is at least w.z and whose n is at most u and whose n is at most v as y` with `w.z` holding `"s"` and items of `ys` that lack both `u` and `v`: both engines say `item 1 of ws: w.z is "s", which isn't a number; item 1 of ws: item 1 of ys: u is missing; item 1 of ws: item 2 of ys: u is missing`, and never `v is missing`, where the rule says every problem.
- **The cause of a `null` root before an empty `first of` or `last of` list ([problems.all_said](semantics.md#which-problems-a-message-says)).** `every ws as w, first of ys whose n is in $params.z sorted by n as y`, and `last of`, with `ys` `[]` and `$params.z` `null` say `$params.z is null; ys is []` and fail as `absent`, where `every` and `some` fail as `null` with the same message. Both engines do it.
- **A value that holds `; ` in a message on a `for` line in Rust.** Rust builds an item's problem on a second `for` list by splitting the finished message of a failing condition on `; ` and `, and `, so a root's value that holds `; ` is garbled: `every ws as w, some ys whose n is at least w.z and whose n is at most u as y` with `ws` holding `[{"z": "p; q"}]` and `ys` holding `[{"n": 1}, {"n": 2}]` says `item 1 of ws: w.z is "p; item 1 of ws: q", which isn't a number; item 1 of ws: item 1 of ys: u is missing; and 1 more` in Rust, where `ergo.rego` says `item 1 of ws: w.z is "p; q", which isn't a number; item 1 of ws: item 1 of ys: u is missing; item 1 of ws: item 2 of ys: u is missing`. The same with `first of`, with a value like `"x; y, and z"` or an object holding one, and on `main`, where the item's problem is left out as well. A value that holds `, and ` alone is not garbled.
- **The wrong problem for an item of a second `for` list ([problems.where_said](semantics.md#which-problems-a-message-says)).** `every ws as w, some ys whose $params.z is in tags as x` with no `z` in the params and `tags` holding `["x", 1]` says `item 1 of ys: tags is ["x", 1], which isn't a list of one kind of value` in `ergo.rego` and `item 1 of ys is {...}, which isn't a list` in Rust.
- **A root read through an alias in the `whose` of a list inside a `for` line, beside items that fail ([problems.all_said](semantics.md#which-problems-a-message-says)).** `for: every ws as w` with `every es whose n is at least w.z, if any, is at most 5` (and the same without `, if any,`, and with `some`), `ws` holding `[{"z": "s"}]` and `es` holding `[{}]`, fails as `unusable` in both engines, with `item 1 of ws: item 1 of es: n is missing` in `ergo.rego` and `item 1 of ws: w.z is "s", which isn't a number; item 1 of ws: item 1 of es: n is missing` in Rust. Item 1 of `ws` in `failures` has the cause `unusable` in both. With `es` holding `[{"n": null}]` the messages say `n is null` in place of `n is missing`, and the cause is `unusable` too.
- **A list read from the subject beside a root read through an alias, on a `for` line ([problems.where_said](semantics.md#which-problems-a-message-says)).** Under `for: every ws as w`, with `ws` holding `[{}]` and `es` `null`, `every es whose v is in w.z, if any, exists` (and `some`) says `item 1 of ws: w.z is missing, and es is null`, with `es` in each item, where `count of es whose v is in w.z is 0` and `sum of es.v that is in w.z is 0` say `es is null; item 1 of ws: w.z is missing`, with `es` once, before any item. Both fail as `absent`, in both engines.
- **A part read in a `whose` inside an option of an `any_of`, beside items that fail ([problems.all_said](semantics.md#which-problems-a-message-says)).** With the parent's part `art.cov` `null` and `ys` holding five `{}`, `{"any_of": {"a": "every ys whose n is at least art.cov.z, if any, exists", "b": "some ys whose n is at least g.gc.z exists"}}` says `a: item 1 of ys: n is missing; item 2 of ys: n is missing; item 3 of ys: n is missing; and 2 more; b: item 1 of ys: n is missing; item 2 of ys: n is missing; item 3 of ys: n is missing; and 2 more` in both engines, with the grandparent's part `g.gc` `null` too, without `art.cov is null` or `g.gc is null`, which the same `every` on its own line says first. With `art.cov` holding `{"z": "s"}` the option fails as `unusable` and still names only the items. A root in the `whose` that is `$params.z`, `$input.z`, a part like `pl.z` or `t.z` and holds `"s"` does the same in `ergo.rego`: with `z` `"s"` and `es` holding `[{}]`, `{"any_of": {"a": "every es whose n is at least $params.z, if any, is at most 5", "b": "ok is true"}}` says `a: item 1 of es: n is missing; b: ok is false` and fails as `unusable` (also with `es` holding `[{"n": null}]`), where Rust says `a: $params.z is "s", which isn't a number; item 1 of es: n is missing; b: ok is false`, the root first, with the same cause. In both engines the cause is the worst of the root and the items, though `ergo.rego` doesn't say the root.
- **`failures` of a walk with a key read from the item.** `every xs whose tags contains $input.m named by key, if any, exists`, and `some`, `matches` and `is in`: `failures` names `$input.m named by key` in `ergo.rego` and `xs[0].tags` in Rust. The messages agree. Rust lists the items in list order, which is the order [problems.item_order](semantics.md#which-problems-a-message-says) wants, and `ergo.rego` puts an item that isn't an object last (`cases/derived`, "an every whose whose reads a field of the subject through a key the item holds..." and "an every or some whose whose reads a part of the subject with a named by key from the item...", both in `engines/rust/known-failures.txt`). With the part null and the first item null, Rust lists items 1 to 3 in list order with paths like `xs[1].tags`, item 1 with the cause `null` where the case expects `not_an_object`.
- **`inputs` of a `sum of … plus` on a `for` line.** `for: every rs as r` with `sum of xs.n plus $params.q named by $input.k is 1`, the params `3` and `xs` holding `[{"n": 1}, 1, null]`: `inputs` has a `sum of xs.n` row with the value `null` in `ergo.rego` and not in Rust, on an input that is an object or a list. The messages agree.
- **The name of an item's field on a `for` line.** `for: every xs as x` with `x.tags contains $input.m named by x.key`: `ergo.rego` says `x.tags is {"a": ["x"]}, which isn't a list` and Rust says `tags is {"a": ["x"]}, which isn't a list`.
- **The "and N more" after three items counts problems, not items, in the Rust engine ([message.items](semantics.md#messages)).** [message.items](semantics.md#messages) says N counts items, and `ergo.rego` counts items. With `$input.x` holding `[1, "a"]` and `es` holding `[{"v": null, "w": 2}, {"v": null, "w": 2}, {"v": null, "w": 2}, {"v": 3}]`, `count of es whose v is in $input.x and whose w is 1 is 0` says `…; item 3 of es: v is null; and 2 more` in the Rust engine, because the fourth item says two things, and `and 1 more` in `ergo.rego`. `main` says `and 1 more` here too, but it counted problems in other shapes already.
- **The entries of a `for` line whose `whose` root has more than three problems, in the Rust engine ([row.parts](semantics.md#what-a-row-shows), [message.items](semantics.md#messages)).** The messages are right, and the entries aren't. In `for` "a name read from outside the item and walked on a for line is said once, before what each item says on its own" ("with more than three items without the name"), the root's problems sit in the assertion's entry, cut to three with no `; and 2 more`, where the case gives `rows` a `list` entry with the cap. In `for` "and N more counts each problem of a part of a subject that is a list once" ("four items that aren't objects are three shown and one more"), the `own` check's `list` entry for `t.rows` says three problems with no `; and 1 more`, where the case says all four, and the `second` check has no `list` entry for `t.ms` and says the four problems, cut with `; and 1 more`, in each item of `m.ws`. R5-7 (#694) builds these entries from the clauses. The Rust test `a_for_lines_whose_root_with_more_than_three_problems_keeps_the_entries_it_has_until_entries_come_from_clauses` pins what they say today.
- **An item's own problem beside a root of a `for` line's `whose` that fails no worse than the item ([problems.all_said](semantics.md#which-problems-a-message-says)).** With the part `pos` `null` and `ws` holding `[{"v": "bob", "n": 2}, {"n": 2}]`, `for: every ws whose v is in pos.name as w` says `pos is null; item 2 of ws: v is missing` in both engines and fails as `null`, where the rule takes the worst cause of all, `absent`. With `pos` holding `[{"name": "bob"}, {}]` and `ws` holding `[{"v": "bob", "n": 2}, null]`, it says `item 2 of pos: name is missing; item 2 of ws is null, which isn't an object` and fails as `absent`, not `not_an_object`. The one-line `every ws.n whose v is in pos.name is 2` takes the worst cause. Cases: `for` "an item's own problem on a for line is said after a root of its whose that can't be read, even when it fails no worse than the root" ("an item without v, with a null part", "an item that is null, with an item of the part without the name"). The cases pin what both engines give and are wrong by [problems.all_said](semantics.md#which-problems-a-message-says), "The row takes the worst cause of all of them, in the order [Causes](semantics.md#causes) gives", and by [for.try](semantics.md#for), which gives `item 2 of ws` its own cause, `absent`, where the cases give it the root's. `ergo.rego` has to change too, so the cases are fixed with G5 (#694).

## Differs from the decisions

The rules in `semantics.md` say what was decided. These shapes don't follow it yet.

### Left for a later PR

The cases below pin what `ergo.rego` gives today, not the decided shape, and the Rust engine lists those it fails in `known-failures.txt`. A later PR moves them to the decided shape in both engines.

- **A `list` entry for a position or a first item that can't be read (#688 D2, plain bugs (a) and (b)).** A walk over `xs[0].ys`, a `for` line over a position, and `every first of region` give an `item` entry, or a `from` line names its read without `$input`, where D2 says a `list` entry named as written. Cases: `messages` "a subject read at the position of a list of the input" (3 cases) and "a subject read from the first item of a list of the input" (2), `sentences` "list positions with more than 15 digits", `subject_name` "every on a position of region" and "the subject name is read in every position of a one-line check on a list subject".

- **A root in a `whose` beside the items it can't read, for the phrases B9 doesn't cover yet (#688 B9).** `ergo.rego` says the root and then each item the clause can't read after `is`, `is not`, `is one of`, `is in` and the phrases that order numbers or times. Case: `walks` "a that key that isn't text, on a list item that isn't an object, names the item and never a field under it", "the item is text".
- **A `null` before a `named by` field on a `for` line (#688 D15, decision 34).** `s.x named by p` with `s` `null` and no `p` is `null` with `p is missing; s is null` on a plain path and on a `for` line alike, so decision 34 is carried for ref-step keys only.
- **Open gaps.** The decisions are silent on a `named by` key on an empty list when one key is missing and the other isn't text, and on a `for` line item that reads a null before a `named by` field.

## Sentences the ABNF and ergo.rego read differently
