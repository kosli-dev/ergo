# Changes to the spec

Each version says whether reports changed, so that anyone who only stores reports knows when to look.

## 0.7

### Changed

- Numbers are compared on every digit, however many they have ([value.number](semantics.md#values)), where the spec left numbers with more than 15 significant digits out. `1234567890.1209567990` is more than `1234567890.1209567890`, in every check that compares numbers, in lists, in the copies `distinct` drops, under `within` and in messages, and a row's answer doesn't depend on the other rows. An implementation reads the input and the params without losing digits. Reports change where an engine counted two such numbers as equal.
- A number in the policy with more than 15 significant digits, counted on the value, is written wrong with `number with more than 15 significant digits: 1234567890.1209567890` ([sentence.value.scalar](syntax.md#values)), wherever a number out of range is. `1.50` has 2 digits and `1e20` has 1. Reports change for policies that write such a number: the requirement fails `$well_formed` and gets no other row.
- A `for` line that starts with `some` and has a second item passes when one item of the first list passes, as [for.pass](semantics.md#for) says, even when another item's alias holds a value the sentence can't read. With `approvers` holding `[{"username": "ada"}, {"state": "APPROVED"}]` and `commits` one commit, `for: some approvers as approver, every commits as commit` with `approver.state is "APPROVED"` passes, where `ergo.rego` 0.6.0 and the Rust engine 0.4.0 failed it as `absent` with `item 1 of approvers: approver.state is missing`. The same goes for a second item with `some`, `first of` or `last of … sorted by …`, and for one whose `whose` reads the first item's alias. An item that is an object, where what a sentence or a later line reads through its alias, like `approver.state`, is missing, `null` or of the wrong type, never counts as passing, even when nothing is checked for it because the second list is empty with `, if any,` or its `whose` leaves nothing, and every sentence reads the second item's alias: with `approvers` holding `[{"username": "ada"}]`, `commits` holding `[]`, `every commits, if any, as commit` and `commit.author is approver.u`, the check still fails as `absent` with `item 1 of approvers: approver.u is missing`. An item that isn't an object is judged as before, so when nothing is checked for it, it passes, and `["str", {"username": "b"}]` now passes through `"str"`. When no item passes, the check fails as before. A spec case pins it.

- A `for` line with a list that's empty with `, if any,`, or whose `whose` leaves nothing, still runs the sentences that don't read that list's alias, as [for.if_any](semantics.md#for) says, where it ran none of them. With `approvers` holding `[{"u": "g", "state": "REJECTED"}]` and `commits` holding `[]`, `for: some approvers as ap, every commits, if any, as c` with `ap.state is "APPROVED"` fails as `value` with `item 1 of approvers: ap.state is "REJECTED"`, where `ergo.rego` 0.6.0 and the Rust engine 0.4.0 passed it. The same goes for a `for` line that starts with `every`. With the empty list first, `for: every commits, if any, as c, some approvers as ap` fails as `value` with `item 1 of approvers: state is "REJECTED"`, as `for: some approvers as ap` does, and approvers `[]` fail as `value` with `approvers is []`. With one item, `for: every xs, if any, as m` with `z is 1` fails as `value` with `z is 3` when `z` holds `3` and `xs` holds `[]`, where [for.roots](semantics.md#for) said it passed. A sentence that reads the second item's alias, like `c.author is ap.u`, has nothing to check and is left out. An item of the first list that isn't an object now fails a sentence that reads it as `not_an_object`, so approvers `["str"]` fail where `ergo.rego` 0.6.0 and the Rust engine 0.4.0 passed them. A spec case pins it.

- A root on the left of a number, text or time compare, of `is not`, `does not equal` and of `is … within` and `is not … within` is read before any item, as one on the right is ([for.roots](semantics.md#for), [tally.whose](semantics.md#counts-and-sums)). Under `every xs, if any, as m` with `z` holding `"s"`, `z is at least 1`, `z is not 1` and `z is 1 within 1` fail as `unusable` with `z is "s", which isn't a number` on an empty list, where they passed, and `count of xs whose $params.q is at least v is 0` with `q` holding `"s"` fails the same way. With items, the root is named once with no item in front, and next to the other roots of the sentence, worst cause first. A missing or `null` root on the right of such a sentence is named next to it too: `za is at least zb` with `za` holding `"s"` and `zb` `null` says `za is "s", which isn't a number; zb is null` where it said `zb is null`. With params that aren't an object, like `3`, `z is at least 1` on an empty list was already `unusable`, and its message changes from `for every xs, if any, as m: z is at least 1 is false` to `z is "s", which isn't a number`.

- When `every`, `some`, `count of … whose` or a `for` line's sentence reads a name that walks a list, its row lists that name as a plain check of the same path does, with `[]` after each list walked, the value of each item, `null` where an item stopped, one location for each and the same `part` tag ([walk.inputs](semantics.md#every-and-some), [for.inputs](semantics.md#for)). With the subject `t` from `every teams` holding `[{"name": "ann", "rows": [{"v": "ann"}]}, {"name": "bob", "rows": [{"v": "bob"}]}]`, `every rows.v is in name` lists `t[].name` holding `["ann", "bob"]` at `/teams/0/0/name` and `/teams/0/1/name`, where it listed `t.name` holding `null`. The same goes for a part on a list subject, like `t[].c.z` for `pl.z`, a list in the middle of a name, like `os[].name` for `os.name`, and a part that holds a list, like `pos[].name`. An alias of a `for` line that holds a list is listed the same way in the `inputs` of `failed_assertions`: `every rows.v is in d.name` with `d` holding `[{"name": "ann"}, {}]` lists `d[].name` holding `["ann", null]`, where it listed `d.name` holding `null`, as `$params.w is in d.name` already did. A list phrase in the sentence of a `for` line whose path starts at a subject that is a list now walks the subject, as [walk.start](semantics.md#every-and-some) says, so `for: every rows as r` with `r.v is in name` passes on that subject, where it failed as `not_an_object`. `r.v is name` still fails as `not_an_object`. Reports change for policies that read such a name. Spec cases pin it.

- A part or a parent's name that holds a list is walked on the right of `is in` and the other phrases [walk.right](semantics.md#compare) names, in a `for` line's sentences and `whose` too, as it is without a `for` line ([for.roots](semantics.md#for)). With the part `pos` at `os` holding `[{"name": "ann"}, {"name": "bob"}]`, `for: every rows as r` with `r.v is in pos.name` passes and lists `pos[].name` holding `["ann", "bob"]`, where it failed as `unusable` with `pos is [...], which isn't an object`. The same goes for `count of r.ws whose x is in rel.os.name is 1` with a parent `rel`, and for a part of a subject that is a list. With the part `pl` at `c` holding `[]`, `for: every xs as m` with `m.v is in pl.z` fails as `value` with `item 1 of xs: m.v is 1, and pl is []`, as `$input.c.z` does, where it failed as `unusable` with `pl is [], which isn't an object`. Reports change for policies that read such a name under a `for` line. Spec cases pin it.

- A `count of` or `sum of` inside a `whose` reads its path as it does on its own, whatever it starts at ([tally.whose](semantics.md#counts-and-sums)). `count of rows whose n is count of $input.lst.name is 1` with `$input.lst` holding `[{"name": "bob"}, {"name": "x"}]` passes, where it failed as `unusable` with `$input.lst is [...], which isn't an object`, and its row lists `$input.lst[].name` holding `["bob", "x"]`. The same goes for `$params`, a part and a parent, and for a `count of` in a `for` line's sentence whose path has a list in the middle, like `count of pl.z is 2` with `pl` holding `[{"z": 1}, {"z": 2}]`, which [for.roots](semantics.md#for) already said is walked and both engines failed as `unusable`. Such a count is still read once, before any item, so a problem it has on its own fails the row on an empty list too, with the count's own cause and message, said once: with `$input.lst` holding `[{"name": "bob"}, {}]` and `rows` empty, `count of rows whose n is count of $input.lst.name is 0` fails as `absent` with `item 2 of $input.lst: name is missing`. With items the message is the same, said once with no item of `rows` in front, so on a subject `t` that is a list, `count of rows whose n is count of pl.z is 1` with `pl` missing from the second item says `item 2 of t: c.z is missing`, where Rego said `item 1 of t: item 1 of rows: the check is false; …` and Rust repeated the problem under each item. Reports change for policies with such a count. Spec cases pin it.

- A `for` line's own `whose` lists a list it walks, as a check without a `for` line does ([for.inputs](semantics.md#for)). `for: every rows whose v is in pos.name as r` lists `pos[].name` holding `["ann", "bob"]` with its `part` tag, where it listed only `rows[]`. The same goes for `$input`, a parent and a parent's part, for the `whose` of a second item, and for a `count of` in the `whose`. Only `inputs` change. Spec cases pin it.

- A name read from outside the item that walks a list, on the right of `is in`, `matches` and the other phrases [walk.right](semantics.md#compare) names, or after a `count of` or `sum of`, says its problem once, with no item in front, in an `every`, a `whose` and a `for` line, as [message.items](semantics.md#messages) says. With the part `pos` holding `[{"name": "bob"}, {"name": 3}]`, `every rows.v is in pos.name`, `every rows whose v is in pos.name exists` and `for: every rows as r` with `r.v is in pos.name` say `pos[].name is ["bob", 3], which isn't a list of one kind of value`, where they said `pos is [...], which isn't an object` or put `item 1 of rows: ` in front of it for each row. With `pos` holding `[{"name": "bob"}, {}]` they say `item 2 of pos: name is missing` once, where a `for` line and an `every … exists` said it under each item. A part that holds a list after `matches` is walked in the message too: `count of xs whose v matches pl.z is 0` with `pl` holding `[{"z": 1}]` says `pl[].z is [1], which isn't a list of patterns`, where it said `pl is [{"z": 1}], which isn't an object` for each item. A `count of` in a `for` line's own `whose`, or in the `whose` of a second item, says its problem once, where it said it again under each item, as in `item 1 of t: item 1 of rows: item 2 of t: c.z is missing`, and a second item's `whose` names that problem, where it said `item 1 of ws is missing`. After three problems, `and N more` counts each one once, where it could count a problem twice. Causes don't change.

- On a `for` line, an item's own problem is said after a root that can't be read, even when it fails no worse than the root, as [for.roots](semantics.md#for) says, and [message.items](semantics.md#messages) now names `for` lines as the exception to a root said alone. With the part `pos` holding `[{"name": "bob"}, {}]` and `ms` holding `[{"ws": [{"v": "bob", "n": 2}, {"n": 2}]}]`, `for: every ms as m, every m.ws whose v is in pos.name as w` with `w.n is 2` says `item 2 of pos: name is missing; item 1 of ms: item 2 of ws: v is missing`, where engines said the root alone, or `item 1 of ms: item 2 of ws is missing`. A plain `every … whose` keeps the root alone. Only messages change. Spec cases pin it.

- A list that a phrase after `is in`, `is not in` or `matches` walks and that reads fine isn't named as `os is [...], which isn't an object` when the item is what can't be compared: `every rows.v is in os.name` with `os` holding `[{"name": 3}]` and `v` `"bob"` says `item 1 of rows: v is "bob", which isn't a number`, and `count of rows whose v matches pos.p is 1` says `item 2 of rows: v is 5, which isn't text`. Only messages change. Spec cases pin it.

- A check that reads one name both item by item and as one value lists both reads in its row ([walk.inputs](semantics.md#every-and-some)). With the part `pos` holding `[{"name": "a"}]`, `count of rows whose v is in pos.name and whose w is pos.name is 0` lists `pos[].name` holding `["a"]` and `pos.name` holding `null`, where it listed only the first. Only `inputs` change. Spec cases pin it.

- The message of a `followed by` row after `contains` or `does not contain` that fails as `unusable` names the left side only when it isn't a list of text ([compare.join](semantics.md#compare)). `tags contains $input.o.a.b followed by ""` with `tags` holding `["a"]` and `$input.o.a` holding `1` says `$input.o.a is 1, which isn't an object`, where engines added `tags is ["a"], which isn't a number`. With every piece read, `p contains "a" followed by v` with `p` holding `5` says `p is 5, which isn't a list`, where it said `"a" followed by v is "ax", which isn't a number`, and `l` holding `[1, 2]` says `l is [1, 2], which isn't a list of text`. A piece read from `$input` on an input that is a list names the input, as a path on its own does: `$input is [...], which isn't an object`. Only messages change. Spec cases pin it.
- A root that a check walks as a list fails the check on an empty list too, or when a `whose` leaves no item, when an item of it can't be read or its values can't be used, as [tally.walk](semantics.md#counts-and-sums) now says, for every root [for.roots](semantics.md#for) names. With the part `pos` holding `[{"name": "bob"}, {}]` and `rows` `[]`, `count of rows whose v is in pos.name is 0` fails as `absent` with `item 2 of pos: name is missing`, where it passed. Reports change only for rows that passed.

- A `named by` whose key can't be read on an input that is a list fails as `not_an_object` with `$input is [...], which isn't an object` in a check that doesn't go through a list item by item ([path.not_an_object](semantics.md#reading-a-path), [path.ref_step](semantics.md#reading-a-path)). `k is $input.m named by $params.k` and `k is $input named by $params.k` do so whatever `k` holds, where engines said `absent`, `null` or `unusable` with `$params.k is missing`, `$params.k is null` or `$params.k is 3, which isn't text`, and `k is m named by $input.k` does so where it failed as `unusable`. Each check decides this on its own, whatever the other checks of its requirement are. The cause is `not_an_object` in every plain check, and the message is the list message for the forms the cases pin: a few, like `n plus m named by $input.k is 2`, give the same cause with a different message in the two engines ([OPEN.md](OPEN.md#where-ergorego-and-the-rust-engine-differ)). A one-line `every` or `some`, a `for` line, a `count of` or `sum of`, a child subject's checks and the `whose` of a `from` line don't follow it yet: the spec says what they give where both engines agree, and [OPEN.md](OPEN.md#where-ergorego-and-the-rust-engine-differ) where they don't. Changes the report of such checks. Spec cases pin it.

- A `for` line's row lists each piece of a `followed by` that doesn't start at an alias, and a `$params` list an `every` or `some` walks, as the sentence's own row would ([for.inputs](semantics.md#for)). With `for: every ts as i`, `i.tags contains i.v followed by $params.x.y` lists `$params.x.y`, and `every $params.q is 1` lists `$params.q[]`. A piece of a `followed by` from `$params` or `$input` is in the check's `$refs` too, after `contains` and after `is` alike ([compare.join](semantics.md#compare)). Reports change where an engine left these out of the row or out of `$refs`.

- A check's `$refs` list every path from `$params` or `$input` it reads, wherever it is in the sentence ([value.refs](semantics.md#values)): on either side of `is`, `is at least` or another comparison, after `count of` or `sum of`, the list an `every` or `some` walks, in a `whose`, on a `for` line and in an `any_of` option, like `$params.n` for `n is at least $params.n`. A path that goes through a list, like `$params.objs.x` after `every`, `some`, `count of` or `sum of`, or on a `for` line, is listed once with what the walk read, as after `is in`: `$params.objs[].x` holding `["y"]` at `$params:/objs/0/x` for params `{"objs": [{"x": "y"}]}`. Nothing in a check's `meta` or `description` is listed. They listed only a path after a phrase like `is in`, a key after `named by` and a piece of `followed by`. The `$applies` entry of a `from` line's conditions keeps those for now. Reports change wherever a check reads such a path.

- An `every` or a `some` whose list is missing, `null` or of the wrong type names a part, a parent's part or a grandparent's part that its `whose` or `that` reads and that can't be read before the list ([walk.flaws](semantics.md#every-and-some)). With the parent's part `art.cov` `null` and no `ys`, `every ys whose n is at least art.cov.z, if any, exists` says `art.cov is null; ys is missing`. `ergo.rego` already did this, and the Rust engine said only `ys is missing` for a parent's part. A part of the subject was already named first in both. In an option of an `any_of` a part is named only when it is in the same state as the list: both `null`, both missing, or the part of the wrong type and the list present but not a list. Otherwise the list is named.

- A path whose key is read from `$params` or `$input` and can't be read takes the key's outcome, and in a check that reads two paths the worse of the two outcomes wins, as it already did for a key read from the subject ([path.ref_step](semantics.md#reading-a-path), [compare.fail](semantics.md#compare)). The key decided before. `k is m named by $params.k` with no `k` on the subject and `$params.k` `null` fails as `absent` with `k is missing, and m named by $params.k is null`, where it failed as `null`. The same goes for an `add`, a `count of` or a `sum of`, a one-line `every` or `some`, a `for` line and the condition of a `from` line, whose `$applies` row says `k is missing`. In the `whose` of a `count of`, each item fails with the worse of its own outcome and the key's ([tally.whose](semantics.md#counts-and-sums-in-sentences)), apart from a phrase that reads the path as a list, like `is in`, which reads it before any item, so the key decides when the list can be read, and the list's own cause comes first when it can't: `count of rs whose zz is in m named by $input.k is 1` with no `rs` and the key `null` fails as `absent` with `rs is missing`, where it said `rs is missing; $input.k is null`. Reports change for such checks.

## 0.6

### Changed

- A `from` line with more than one name needs `every` to read a list, wherever the list is ([subjects.from.list](semantics.md#requirements)). `$input`, another subject's name, each field and each key a `named by` reads are names, and a leading dot and a position aren't ([subjects.from.names](semantics.md#requirements)). Without `every`, `$min_subjects` fails as `unusable` with a message that names the list and the fix, like `trails is a list: write every trails.r.prs to read each item`, where `artifact.pull_requests`, `$input.deployments`, `build named by $params.k` and `builds[0].tests` used to give each item of a list, and a list in the middle gave no subject and `in-scope pr count is 0`. A line with one name, like `deployments`, still gives each item.
- `every` works on a child subject: `every artifact.pull_requests` reads the pull requests of each artifact, with the artifact under `in` and `$min_subjects` and `$unique_ids` per artifact ([subjects.every.child](semantics.md#requirements)), where it was written wrong. A parent that is a list is read with it too, and `batch.owner` on a list says `batch is a list: write every batch.owner to read each item`. `every deployment` and `every deployment whose …` are written wrong with `deployment is a subject: write deployment whose … to narrow it, without every` ([subjects.every.subject_name](semantics.md#requirements)).
- A `from` line that ends at text, a number or true or false gives that value as one subject, with or without `every` ([subjects.from.value](semantics.md#requirements), [subjects.every](semantics.md#requirements)), where `$min_subjects` failed as `unusable`. An input that is itself text still fails.
- All the subjects of a `from` line must be of one type, or `$min_subjects` fails as `unusable`, even with `min_subjects: 0`, with a message like `item 1 of builds: version is text, item 2 of builds: version is an object`, and they're still listed and checked ([subjects.one_type](semantics.md#requirements)). `from: tags` on `["a", {"x": 1}]` used to pass. `failed_items` lists the values the message names, one entry each, with `unusable` ([subjects.failed_items](semantics.md#requirements)), and a line without `every` has `failed_items` only then. A child subject of such a line is still read under each parent, as before ([subjects.one_type.children](semantics.md#requirements)).
- `every` reads one list per name, so a list directly inside a list is one subject, and a name after it fails `$min_subjects` as `not_an_object`, like `item 1 of batches is [...], which isn't an object`, where it failed as `unusable` with `owner is null` ([subjects.every.lists](semantics.md#requirements)). Text, a number or true or false where `every` reads a name still fails as `unusable`, and the message names the value where the read stopped, as a check does: `every builds.version.x` on `{"builds": [{"version": "1.0"}]}` says `item 1 of builds: version is "1.0", which isn't an object`, where it said `version.x is null, which isn't a list or an object`.
- A name `every` reads as a list in one item must be a list in all of them, or `$min_subjects` fails as `unusable`, like `tags is a list in item 1 of builds but "c" in item 2`, and the other values are still subjects ([subjects.every.same](semantics.md#requirements)). `failed_items` lists the item where the name is a list and the item where it isn't.
- A list before `named by each of` says `build.test_runs is a list, but named by each of reads the keys of one object: make each item a subject and read the keys in it`, where it said `in-scope test run count is 2` ([subjects.keyed.list_before](semantics.md#requirements)). A list input before it, as in `$input named by each of $params.kinds`, says `$input is a list, but …`, where it said `in-scope t count is 1`, and a parent subject that is a list fails as `not_an_object` with `artifact is a list, but …`, where it said `in-scope k count is 0`.
- A child subject whose parent is text, a number or true or false says `artifact is "x", which isn't an object`, where it said `which isn't a list or an object` ([message.from](semantics.md#messages)).
- The sentence decides where each name resolves, never the data, and one table in [Where a name resolves](syntax.md#where-a-name-resolves) says it for every word. Reports change for the policies below, and for no other.
- A bare name on the right side of the phrase after `every` or `some` is the subject's field, not the item's ([sentence.resolve.root](syntax.md#where-a-name-resolves)). With the subject `pr`, `every approvers.username does not equal author` compares each username with the pull request's `author`, so `ann` fails as `value` where the row failed as `absent` because approvers have no `author`. The same holds for a name written with a dot, a `named by` field there, and the right side of a `some` or `every` condition in a `from` line, which reads the candidate subject. `every conditions.type equals type` is no longer compared with itself, so it isn't written wrong. Comparing two fields of one item takes a `for` line. Such a row's message names the subject's field without the item, like `author is missing`, and its `inputs` list it.
- `whose` and `that` after `every`, `some`, `count of` and `sum of`, and on a `for` item, read the value the path ends at, not the item of the last list walked ([sentence.resolve.focus](syntax.md#where-a-name-resolves)). `count of approvers.username whose state is "APPROVED"` fails as `not_an_object`, with `item 1 of approvers: username is "ann", which isn't an object`, where it read each approver's `state`. To filter on one field and check another, put the item on a `for` line. The `sorted by` field of a `for` item is read on that value too. A value that is missing fails a condition that reads it as `absent`, like `item 2 of approvers: username is missing`.
- The subject's name followed by a step, like `pr.author`, reads the subject's field inside a relative clause, in a check, an `any_of` option, a `for` item and a `from` line, where it used to be written wrong ([sentence.path.subject.step](syntax.md#paths)). Outside a relative clause it is still written wrong.
- `sentence.argument.item` is gone, and so is the warning about `every $input.artifact.developers does not equal tested_by` in [sentence.every.walk](syntax.md#every-some-and-whose). [sentence.subject.own](syntax.md#subjects) is narrowed to the two places a subject's own name in its `from` line is the input field.
- The subject's name followed by a step, a position or `named by`, like `pr.author`, `pr[0].y` or `pr named by k`, is allowed inside a relative clause, where `k` is the focus's field.
- A `whose` that compares a field with itself says how to read the subject's field, with the subject's name: `to read the subject's x, write pr.x`, in a check, an `any_of` option and on a `for` item, where it said to compare under `assert`, or that a count or a sum couldn't read it. A `from` line says `whose: x is compared with itself` alone.
- `distinct` no longer makes a phrase that reads a bare name written wrong, because that name resolves from the subject. Such policies now run.
- A `sum of` whose `whose` reads a name against the value it adds is written wrong ([sentence.derived.sum](syntax.md#derived-values)): write `that` instead. So is a `that` whose right side is such a name, like `sum of xs.n that equals k is 1`, which says `that k: sum of adds up numbers, which have no fields, so k can't be read from one: to read the subject's k, write pr.k`, so such policies now fail `$well_formed`. A `named by` key read against the number counts too, like `k` in `sum of xs.n that equals $params.m named by k is 1`.
- A `named by` on the right of the phrase after `every` or `some` reads the subject's field whatever the path starts at, a part, a parent, an alias, `$params` or `$input` included ([path.field_step](semantics.md#reading-a-path)), where it read the item's. `every xs.v equals $params.m named by k` reads the subject's `k`, fails once with `k is missing` when the subject has none, and lists `$params.m named by k` and `k` in its `inputs`.

The spec only said the field of the first check that couldn't decide, and `ergo.rego` named the side that isn't a `count of`, or the left side when there was none. Reports change for items where a `whose` finds one of its two fields: `whose lo is at least hi` on `{"lo": 1}` now names `hi` with `null`, where it named `lo` with `1`. A side counts as read only when its path ends `found`, and a `count of` or `sum of` side only when its list is a list, so a `null` field or `{"kids": 5}` is the side named. A `plus` side follows the same rule, and a side that reads outside the item, a `$params` or `$input` path, a part or a parent's field, is named by its own path, like `$params.min`, `w` or `art.q`, with its own location. Verdicts, causes and statuses don't change.
- [sentence.subject.every](syntax.md#subjects) now says that `every` can go with a path that starts with a dot and another subject's name, like `every .artifact.p`, because the dot reads the input field and not the subject. `ergo.rego` wrote it wrong. Without the dot it is still written wrong. A `from: .artifact` also no longer narrows the subject `artifact`, as [sentence.path.start](syntax.md#paths) already said, because `ergo.rego` read it as narrowing. Reports change for such a policy.
- [parts.where](semantics.md#parts) now says that every term of a `plus` on the right side of a `whose`, and each path of an elapsed time there, reads a part or a parent's name, as a bare path on that side does. `ergo.rego` read them as fields of the item, so a check could pass on the item's own data: with the part `pa` set to `meta`, `whose lo is at least pa.w plus hi` passed on an item's own `pa.w` where `meta` had no `w`. Reports change for such checks.
- [sentence.for.pick](syntax.md#the-for-line) now says that a picked second item can read the first item's alias in its `whose`, and is picked for each item of the first list, as a second `every` or `some` item is walked. Reports change for such policies: `every xs as p, first of ys whose k is p.k as q` gave `absent` whatever the data in `ergo.rego`, and now passes or fails on it. [for.pick](semantics.md#for) and [for.failed_items](semantics.md#for) now say that a pick that finds nothing lists no failed item, and [for.shared_failures](semantics.md#for) that a second list that can't be walked is listed once also then. The cases are in `spec/cases/for`.
- [for.failure_inputs](semantics.md#for) now says that the order of a failed `every` or `some` on a `for` line holds when a walk reads a name that sorts before an alias, like a `whose` that reads `$input` or a parent, or a walked path like `"#rows"`, and it's no longer listed as open. `ergo.rego` listed what such a `whose` read first. Reports change for such a policy: the order of `inputs` in `failed_assertions` and `items`. Whether a check passes and its cause don't change.
- On a `for` line whose first item has a `whose` and whose second item starts at the first item's alias, the row's `inputs` showed the second list's values under every first item, including the ones `whose` left out or couldn't decide. They're shown only under the first items that `whose` kept now, as [for.inputs](semantics.md#for) says, and the first item's own entry still lists every item. Reports change for such checks. The verdict, the cause and `failed_items` don't.
- [sentence.path.start](syntax.md#paths) now says that an unknown `$<word>` is read by the grammar like `$params`, and only makes the line written wrong with `unknown name`, next to any other problem the line has. A line that doesn't parse says why. Cases pin what `report.subjects` lists for a `from` with an unknown name, and the messages of a sentence and a `for` line with an unknown name and a syntax error. [sentence.written_wrong.self](syntax.md#written-wrong) is listed next to an unknown name too.
- `sentences.abnf` now reads `$<name>` as a start, after `named by` and in brackets, where it read only `$params` and `$input`, so a line with an unknown name is one the grammar reads. A bare `$params` or `$input` after `named by` or in brackets is still not accepted.
- [parts.tag](semantics.md#parts) says a `count of` or `sum of` entry has a part's tag only when the list it counts or sums starts at the part, and [parts.where](semantics.md#parts) says a `count of` or `sum of` on the right of a `whose` reads a part's alias, and on the left the item's field. Both were already how the rules read for other sides, and the cases now pin them. With a part `pa: "pa"`, `count of items whose w is pa.w is 1` on `{"things": [{"id": "a", "items": [{"w": 1}, {"w": 2}], "pa": {"w": 2}}]}` gives the number entry no `part`, and with a part `x: "p"`, `every xs.v whose n is count of x.z is 1` on `{"things": [{"id": "a", "p": {"z": [1]}, "xs": [{"n": 1, "v": 1, "x": {"z": [1, 1, 1]}}, {"n": 3, "v": 5, "x": {"z": [1, 1, 1]}}]}]}` counts the part's `z` and is satisfied. Reports change for an engine that did otherwise.
- Cases pin that a walk over ten steps on a `for` line, in its `whose` too, is listed with `for: ` in front, as [sentence.for.line](syntax.md#the-for-line) says.

## 0.2

### New

- A `whose` in a subject's `from` line takes a one-line `some` or `every` as a condition ([sentence.subject.condition](syntax.md#subjects)), like `release whose some files.path does not match "^docs/"`. Its `$applies` row gives the inputs and the cause the same sentence gives as a check row. It doesn't change the report of a policy that was read before, and a `from` line that used to be [written wrong](syntax.md#written-wrong) is now read. Its `$applies` row has `failed_items`, as a check's row does ([scope.failures](semantics.md#scope)), and `[]` when it passes. For `from: releases whose some files.path does not match "^docs/"`, the row of release `1.4.1` in `{"releases": [{"id": "1.4.1", "files": [{"path": "docs/typo.md"}]}]}`, which only changes `docs/typo.md`, is:

  ```json
  {"check": "$applies", "subject": {"id": "1.4.1", "type": "release"}, "passed": false, "cause": "value",
   "inputs": [{"name": "files[].path", "value": ["docs/typo.md"], "locations": ["/releases/0/files/0/path"]}],
   "failed_items": [{"path": "files[0].path", "item": "item 1 of files", "cause": "value", "value": "docs/typo.md", "locations": ["/releases/0/files/0/path"]}]}
  ```
- `it` is the subject itself, for a subject of any type, so a list of plain values like ids, regions or tags can be checked: with `from: every deployments.regions`, `it is one of $params.allowed_regions` fails the region that isn't allowed. It starts an assertion, a `whose` condition of a `from` line, and the path after `every`, `some`, `count of` and `sum of`. A position works on a subject that is a list, written in words as for a field: `first of it`, `item 2 of it`. A row's `inputs` name it `it`, and a failed item `item 1 of it`. See [sentence.path.it](syntax.md#paths). Written anywhere else, `it` is written wrong ([sentence.path.it.step](syntax.md#paths), [sentence.path.it.place](syntax.md#paths)).
- Every entry in a row's `inputs`, in a check's `$refs` and in `failed_items` has `locations`, where its value was read: JSON Pointers like `/deployments/3/approved_by`, or `$params:` and a pointer for the params ([location](semantics.md#where-a-value-was-read)). A read that stops early points at the last value it reached, and a worked-out number lists the locations of what it was worked out from.

### Changed

- A policy says `ergo_spec: v0.2`, and the report's `ergo` changes from `"ergo": "v0.1"` to `"ergo": "v0.2"`. A policy that says `v0.1` is written wrong, with `unsupported version v0.1, expected v0.2`. The schemas are under `https://ergo.kosli.com/spec/0.2/`. A policy moves to `v0.2` once the entries below don't affect it, or once it's changed to follow them.
- Reports change: `locations` is required on every entry of `inputs`, `$refs` and `failed_items`, and is `[]` on the entries of `$well_formed`. For the second deployment in `{"deployments": [...]}`, an input that was `{"name": "approved_by", "value": null}` is now `{"name": "approved_by", "value": null, "locations": ["/deployments/1"]}`. Two reads with the same name and value are merged into one entry only when their locations match too, so a report that listed one entry may list two.
- [policy.version](syntax.md#policies) takes an optional `-dev` after the version, which `main` uses until a version is released, like `v0.2-dev`. `v0.2-beta` is still not a version.
- The `$applies` row of a `from` line with two or more conditions has what a check's row would have if the conditions were its assertions ([scope.failures](semantics.md#scope)): `failed_assertions`, with an entry for each condition that failed, in the order written, and `[]` when it passes. The violations keep it. Apart from `locations`, the row of a single plain condition, like `environment is "prod"`, doesn't change. For `from: deployments whose environment is "prod" and change_type is "emergency"`, the row of `d-2` in `{"deployments": [{"id": "d-2", "environment": "prod", "change_type": "standard"}]}` was:

  ```json
  {"check": "$applies", "subject": {"id": "d-2", "type": "deployment"}, "passed": false, "cause": "value",
   "inputs": [{"name": "change_type", "value": "standard"}, {"name": "environment", "value": "prod"}]}
  ```

  and is now:

  ```json
  {"check": "$applies", "subject": {"id": "d-2", "type": "deployment"}, "passed": false, "cause": "value",
  ```

- `it` is a word of the grammar ([sentence.words](syntax.md#words-a-field-cant-be-called)). A subject called `it` is written wrong for the requirements that use it ([sentence.path.it.name](syntax.md#paths)), and so is a `for` [alias](syntax.md#the-for-line) or a [part](syntax.md#parts) called `it`: rename it. A field called `it` is written `.it`, and the report prints `.it`. A bare `it` at the start of a path now reads the subject itself instead of its field `it`, so the report changes for a policy that has one.
- A sentence that failed on a `for` line gives the values it compared, in `inputs` ([for.failure_inputs](semantics.md#for)). Each entry of a failed sentence's `items` has them, and so does a failed sentence that has no `items`, because it doesn't read the second list's item. They are the entries the sentence would have in the `inputs` of a row of its own, with `name`, `value`, `locations` and `part`, and the names as the sentence writes them, like `approver.timestamp`. The report schema gains `inputs` on those entries. A tool can show "1792655359 is not after 1792656245" without reading the sentence. Every failure has them, so a report with many failed items is longer.

  and this check:

- A row shows each entry of its `inputs` once ([row.inputs_once](semantics.md#what-a-row-shows)). A check that reads the same value twice, like `count of approvals plus count of approvals is 4`, listed it twice, as [tally.inputs](semantics.md#counts-and-sums-in-sentences) said. Such a row's `inputs` is now shorter.
- The row of a one-line `some` or `every`, of a `count of` or `sum of`, and an `$applies` row of a `from` condition list the value of each parent or `$input` path they compare with, as a plain check does ([walk.inputs](semantics.md#every-and-some), [tally.inputs](semantics.md#counts-and-sums-in-sentences)), and never the value of a `for` alias. They list the subject's own part they compare with too, with its `part` tag ([parts.tag](semantics.md#parts)). For the check `some commits.author is artifact.owner` the row's `inputs` held only `{"name": "commits[].author", "value": ["bob", "ann"], ...}`, and now `{"name": "artifact.owner", "value": "ann", ...}` comes before it. For `some commits.author is w` it now has `{"name": "w", "value": "ann", "part": {"id": null, "name": "w"}, ...}`. Under a `for` line, a `count of` or `sum of` lists the parent values its `whose` reads, and its own list when that list doesn't start at the alias ([for.inputs](semantics.md#for)). Such rows' `inputs` gain those entries.

What's limited is the path after `every`, `some`, `count of` and `sum of`, which takes ten steps at most, wherever it stands ([sentence.walk.steps](syntax.md#every-some-and-whose)). Policies and reports that stay under it don't change.

It's written wrong with `<alias> can't be an alias: it's a subject's name` or `<alias> can't be an alias: it's a part of <subject>`, which names the subject that declares the part and quotes a name with a space in it. The same alias on two items of a `for` line is still `for: <x> is given twice`.

## 0.1

The first version. Policies need `ergo_spec: v0.1` at their top, and reports get `ergo` and `engine` there.

Before it, the spec had no version, and Ergo read policies written in an older shape: checks as objects with `op` and `path`, subjects with `applies_to` filters, custom operators added as Rego rules, and substitutes. The changes below are against that shape, for anyone with a policy or reports from before 0.1. `ergo.as_sentences` rewrites such a policy into sentences where it can.

- One version for the policy, the report and what one means for the other. A policy names it in `ergo_spec`, and a report in `ergo`.
- A report says what made it in `engine`.
- A report's hash is the SHA-256 of the report without `engine`, written as RFC 8785 says.
- The schemas have `$id`s under `https://ergo.kosli.com/spec/0.1/`.
- Custom operators, which a policy added as `op_passed` rules in the `ergo` package, go, because a sentence can't call one. They come back once a definition format is built, see [OPEN.md](OPEN.md#custom-operators).
- Substitutes, a `substitute` check that satisfied another when it failed, go, since an `any_of` of sentences says the same. Reports lose the `substituted` cause.
- Checks are sentences only. A check written as an object with `op` is written wrong, with `missing assert` and `unknown field op`, and so are `all`, `any`, `inputs`, `literal`, `ref` values, selectors and derived sides written by hand.
- Subjects are written with `from` lines only. A `from` or `identified_by` that isn't a string is written wrong with `not a string`, and `applies_to` and `of` are unknown fields. Literal key lists, selectors in `from` and `identified_by`, and filter names, descriptions and meta have no `from` line form and go with them.
- A requirement written wrong gets only its `$well_formed` row, and its `subjects` counts are 0. Reports lose the `ill_formed` cause, which only such a requirement's rows had. A filter written wrong on a parent subject now fails the `$well_formed` row of each requirement on its children too.
- Reports lose the `unmatched` cause, which only a selector gave, and a check's entry in `requirements` has only `description`, `meta`, `expression` and `$refs`. Its `expression` is always the sentence, printed as [sentence.print.canonical](syntax.md#printing-the-sentence) says.
- A position read from a param that holds a number above 9007199254740991 is `unusable`. It used to read nothing, so `does not exist` passed. A check on such a path fails as `unusable`, so does a check on a part whose path reads it, where it failed as `value`, and a `from` line like `ls[$params.big]` fails `$min_subjects` as `unusable`, where it failed as `absent`.
- `$well_formed`, `$min_subjects`, `$unique_ids` and `$applies` are reserved: a check with one of those names is written wrong with `name reserved`, where it used to add a second row of that name.
- A `from` line that loops through a child subject says `leads to a loop`, where it said `a chain of more than three subjects isn't supported yet`.
