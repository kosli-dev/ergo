# Changes to the Rust engine

Each release names the version of the spec it follows. The spec's own changes are in [spec/CHANGELOG.md](../../spec/CHANGELOG.md), and those of `ergo.rego` in [CHANGELOG.md](../../CHANGELOG.md).

## 0.5.0 (not released yet)

### New

- `ergo report --format pretty` colours its last line by the verdict, bold green for `∴ compliant` and bold red for `∴ not compliant`, and writes it as plain text, as before, when colour is off.

- Experimental: `ergo test policy.yaml` runs the examples a policy carries under `tests.examples`, with the params in `tests.params`, and checks each one's outcome against its report, as spec 0.7 says ([outcome.match](../../spec/semantics.md#examples), [outcome.coverage](../../spec/semantics.md#examples)). It prints each failed example with its lines next to the report's, warns about each check no example shows failing or passing, and exits 1 when an example failed, or on a warning with `--strict`. It exits 2 for a policy with `examples` or `example_params` at the top level, and for a field under `tests` it doesn't know, like `exmples`; `tests.inputs` and `tests.rules` are kept for later and refused for now. `ergo report --format outcome` prints a report as outcome lines in YAML, ready to paste into an example ([outcome.print](../../spec/semantics.md#examples)). A child subject's line names each subject it is read inside after its id, parent first, like `artifact web in deployment d1 fails tests_passed`, and `ergo_policy_engine::ancestors` gives those subjects for a policy. The checks Ergo adds have lines too, like `fails $min_subjects because in-scope deployment count is 0` and `artifact in deployment d4 fails $min_subjects because in-scope artifact count is 0`, and a subject out of scope has `deployment d3 is out of scope because env is "dev"`. `--format outcome` prints them only when the check fails or the subject is out of scope, and refuses a policy written wrong and two rows of one check and one subject that say different things. For now both refuse an `$applies` row that failed with another cause than `value`, ids that are objects or lists, a `$min_subjects` row with only some of its parents in `in`, a row of a check Ergo adds that a longer subject name starts the same way as, like `sign` and `sign in`, and both refuse a heading that could name two requirements, like `x is met` with requirements `x` and `x is met`.

- Experimental: `ergo test --engine rego policy.yaml` builds each example's report with `ergo.rego` through `opa`, in place of the Rust engine, and checks the same lines against it, so a difference between the engines shows up as a failing example. It runs `opa eval` once for all the examples, compiling the policy once with `ergo.compile`. The path of `ergo.rego` is `--ergo-rego`, or the `ERGO_REGO` environment variable, and `opa` is the one on the `PATH`, or `ERGO_OPA`. The output starts with the engine the reports name, like `engine: ergo-rego 0.7.0`. It exits 2, and never falls back to the Rust engine, when `ergo.rego` can't be read, `opa` can't run, fails or prints something that isn't a report, or `ergo.rego` doesn't support the policy's `ergo_spec`. `--ergo-rego` and `ERGO_REGO` are refused without `--engine rego`.

- `ergo report`, `ergo violations` and `ergo test` read the policy, the input or the params from standard input when its value is `-`, with `--stdin-format json` or `--stdin-format yaml`, which is needed when a value is `-` and refused otherwise. Only one value can be `-` in a run. The reading rules are the ones for a file, with the same errors and exit codes, and the messages say `standard input`. It exits 2 and prints no report when `--stdin-format` is missing, unknown or has no value of `-`, when two values are `-`, and when standard input is a terminal. It reads standard input last, after the command line and every file, so those errors are reported without waiting for it to close. It works with `--engine rego`.

- Experimental: `ergo report` and `ergo violations` take `--engine rego` and `--ergo-rego`, with the rules `ergo test` has: the report, and the violations, are the ones `ergo.rego` builds through one `opa eval` that calls only `ergo.report` and `ergo.violations`, and its `engine` says `ergo-rego`. `--ergo-rego` and `ERGO_REGO` are refused without `--engine rego`, and it exits 2, and never falls back to the Rust engine, when `ergo.rego` can't be read, `opa` can't run, fails or prints something that isn't a report, or `ergo.rego` doesn't support the policy's `ergo_spec`. When `ergo.rego` isn't found, the message, for `ergo test --engine rego` too, gives a `curl` line for the latest release of `ergo.rego`. A report that lacks a `results` list or an `engine` name or version, `violations` that aren't a list, and a requirement `status` this version doesn't know are each named in the message that exits 2.

- Experimental: `ergo report --format pretty` prints a report, from either engine, for a person: the requirements that are not met first, each with its failed rows and the report's own `message` after `because`, then the requirements that are met, one line each, a count of the rows, and a last line, `∴ compliant` or `∴ not compliant`. `--show failed|all` says whether only the failed rows or every row is listed, and `--color auto|always|never` and `NO_COLOR` decide the colour. `ergo test` marks its lines with `✓`, `✗` and `⚠` and ends with `∴ N examples: P passed, F failed` on a terminal, or with `--color always`; piped, it prints the lines it always did. Colour is written only for a terminal, and the glyphs only when `LC_ALL`, `LC_CTYPE` or `LANG` names UTF-8, with `ok`, `FAIL`, `warn`, `-` and `->` otherwise. A subject is out of scope only when its `$applies` row fails with the cause `value`; any other cause is a failed row, listed and counted as failed. A row names its parent subjects, like `artifact web in deployment d1`. Control characters in names, ids and messages are written as `\u{1b}`. The first line of `ergo --help` has the therefore sign, or `->` when the locale isn't UTF-8. A report it can't read, a value of `--format`, `--show` or `--color` it doesn't know, and `--format pretty` with `violations` or `--compact` exit 2. The JSON, `--format outcome`, `violations` and `--version` don't change, and no exit code does.

- `from: every member of <path>` makes each member of the object the path ends at a subject, whatever its key, as in `ergo.rego` 0.7.0 and spec 0.7 ([subjects.every.member](../../spec/semantics.md#requirements)). The id is the key unless `identified_by` is written, and a value at the end that isn't an object fails `$min_subjects` as `unusable`.

- `member of` also goes after `every`, `some`, `count of` and `sum of` in checks and on `for` lines, and reads each member of the object the path ends at as an item, named by its key ([walk.member](../../spec/semantics.md#every-and-some), [walk.member.not_an_object](../../spec/semantics.md#every-and-some), [tally.member](../../spec/semantics.md#counts-and-sums-in-sentences)). With `{"statuses": {"build": "DONE", "sign-off": "FAILED"}}`, `every member of statuses is "DONE"` fails as `value` with `member sign-off of statuses is "FAILED"`, and the entry under the assertion is the item `member sign-off of statuses` with the input `statuses.sign-off`. `count of member of evidence whose kind is "approval" is 1` counts the members that pass the `whose`, and `for: every member of evidence as e` checks each member with `e`. A value at the end that isn't an object fails as `unusable`, like `statuses is ["DONE"], which isn't an object`. `distinct` with `member of` is written wrong everywhere, with `distinct can't go with every member of`. As in `ergo.rego` 0.7.0 and spec 0.7. Changes the report of a check or `for` line with `member of` right after `every`, `some`, `count of` or `sum of`, which was written wrong.

- `is`, `equals`, `is equal to`, `is not`, `does not equal`, `is one of`, `is not one of`, `is in` and `is not in` can end with `ignoring case`, `ignoring surrounding spaces` or `ignoring case and surrounding spaces`, as in `ergo.rego` 0.7.0 and spec 0.7 ([text.ignoring](../../spec/semantics.md#text-ignoring-case-and-surrounding-spaces), [text.not_text](../../spec/semantics.md#text-ignoring-case-and-surrounding-spaces)). `status is one of "in progress", "done" ignoring case and surrounding spaces` passes on `"  IN Progress "`. A value that isn't text fails as `unusable`, on either side. With a list read from a path, like `type is in $params.states ignoring case`, each item is prepared too, and an item that isn't text fails as `unusable`, or as `null` when it is `null`, even when the field matches another item, with `item 2 of $params.states is 3, which isn't text`. A path of more than one step, like `$input.cs.name`, `xs[0]` or `pl.name`, is written wrong for now, with `"is in" can't take ignoring case yet`. Such items are named in list order, three at most and then how many more, after what the field itself can't give, the worst cause wins, and an `every` or a `count of` that compares with such a list fails even over an empty list.

### Changed

- `ergo report`, `ergo violations` and `ergo test` with `--engine rego` exit 2 with `the ergo.rego at PATH has no ergo.report` (or `ergo.violations`, or `ergo.compile` for `ergo test`) when `opa` says the entry point is undefined. They said `opa failed on ergo.rego at PATH: ...` or `opa printed something that isn't a report` before. The report printed keeps what `opa` gave, apart from an exponent, which is printed with a lowercase `e` and a sign, so `1e400` and `1E5` are printed `1e+400` and `1e+5`.

- `ergo --version` also prints the commit the binary was built from, like `ergo 0.5.0-dev (commit ab81076ed80cff04a4c2e395418ca5535c6c3dab)`, and `unknown` when the build isn't in a git checkout of this repo. It no longer prints only `ergo 0.5.0-dev`. A script that reads the version line must read the first word after `ergo`.

- `ergo-policy-sentences` reads `member of` after `every`, `some`, `count of` and `sum of` and on `for` lines into new public fields, `ListOptions::member`, `Derived::member` and `ForItem::Walk`'s `member`, so a struct literal of them outside the crate no longer compiles until it sets the field.

- A failed `$min_subjects` row has `failures`, `[]` when it has no entries, whatever its `from` line, as spec 0.7 says ([row.parts](../../spec/semantics.md#requirements)). A passed one has none. Changes the report of every failed `$min_subjects` row that had no `failures`.

- `ergo-policy-sentences` reads `member of` into a new public field of `FromLine`, `member`, so a struct literal of `FromLine` outside the crate no longer compiles until it sets the field.

- `ergo-policy-sentences` reads the words into a new variant, `Phrase::Ignoring`, which holds the phrase they follow and an `Ignoring`. `Phrase` is an exhaustive public enum, so a `match` on it outside the crate no longer compiles until it handles the new variant.

- `ignoring` is a word of the grammar now, as spec 0.7 says ([sentence.words](../../spec/syntax.md#words-a-field-cant-be-called)), so a field called `ignoring` is written `.ignoring`. A sentence that read a bare `ignoring` as a field, like `ignoring is "a"`, `x is ignoring`, `x is in ignoring`, `sum of xs.v is 1 plus ignoring`, `every ignoring.v is 1`, `count of ignoring is 1` or `count of xs whose ignoring is "a" is 1`, is written wrong, and so are `named by ignoring` (`ignoring can't be an alias`), `for: every xs as ignoring`, `for: every ignoring as i`, a part called `ignoring` (`invalid alias`), `from: ignoring`, `from: things whose ignoring is "a"` and `identified_by: ignoring`. With a field `ignoring` holding `"a"`, `.ignoring is "b"` says `.ignoring is "a"` and names its input `.ignoring`, where it said `ignoring is "a"` and `ignoring`. Changes the report of a policy that uses `ignoring` as a name, as in `ergo.rego` 0.7.0: a bare `ignoring` is written wrong everywhere a name can stand, also in a subject's check, a child's `from: every ignoring.xs`, `sum of ignoring` and `sorted by ignoring`.

- Every subject must have an id, as in `ergo.rego` 0.7.0 and spec 0.7 ([unique_ids](../../spec/semantics.md#requirements)). With `from: ds`, `identified_by: id` and `ds` holding `[{"id": "a"}, {}, {"id": null}, {"id": "a"}]`, the `$unique_ids` row fails as `absent` with `repeated d ids is ["a"]; item 2 of ds: id is missing; item 3 of ds: id is null`, where it failed as `value` with `repeated d ids is ["a", null]`, and one subject without an id, which passed, fails too. `$unique_ancestor_ids` does the same for ancestors, each subject without an id is an `item` entry in `failures`, and every failed id row has `failures`, `[]` when only an id repeats. The checks' entries say `Every d has a unique id` and `count(missing(ids(ds))) + count(repeated(ids(ds))) == 0`. A subject read from inside an item, like one of `every xs.meta`, is named by that item, `item 1 of xs: meta.id is missing`, and the whole input from `$input`, `$input.id is missing`. Changes every report.

- A one-line `every … exists`, `some … exists` or `count of` compared with a value, over a list that is one field of the subject, like `xs`, whose one `whose` is a field of the item that `contains` or `matches` a path from outside the item through a key the item holds, like `count of xs whose tags contains $input.m named by key is 1`, says the part before the key once, first, when it is missing, `null` or not an object. A part, like `cov` with `has: {cov: c}`, is said by its name, like `cov is null`. Then it says each item that isn't an object, or whose field or key can't be read, in list order, and the row takes the worst cause of all of them. With `$input.m` missing and `xs` holding `[null, {"key": "a", "tags": ["x"]}]`, it fails as `not_an_object` with `$input.m is missing; item 1 of xs is null, which isn't an object`. With `$input.m` `null` and an item whose `key` is `3`, it says `$input.m is null; item 1 of xs: key is 3, which isn't text`. With `$input.d.m` and `d` `null`, it says `$input.d is null; item 1 of xs: key is missing; item 2 of xs: key is missing`. With `$input.m` holding `3` and an item whose `tags` is `{"a": ["x"]}`, it says `$input.m is 3, which isn't an object; item 1 of xs: tags is {"a": ["x"]}, which isn't a list`. When the list is missing, `null`, not a list or empty, it says the part before the key and then what it said about the list, like `$input.m is null; xs is missing` or `$input.m is null; count of xs whose tags contains $input.m named by key is 0`. Other shapes, like a list reached through a list (`count of xs.v whose …`), a second `whose`, two counts compared, `distinct`, an option of an `any_of` or a `for` line, say what they said before. Before, Rust said the root in each item, or `$input.m named by key is missing` in each item when the root was missing, and named an item that isn't an object `the subject`. The same as in `ergo.rego` 0.7.0 and spec 0.7 ([problems.where_said](../../spec/semantics.md#which-problems-a-message-says)). Changes the report of such checks.

- A number in the policy with more than 15 significant digits is written wrong, as in `ergo.rego` 0.7.0 and spec 0.7 ([sentence.value.scalar](../../spec/syntax.md#values)). `l equals 1234567890.1209567890` fails `$well_formed` with `number with more than 15 significant digits: 1234567890.1209567890`, and a `min_subjects` like `9007199254740993` says `number with more than 15 significant digits`, where it said `not a whole number from 0 to 1000000`. Digits are counted on the value, so `1.50` has 2 and `1e20` has 1. Numbers in the input and the params were already compared on every digit. The same goes for a number in the `meta` of the policy, a requirement or a check, and one out of range there, like `1e400`, is written wrong with `number out of range`, where Rust let both through. Changes the report of every policy that writes such a number.

- A key read from an input that is a list, like `m named by $input.k`, fails the check as `not_an_object` in every sentence, as in `ergo.rego` 0.7.0 and spec 0.7 ([path.not_an_object](../../spec/semantics.md#reading-a-path)), and the check says `$input is [...], which isn't an object` once, with no item in front. On the input `[{"k": "a", "m": {"a": "a"}, "rs": [{"v": "a"}]}]`, `every rs.v is m named by $input.k` fails as `not_an_object` with `$input is [{"k": "a", "m": {"a": "a"}, "rs": [{"v": "a"}]}], which isn't an object`, where it failed as `unusable`. The same goes for a one-line `some`, `count of` and `sum of` with or without `whose` or `that`, `some … whose … exists`, a `plus`, an option of an `any_of`, a child subject's checks, the `$applies` row of a `from` line's condition and the `$min_subjects` row of a `from` line that reads such a key. The messages `item 1 of rs: the check is false`, `count of rs whose v equals m named by $input.k is 1 is false` and `v equals t.m named by $input.k is false` are gone. On a `for` line, a `sum of`, `count of` or `plus` names an item that is `null` as `item 1 of xs is null, which isn't an object`, where it said `item 1 of xs: x is null`. The same goes for the list of a `for` line that reads such a key, like `every rs as r, every ls named by $input.k as g`, which said `ls named by $input.k is null, which isn't a list or an object`, and for its `whose`, like `every rs whose v is m named by $input.k as r`, which said `item 1 of rs: the check is false`, and `every rs as r, every xs whose v is m named by $input.k as x`, which said `item 1 of xs is {...}, which isn't a list` of an item that is an object. When the params aren't an object, a `count of`, `sum of` or `plus` that reads them and such a key, like `count of rs.v that is $params.m named by $input.k is 1` or `count of rs is n plus $params.q named by $input.k`, says `$input is [...], which isn't an object, and $params is 3, which isn't an object`, where it said only `$params is 3, which isn't an object`, or only the input for a `plus`. Other sentences and `for` lines that read both, like `v is $params.m named by $input.k`, still say only `$params is 3, which isn't an object`. Changes the report of checks that read such a key.

- A root that a `whose` or a `that` reads and can't use, beside a list that is missing, `null`, not a list, or empty where an empty list fails, is said first, then the list, with the worst cause of all of them, in an `every`, a `some`, a `count of` and a `sum of`, as spec 0.7 says ([problems.all_said](../../spec/semantics.md#which-problems-a-message-says)). With no `z` in the params and `es` `null`, `every es whose v is in $params.z, if any, exists` fails as `absent` and `count of es whose v is in $params.z is 0` says `$params.z is missing; es is null`, where the `every` failed as `null` and the `count of` said only `$params.z is missing`. With `pl.z` holding `"s"` and no `es`, `some es whose v is in pl.z exists` fails as `unusable`, where it failed as `absent`. A root on the right of the phrase that can't be used is said after the roots and before the list: with the params `{"y": "s"}` and no `es`, `some es whose v is in $params.z is in $params.y` says `$params.z is missing; $params.y is "s", which isn't a list; es is missing`, where it said only the two params. Two roots in a `whose` that fail in different ways take the worst cause on a list that can be read too: with `$params.z` `null`, no `y` in the input and `es` holding `[{"v": 1}]`, `some es whose v is in $params.z and whose v is in $input.y exists` fails as `absent`, where it failed as `null`. A root of the wrong type or `null` beside items that fail on a list that can be read takes the worst cause too, though the message is as before: with `$params.z` holding `"s"` and `es` holding `[{}]`, `every es whose n is at least $params.z exists` says `$params.z is "s", which isn't a number; item 1 of es: n is missing` and fails as `unusable`, where it failed as `absent`, and with `es` holding `[{"n": null}]` it fails as `unusable`, where it failed as `null`. The same goes for `some`, `every … if any, is at most 5`, `$input.z`, a part like `pl.z` and `t.z`, for `every ys whose n is at least art.cov.z, if any, exists` with `art.cov` holding `{"z": "s"}` and five `{}` in `ys`, for an option of an `any_of`, like `a: $params.z is "s", which isn't a number; item 1 of es: n is missing; b: ok is false`, and for a `for` line whose `every es whose n is at least w.z, if any, is at most 5` reads the alias `w` holding `{"z": "s"}`. `failed_items` keeps the same entries, and on a `for` line an item's cause follows its sentence's new cause. When the params aren't an object, the cause and the message of a row stay as they were, and so does an item's cause on a `for` line, except that `every es whose v is in pl.z, if any, exists` under `for: every ws as w`, with the params `3` and `es` `null`, lists item 1 of `ws` with the cause `absent`, where it said `null`, and with the params `3`, `pl.z` holding `"s"` and no `es`, with the cause `unusable`, where it said `absent`.

- Failed rows list their parts in `failures` and inputs carry `outcome`, and messages say what spec 0.7 says: the same change as `ergo.rego` 0.7.0 ([row.parts](../../spec/semantics.md#what-a-row-shows)). `failures` replaces `failed_items` and `failed_assertions`, `any_of` rows list each failed option, and a name read through a `for` alias keeps its alias in messages.  Reports change as in `ergo.rego` 0.7.0.

- A `count of` or a `sum of` names every item it can't read, in list order, after the roots, and each item is an `item` entry under its assertion, as spec 0.7 says ([message.items](../../spec/semantics.md#messages), [row.parts](../../spec/semantics.md#what-a-row-shows)). A `for` alias that holds a list nests its items under the alias, and a walk, a `count of` or a `sum of` has the same entries beside other sentences, in an option of an `any_of`, on a `from` line and under a `for` item. An option's `message` is `""`, and the list a sentence walks is no longer an input of its assertion.

- The `$min_subjects` row has `failures` in place of `failed_items`, on every failed row, and `every.same` says the kind in each item, like `item 1 of builds: tags is a list, item 2 of builds: tags is text`, with a clause both rules give said once ([subjects.every.broken](../../spec/semantics.md#requirements)).

- A root in a `whose` that can't be read no longer hides the items the clause can't read after the phrases that order numbers or times and after `starts with`: the root comes first, then each such item. In a walk the same now holds after `is`, `is not`, `is one of`, `is in`, `matches` and `contains`, except that after `is one of`, `is in` or `matches` a root that isn't a list is still said alone.

- A `named by` key that can't be read is said once before the items, with each item's own problem after it, and a count whose two sides fail in different ways takes an item with its missing end as the spec decides.

- A `count of` or `sum of` says each root of its `whose` or `that` that can't be read once, first, and then what each item says on its own, without the root, and fails with the worst cause of all of them ([problems.all_said](../../spec/semantics.md#which-problems-a-message-says)). With no `k` in the params and `es` holding `[{"v": "s"}, {"v": {}}]`, `count of es.v that is m named by $params.k is 0` says `$params.k is missing; item 1 of es: v is "s", which isn't an object; item 2 of es: v: m is missing` and fails as `not_an_object`, where it said the key inside each item and failed as `absent`. With `$params.q` holding `"s"` and no `k` in the input, `sum of rs.n that is at least $params.q named by $input.k is 1` says `$params.q is "s", which isn't an object; $input.k is missing` and fails as `unusable`. A key that isn't text is said once, before items that say only their own reads, like `$params.k is 3, which isn't text; item 1 of es: zz is missing, and m is missing` (D14 of #688), and a root before a key the item holds, like `$input.m` in `$input.m named by key`, is said once with the item saying only its key (D10). The same goes for the other way round, a map from outside the items with a key read from each item: with `$params.m` `null` and `es` holding `[{"v": "a"}]`, `count of es.v that is $params.m named by k is 0` says `$params.m is null; item 1 of es: v is "a", which isn't an object` and fails as `not_an_object`, where it left out `$params.m is null`, and with `es` holding `[]`, `count of es whose v is p.m named by k is 0` fails as `null` with `p.m is null`, where it passed, because a name read from a root is read once, before any item, even when the list is empty ([tally.whose](../../spec/semantics.md#counts-and-sums)). The assertion of such a count says only its roots, and each item is an `item` entry under it.
- An `every` or a `some` says each root of its `whose` or `that` that can't be read once, first, and then what each item says on its own, without the root, in list order, three and then `and N more`, and fails with the worst cause of all of them, as a `count of` does ([walk.flaws](../../spec/semantics.md#every-and-some), [problems.all_said](../../spec/semantics.md#which-problems-a-message-says)). With no `k` in the params and `es` holding `[{"v": {}}, {"v": {"m": null}}]`, `every es.v that is m named by $params.k is 1` says `$params.k is missing; item 1 of es: v: m is missing; item 2 of es: v: m is null`, where it said only `$params.k is missing`. With `k` holding `3` it says `$params.k is 3, which isn't text` and then the same items and fails as `unusable`, where it said the key inside each item, and an item whose focus isn't an object, like `{"v": "s"}`, says `item 1 of es: v is "s", which isn't an object` and the row fails as `not_an_object`. A key that isn't text is said once beside an item that also fails on another field, like `$params.k is 3, which isn't text; item 1 of rs: zz is missing, and m is missing` for `every rs whose zz is m named by $params.k exists` (D14 of #688), and a root that the items can't read comes before them, like `$params.x is missing; item 1 of es: v is missing; item 3 of es: v is 3, which isn't a list` for `every es whose v contains $params.x is an object` with no `x` and `es` holding `[{}, {"v": []}, {"v": 3}]`. ## 0.3.0

### New

- Every failed row has a `message`, a line that says in plain words what Ergo found, as the spec says: `approver is "ana", and author is "ana"`, `item 2 of tests: ok is missing` or `signed: signature is missing; reviewed: reviewer is missing`. A row that passed has none. Each violation carries the message of its row. The Rego engine writes the same text for every case in the spec.

- A path on the right side of `is one of`, `contains`, `matches` and the other phrases that take a list walks lists, as the spec says, from the input, the params, the subject, a parent, a part or an alias and inside `whose`, `count of`, `sum of` and `for` lines: `pin is in $input.sbom.components.name` compares `pin` with the names of the components. A list it can't read from every item fails every row, with the cause and words `every` uses. A leading dot on that path reads the subject's field, and a message and an input name keep the dot only when a part, a parent subject or an alias has the same first name. A `$input` path or a field on the right that reads into text now says which value can't hold the next step, where it said `the check is false`. A position after a key, like `id is in $input.l[0]`, fails every row as `unusable` when an item holds a value that isn't a list there, and the message names it, `item 2 of $input: l is "ab", which isn't a list`, where it read the position as `null` and a row could pass on the other items.
- `that` picks items by the value itself, where `whose` picks them by a field, as the spec says: `from: every ws that starts with "b"`. It works on a `from` line, in a check and on a `for` line, and a field called `that` is written `.that`.
- `distinct` drops exact copies after `every`, `some`, `count of` and `sum of`, as the spec says, and a bare field called `distinct` is written `.distinct`.

### Changed

- `ergo` reads YAML the way OPA 1.21 and later do, and no longer the way OPA 1.20 does. `ergo.rego` is tested with OPA 1.22.0, which reads YAML the same way as 1.21. Reports change for YAML inputs, policies and params that use any of these:
  - Values that read differently: `yes`, `no`, `on`, `off`, `y` and `n` (in any of their spellings) are strings, as values and as keys, where they were booleans. With `approved: yes`, `approved is true` used to pass and now fails as `unusable` with `approved is "yes", which isn't true or false`, as in `ergo.rego`. A key written in a mapping wins over a merged one wherever the `<<` is, and the first of several merges wins, where the later one did. A date tagged `!!timestamp` is written out in full, like `2001-12-14T00:00:00Z`, where it kept its text.
  - Files that were refused and are now read: a tag YAML doesn't define on a value, like `!custom 5`, which keeps the text, `"5"`; a bare `!`, which reads a plain value as if it had no tag, so `! 5` is 5 and `! .inf: 1` is `{".inf": 1}`; a verbatim tag like `!<tag:yaml.org,2002:int> 5`; `!!merge`; a key from 9223372036854775808 to 18446744073709551615; and `%YAML 01.1` or `%YAML 1.01`.
  - Files that were read and are now refused: a later document that isn't valid YAML, has an alias with no anchor, nests more than 10,000 levels or says `%YAML 1.2` after `...`; a directive other than `%YAML` and `%TAG`, like `%FOO bar`; the same alias twice as a key of one mapping, compared by the anchor's name; a `!!timestamp` key; a `!!timestamp` whose time zone is 24 hours or more; and `!!bool yes` and `!!bool on`. These are refused too, where OPA reads them: a directive inside a document with no `...` before it, like `a: 1`, `%YAML 1.1`, `---` and `b: 2` on four lines, which OPA reads as `{"a": 1}`; a byte order mark right after `---` at the start of a later document; and flow collections nested more than 255 levels in a later document. CLI.md lists them.
- The message of a `$min_subjects` row that failed because a `from` line couldn't be read is the same as `ergo.rego`'s for every shape in `spec/cases/messages`: `item 2 of things is missing`, and for a child subject the path as it walks its parent's value, without the parent's name, like `ws is missing`, `item 1 of ws is missing` or `meta.owner is missing`.
- A `whose` in a `from` line that compares a field of the item with itself, like `things whose x is x` or `t.ws whose t.lo is at most .t.lo`, is written wrong, `whose: x is compared with itself`, as in `ergo.rego`. A left side that names a parent, like `t.ws whose t.lo is at least t.lo`, reads the item's own field, and the right side reads the parent only when it has no dot, so that one is fine.
- When a child's parent has a `from` line that fails on a `named by` key or on `last of`, a `whose` of the child that compares or tests membership against a subject further up, like `w.kids whose lo is at least t.cov.x`, adds the problem `subjects.g.from: unknown alias $t`, listed after the other problems, as `ergo.rego` does. It isn't reported when the parent's `from` has `every` or `named by each of`, when the right side is a `count of`, a `sum of`, a `plus`, `contains`, `matches` or `contains all of`, or when the name starts with a dot. The child's `from` is `<invalid from>` in the report's `subjects`, as in Rego. For a parent written wrong by a self-comparison, `matches` on the right isn't reported, and Rego does report it. The policy fails `$well_formed` either way. `named by one`, where `one` is a word of the grammar, gives only `one can't be an alias`.
- A comparison whose right side can't be read through something that isn't an object, like `lo is at least t.cov.x` with `t.cov` 5 and `lo` true, names the left side too when it isn't a number: `t.cov is 5, which isn't an object, and lo is true, which isn't a number`.
- In an `any_of`, an input that reads the same path as a part of the check carries the part's `part` tag, like `ergo.rego`: `has: {cv: "name"}` with `name exists` in one option and `cv is 1` in another.
- On the left of a `whose` and after `sorted by`, the subject's name is the item's field, in a check, a `for` line and a `from` line, as the spec says, so `from: every ws whose w starts with "b"`, for a subject called `w`, reads each item's `w` field. On the right of a `whose` the name reads the subject and `.s` the item's field. A field named like the subject or a part, read on the item, is printed with its dot, like `item 3 of ys: .s is missing` and `item 1 of .cov.xs is 1`, as `ergo.rego` prints it.
- The engine follows spec 0.5, so a policy says `ergo_spec: v0.5`. Reports change for every policy: the report's `ergo` says `v0.5`, its `engine` version says `0.3.0`, and each failed row and each violation has a `message`. - `does not exist` on a path with a `named by` field that can't be read, like `x[0] named by zz does not exist` with `x` missing and `zz` missing, `null` or not text, now fails as `absent`, as spec 0.5 says and `ergo.rego` does, where it passed. Reports change for such a check: `passed` goes from `true` to `false`.
- A check that reads the params by a position, like `every $params[0].a is 1` or `some $params[0].a is 1`, with params that aren't a list or an object, now says `$params is 3, which isn't a list` as `ergo.rego` does, where it said `every $params[0].a is 1 is false`, and a check that reads them by a key, like `$params.a is 1` or `zz is in $params.a`, says `$params is 3, which isn't an object`, where it said `$params.a is 1 is false`. `count of $params[0] is 1` with params `[]` says `$params is [], which isn't an object`, where it said `needs more than 15 digits`. Messages change for such checks. Params that are a list, text, a number or a boolean are read for `inputs`, so an entry that reads a position of them has the value and the location the spec says, `$params:/0`, where it had no value and `$params:`.
- A `for` line over params that aren't an object, a sentence of a `for` line, a `named by` key and a `whose` that read them, like `for: every $params as p`, `x named by $params.v is 1` or `every ws whose x is $params.v is 1`, say `$params is 3, which isn't an object` as `ergo.rego` does, where they said the check was false, and so does `count of $params whose v is 1 is 1` with params `[3]`, where it said `needs more than 15 digits`. `x is in $params[0].v` with params `[[1]]` says `item 1 of $params is [1], which isn't an object`. Messages change for such checks.
- A subject's `from` line that reads params that aren't an object, like `things named by each of $params.ks` or `things named by $params.env`, says so in its `$min_subjects` message, `$params is 3, which isn't an object`, as `ergo.rego` does, where it said `$params.ks is missing`. A position says what it found, like `item 1 of $params is 3, which isn't a list of text` for `$params[0]` with params `[3]`. It still makes no subjects, also when the list of keys can be read, like `$params[0]` with params `[["k"]]`. Messages change for such policies.
- When both sides of `contains` or `is in` can't be read and the right side is a path from `$input` or `$params`, the message names the left side first, as `ergo.rego` does: `zz is "v", which isn't a list, and $input.y is 3, which isn't an object`. A `count of` through a position, like `count of y[0].v is 1` with `y` holding `[{"v": 1}]`, names the item once, `item 1 of y: v is 1, which isn't a list or an object`, where it also said `y[0].v is 1, which isn't a list or an object`. Messages change for such checks.

## 0.2.0

### New

- Every phrase that lacked an opposite has one, as spec 0.4 says: `does not start with`, `does not end with`, `is not a <type>`, `is not a non-empty string`, `is not between`, `is not <value> within <number>`, `does not equal <field> within <number>`, `contains some of` and `does not contain all of`, plus `is alphabetically on or before` and `is alphabetically on or after`. The sentence reader's `Phrase` has the variants `NotStartsWith`, `NotEndsWith`, `NotType`, `NotNonEmptyString`, `ContainsSome` and `NotContainsAll`, `Between` has a `not` field and `Alphabetically` an `or_equal` field. A count, a sum, a plus or an elapsed time can now be followed by `is not ... within` too, which the engine refused before.
- Text can be joined on the right side with `followed by`, as spec 0.4 says: `rego.version is tag.version followed by "-dev"`. The sentence reader's `Operand` has a new variant `Joined`, with the pieces in order, and `compare` and `contains` read it.

### Changed

- A path that names its key by a field lists the field in a row's `inputs` for a `count of`, a `sum of`, an `every` and a `some` too, right after the list's entry, and the check of a `for` line keeps its whole path, `m named by p` and then `p`, where it showed only `m`, as spec 0.4 says. When the path before the field can't be read, an `every` or `some` fails with that path's cause, not the field's, so `every zz.x named by p is 1` with `zz` missing or a string is `absent` or `unusable` when `p` is `null`, where it was `null`. A list it walks before the field doesn't count, so `every rows.w named by k is "xy"` still fails as `null` when `k` is `null`. With `rows` `null` it fails as `null` whatever `k` holds, where a missing or number `k` gave `absent` or `unusable`, and `failed_items` names `rows`, where it was empty when `k` couldn't be read. A `for` line whose own path has such a field, like `every rows.w named by p as w`, lists `p` too, sorted with the rest by name, as `ergo.rego` does. A `plus` or an elapsed time that reads such a path no longer has the field's location in its own entry, as spec 0.4 says. Reports change for such policies.
- The report's `engine` name is `ergo-rust`, where it was `ergo-policy-engine`, so it matches the Rego engine's `ergo-rego` and the `rust-v*` tag. Every report changes in that field only, and the hash leaves `engine` out, so hashes stay the same. The version is the same.
- The engine follows spec 0.4, so a policy says `ergo_spec: v0.4`.
- An empty name, `""`, is written wrong too, whether it names a requirement, a check, an `any_of` option or a part, with `a name can't be empty`.
- The CLI has its own page, [`CLI.md`](../../CLI.md): install, how to run it, its exit codes and how it reads YAML. They were in the README and in this folder's README.
- The `$well_formed` row lists the problems of fields, parts and checks sorted by name as the report writes it, quotes and escapes included, by code point, where the quotes were left out, and lists the requirement's own fields first, then the subject's, then the checks. Reports change for names that need quoting and for a requirement with both a field and a subject problem.
- An own field named like a part of the subject or like a `for` alias keeps its dot in the name of an input, like `.cov.pct`, and so does the list a `count of`, `sum of` or a walk reads, like `.art.xs[]`. A policy written wrong keeps the dots it was written with in the expression and in `from`: a check whose `for` isn't a string, and a part named like one of its parent's.
- An input that reads the item's own field named like a parent subject keeps its dot, like `.art.k`, as spec 0.4 says. A `from` that starts at the input with a `named by` step is written as it is in the `$min_subjects` and `$unique_ids` expressions, so `every $input named by $params.k` is no longer `count(matching(every [$params.k]))`. Reports change for such policies. The `from` a subject gets in `subjects` keeps every dot the policy wrote on the left of a `whose`, like `.art.k`, `.art.xs[0]` or a part's `.att.id`, where it dropped them.
- A policy with no requirement, because `requirements` is missing, `null`, not an object or empty, gets Ergo's own requirement `$policy` with a failing `$well_formed` row that says what is wrong, as spec 0.4 says, where the report had no row and `violations` was empty while `compliant` was `false`. A requirement called `$policy` is written wrong. Reports change for such policies.
- A name that starts with `$` is written wrong, whether it names a subject, a requirement, a check, an `any_of` option or a part, with `a name can't start with $`, as spec 0.4 says, in place of `name reserved`, `a subject can't be named $input` and `invalid alias` for a part called `$dollar`. A check with such a name has no entry in `requirements`. Reports change for such policies.
- A name that starts or ends with a space or an invisible character (Unicode White_Space or general category Cf, like U+200B or U+FEFF) is written wrong too, with `a name can't start or end with a space or an invisible character`, as spec 0.4 says, for a subject, a requirement, a check, an `any_of` option and a part. Reports change for such policies.
- A key read from `$params` or `$input`, after `named by` or in brackets, has to be a string, as spec 0.4 says. A whole number used to read that item of a list, so `m named by $input.k is 1` with `k` holding `1` and `m` holding `[5, 1]` passed by reading `1`, and `commits[$params.n]` read a commit. It fails as `unusable` now, and a `from` line with such a key gives no subjects. Reports change for such policies.
- A `from` line like `scans named by $params.env named by each of $params.k` gave `$min_subjects` the worst of the causes of `env` and `k`, so a `null` `env` with `k` missing gave `absent`. The ref before the list decides now, as [subjects.sentence](../../spec/semantics.md#requirements) says, so that one gives `null`. Reports change for such policies, in the cause only.

### Fixed

- A check could pass when it should fail. A path named by a `for` alias that holds a number read the number as a list position, so `m named by k is 1` under `every ks as k` passed on `{"ks": [1], "m": [5, 1]}`, by reading `m[1]`. ## 0.1.0

### New
