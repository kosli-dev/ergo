# Changes to the Rust engine

Each release names the version of the spec it follows. The spec's own changes are in [spec/CHANGELOG.md](../../spec/CHANGELOG.md), and those of `ergo.rego` in [CHANGELOG.md](../../CHANGELOG.md).

## 0.3.0 (not released yet)

### New

- Every failed row has a `message`, a line that says in plain words what Ergo found, as the spec says: `approver is "ana", and author is "ana"`, `item 2 of tests: ok is missing` or `signed: signature is missing; reviewed: reviewer is missing`. A row that passed has none. Each violation carries the message of its row. The Rego engine writes the same text for every case in the spec.

- A path on the right side of `is one of`, `contains`, `matches` and the other phrases that take a list walks lists, as the spec says, from the input, the params, the subject, a parent, a part or an alias and inside `whose`, `count of`, `sum of` and `for` lines: `pin is in $input.sbom.components.name` compares `pin` with the names of the components. A list it can't read from every item fails every row, with the cause and words `every` uses. A leading dot on that path reads the subject's field, and a message and an input name keep the dot only when a part, a parent subject or an alias has the same first name. A `$input` path or a field on the right that reads into text now says which value can't hold the next step, where it said `the check is false`.
- `that` picks items by the value itself, where `whose` picks them by a field, as the spec says: `from: every ws that starts with "b"`. It works on a `from` line, in a check and on a `for` line, and a field called `that` is written `.that`.

### Changed

- `ergo` reads YAML the way OPA 1.21 and later do, and no longer the way OPA 1.20 does. `ergo.rego` is tested with OPA 1.22.0, which reads YAML the same way as 1.21. Reports change for YAML inputs, policies and params that use any of these:
  - Values that read differently: `yes`, `no`, `on`, `off`, `y` and `n` (in any of their spellings) are strings, as values and as keys, where they were booleans. With `approved: yes`, `approved is true` used to pass and now fails as `unusable` with `approved is "yes", which isn't true or false`, as in `ergo.rego`. A key written in a mapping wins over a merged one wherever the `<<` is, and the first of several merges wins, where the later one did. A date tagged `!!timestamp` is written out in full, like `2001-12-14T00:00:00Z`, where it kept its text.
  - Files that were refused and are now read: a tag YAML doesn't define on a value, like `!custom 5`, which keeps the text, `"5"`; a bare `!`, which reads a plain value as if it had no tag, so `! 5` is 5; a verbatim tag like `!<tag:yaml.org,2002:int> 5`; `!!merge`; a key from 9223372036854775808 to 18446744073709551615; and `%YAML 01.1` or `%YAML 1.01`.
  - Files that were read and are now refused: a later document that isn't valid YAML, has an alias with no anchor, nests more than 10,000 levels or says `%YAML 1.2` after `...`; a directive other than `%YAML` and `%TAG`, like `%FOO bar`; the same alias twice as a key of one mapping, compared by the anchor's name; a `!!timestamp` key; a `!!timestamp` whose time zone is 24 hours or more; `!!bool yes` and `!!bool on`; and `! .inf` or `! ~` as a key.
- The message of a `$min_subjects` row that failed because a `from` line couldn't be read is the same as `ergo.rego`'s for every shape in `spec/cases/messages`: `item 2 of things is missing`, and for a child subject the path as it walks its parent's value, without the parent's name, like `ws is missing`, `item 1 of ws is missing` or `meta.owner is missing`.
- A `whose` in a `from` line that compares a field of the item with itself, like `things whose x is x` or `t.ws whose t.lo is at most .t.lo`, is written wrong, `whose: x is compared with itself`, as in `ergo.rego`. A left side that names a parent, like `t.ws whose t.lo is at least t.lo`, reads the item's own field, and the right side reads the parent only when it has no dot, so that one is fine.
- When a child's parent has a `from` line that fails on a `named by` key or on `last of`, a `whose` of the child that compares or tests membership against a subject further up, like `w.kids whose lo is at least t.cov.x`, adds the problem `subjects.g.from: unknown alias $t`, listed after the other problems, as `ergo.rego` does. The same goes for a parent written wrong by a `whose` that compares a field with itself, where a `contains` on the right is reported too. It isn't reported when the parent's `from` has `every` or `named by each of`, when the right side is a `count of`, a `sum of`, a `plus`, `contains`, `matches` or `contains all of`, or when the name starts with a dot. The child's `from` is `<invalid from>` in the report's `subjects`, as in Rego. For a parent written wrong by a self-comparison, `matches` on the right isn't reported, and Rego does report it. The policy fails `$well_formed` either way. `named by one`, where `one` is a word of the grammar, gives only `one can't be an alias`.
- A comparison whose right side can't be read through something that isn't an object, like `lo is at least t.cov.x` with `t.cov` 5 and `lo` true, names the left side too when it isn't a number: `t.cov is 5, which isn't an object, and lo is true, which isn't a number`.
- In an `any_of`, an input that reads the same path as a part of the check carries the part's `part` tag, like `ergo.rego`: `has: {cv: "name"}` with `name exists` in one option and `cv is 1` in another.
- The engine follows spec 0.5, so a policy says `ergo_spec: v0.5`. Reports change for every policy: the report's `ergo` says `v0.5-dev`, its `engine` version says `0.3.0-dev`, and each failed row and each violation has a `message`. Every case in `spec/cases` passes, so `known-failures.txt` is empty. The text still differs from the Rego engine's in a few cases that no spec case covers. `named by each of t.keys`, a list that is a field of a parent, is an open question: the spec doesn't define it and the grammar allows it. Rego never reads it, and says `<invalid ref> is missing` whatever the parent holds, and the Rust engine reads the parent's field. A `sum of` over a number of more than 15 digits next to a missing value is `absent` with `item 2 of ws: lo is missing` in Rego and `unusable` with `sum of ws.lo needs more than 15 digits` in the Rust engine. For a child subject whose own value isn't an object, Rego says `item 1 of items: it is 3, ...` and the Rust engine `item 1 of items is 3, ...`, and Rego looks wrong there. When both sides of a child's `whose` name an ancestor, like `w is .w within 1 and t.lo is more than t.lo`, Rego gives two problems and the Rust engine only the first. The `from` printed in the report's `subjects` can differ in a dot, `.t.lo` against `t.lo`, when another subject is broken, as it also does on `main` for valid policies like `w.kids whose t contains all of .t.lo`. The pass or fail result is the same in all of these. In a `from` line, a `whose` that is a quantified condition isn't checked for comparing a field with itself. `unknown alias $t` is still missing for `w.kids whose .w.lo contains t.lo` under a parent with `named by zz`. For an `$applies` row of `is in` or `is not in` with a path on the right, like `w.kids whose .w.lo is in .w.lo`, the message and sometimes the cause differ. The Rust engine adds problems that Rego doesn't in some policies with more than one: `unknown alias zz` and `last of isn't supported yet here` next to an `exists` problem, and `can't build on a subject read from another subject yet` next to Rego's `last of` problem. An `$applies` message can name one side more than Rego's, like `t.ws whose x is before t.cov.y` with `t.cov` `[1]` and `x` null. A grandchild of `t.ws named by each of $params.keys` with `ws` a list, `null` or a scalar, or with the keys missing or `[]`, gets one row without the key in Rego and a row with it in the Rust engine. On a `for` line over a path through two lists, like `kids.kids`, Rego repeats the outer item and the Rust engine prints `item 1 of kids[0].kids: ...`. Rego has bugs the Rust engine doesn't share: `w: t.ws whose meta.owner contains all of t` with `meta` 5 and `whose sum of lo is not t.zz.x and lo is not in t` end in an `eval_conflict_error`, and on a `for` line over two lists, a `whose` or `sorted by` that meets an item of the second list that isn't an object can leave the message empty, a key sort that can't be used is named by its value (`item 1 of items is missing` for a missing `lo`), and when two sentences of a `for` line read the same, like `i.k is in $params.l` and `i.k is one of $params.l`, Rego lists each failed item in `items` once for each of them.
- Every condition after an `and` in a `whose` chain starts with its own `whose` or `that`, as `ergo.rego` reads it, so `whose a is 1 and b is 2` is written wrong. Reports of policies written the old way change, because they now fail `$well_formed`. Their problem reads `a condition after and starts with whose or that`, and a `whose` or `that` in the wrong place names the word that was written. The expression of a `that` filter writes the subject's name in quotes when it is a word of the grammar, as `ergo.rego` does, like `"item" starts with "b"`.

### Fixed

- A `from` line whose `named by each of` list starts at a field or a subject, like `t named by each of t.keys`, is written wrong, as the spec says, where the engine read the parent's field. Its `$well_formed` row lists `named by each of takes a list from $params or $input, so it can't start at a field or a subject`, like `ergo.rego`.
- A tie in the second list of a `for` line names the second item's key, like `item 1 and item 2 of p.items tie on hi`, where it named the first item's.

## 0.2.0

### New

- Every phrase that lacked an opposite has one, as spec 0.4 says: `does not start with`, `does not end with`, `is not a <type>`, `is not a non-empty string`, `is not between`, `is not <value> within <number>`, `does not equal <field> within <number>`, `contains some of` and `does not contain all of`, plus `is alphabetically on or before` and `is alphabetically on or after`. The sentence reader's `Phrase` has the variants `NotStartsWith`, `NotEndsWith`, `NotType`, `NotNonEmptyString`, `ContainsSome` and `NotContainsAll`, `Between` has a `not` field and `Alphabetically` an `or_equal` field. A count, a sum, a plus or an elapsed time can now be followed by `is not ... within` too, which the engine refused before.
- Text can be joined on the right side with `followed by`, as spec 0.4 says: `rego.version is tag.version followed by "-dev"`. The sentence reader's `Operand` has a new variant `Joined`, with the pieces in order, and `compare` and `contains` read it.

### Changed

- A path that names its key by a field lists the field in a row's `inputs` for a `count of`, a `sum of`, an `every` and a `some` too, right after the list's entry, and the check of a `for` line keeps its whole path, `m named by p` and then `p`, where it showed only `m`, as spec 0.4 says. When the path before the field can't be read, an `every` or `some` fails with that path's cause, not the field's, so `every zz.x named by p is 1` with `zz` missing or a string is `absent` or `unusable` when `p` is `null`, where it was `null`. A list it walks before the field doesn't count, so `every rows.w named by k is "xy"` still fails as `null` when `k` is `null`. With `rows` `null` it fails as `null` whatever `k` holds, where a missing or number `k` gave `absent` or `unusable`, and `failed_items` names `rows`, where it was empty when `k` couldn't be read. A `for` line whose own path has such a field, like `every rows.w named by p as w`, lists `p` too, sorted with the rest by name, as `ergo.rego` does. A `plus` or an elapsed time that reads such a path no longer has the field's location in its own entry, as spec 0.4 says. Reports change for such policies.
- The report's `engine` name is `ergo-rust`, where it was `ergo-policy-engine`, so it matches the Rego engine's `ergo-rego` and the `rust-v*` tag. Every report changes in that field only, and the hash leaves `engine` out, so hashes stay the same. The version is the same.
- The engine follows spec 0.4, so a policy says `ergo_spec: v0.4`.
- An empty name, `""`, is written wrong too, whether it names a requirement, a check, an `any_of` option or a part, with `a name can't be empty`.
- The CLI has its own page, [`CLI.md`](../../CLI.md): install, how to run it, its exit codes and how it reads YAML. They were in the README and in this folder's README.
- The `$well_formed` row lists the problems of fields, parts and checks sorted by name as the report writes it, quotes and escapes included, by code point, where the quotes were left out, and lists the requirement's own fields first, then the subject's, then the checks. Reports change for names that need quoting and for a requirement with both a field and a subject problem.
- An own field named like a part of the subject or like a `for` alias keeps its dot in the name of an input, like `.cov.pct`, and so does the list a `count of`, `sum of` or a walk reads, like `.art.xs[]`. A policy written wrong keeps the dots it was written with in the expression and in `from`: a check whose `for` isn't a string, and a part named like one of its parent's.
- An input that reads the item's own field named like a parent subject keeps its dot, like `.art.k`, as spec 0.4 says. A `from` that starts at the input with a `named by` step is written as it is in the `$min_subjects` and `$unique_ids` expressions, so `every $input named by $params.k` is no longer `count(matching(every [$params.k]))`. Reports change for such policies. The `from` a subject gets in `subjects` keeps every dot the policy wrote on the left of a `whose`, like `.art.k`, `.art.xs[0]` or a part's `.att.id`, where it dropped them.
- A policy with no requirement, because `requirements` is missing, `null`, not an object or empty, gets Ergo's own requirement `$policy` with a failing `$well_formed` row that says what is wrong, as spec 0.4 says, where the report had no row and `violations` was empty while `compliant` was `false`. A requirement called `$policy` is written wrong. Reports change for such policies.
- A name that starts with `$` is written wrong, whether it names a subject, a requirement, a check, an `any_of` option or a part, with `a name can't start with $`, as spec 0.4 says, in place of `name reserved`, `a subject can't be named $input` and `invalid alias` for a part called `$dollar`. A check with such a name has no entry in `requirements`. Reports change for such policies.
- A name that starts or ends with a space or an invisible character (Unicode White_Space or general category Cf, like U+200B or U+FEFF) is written wrong too, with `a name can't start or end with a space or an invisible character`, as spec 0.4 says, for a subject, a requirement, a check, an `any_of` option and a part. Reports change for such policies.
- A key read from `$params` or `$input`, after `named by` or in brackets, has to be a string, as spec 0.4 says. A whole number used to read that item of a list, so `m named by $input.k is 1` with `k` holding `1` and `m` holding `[5, 1]` passed by reading `1`, and `commits[$params.n]` read a commit. It fails as `unusable` now, and a `from` line with such a key gives no subjects. Reports change for such policies.
- A `from` line like `scans named by $params.env named by each of $params.k` gave `$min_subjects` the worst of the causes of `env` and `k`, so a `null` `env` with `k` missing gave `absent`. The ref before the list decides now, as [subjects.sentence](../../spec/semantics.md#requirements) says, so that one gives `null`. Reports change for such policies, in the cause only.

### Fixed

- A check could pass when it should fail. A path named by a `for` alias that holds a number read the number as a list position, so `m named by k is 1` under `every ks as k` passed on `{"ks": [1], "m": [5, 1]}`, by reading `m[1]`. So did a later item, `every ks as k, every m named by k as x`, and a one-line `every` or `some` under the `for` line. A `for` alias that holds anything but a string now fails as `unusable`, as [for.named_by](../../spec/semantics.md#for) says, and as `ergo.rego` does. When the path before it is an object, the failed item is named `m named by k`, where it was `item 4 of m` for a `3`. Reports change for such policies: some that passed now fail.

## 0.1.0

### New

- The first version of the Rust engine. It follows spec 0.3, so a policy says `ergo_spec: v0.3`, and it's experimental: anything in it may still change.
- `ergo-policy-sentences` reads check sentences, `for` lines, `from` lines and paths, without the engine.
- `ergo-policy-engine` builds the report and the violations from a policy, an input and params, as JSON.
- `ergo-policy-cli` is the `ergo` command, which prints the report or the violations from policy, input and params files in JSON or YAML.
- `ergo-policy-wasm` builds the report in a browser, from JSON text. It isn't published: it's built from the repository for the editor.
- `ergo-policy-sentences-wasm` reads check sentences in a browser, from and to JSON text. It isn't published either: it's built from the repository for the editor.
- A `for` item whose path goes on into a list item that isn't an object, `null` included, fails that item as `not_an_object`, as `every` and `some` do, where it failed as `unusable`.
