# Changes to the Rust engine

Each release names the version of the spec it follows. The spec's own changes are in [spec/CHANGELOG.md](../../spec/CHANGELOG.md), and those of `ergo.rego` in [CHANGELOG.md](../../CHANGELOG.md).

## 0.5.0 (not released yet)

### Changed

- A number in the policy with more than 15 significant digits is written wrong, as in `ergo.rego` 0.7.0 and spec 0.7 ([sentence.value.scalar](../../spec/syntax.md#values)). `l equals 1234567890.1209567890` fails `$well_formed` with `number with more than 15 significant digits: 1234567890.1209567890`, and a `min_subjects` like `9007199254740993` says `number with more than 15 significant digits`, where it said `not a whole number from 0 to 1000000`. Digits are counted on the value, so `1.50` has 2 and `1e20` has 1. Numbers in the input and the params were already compared on every digit. The same goes for a number in the `meta` of the policy, a requirement or a check, and one out of range there, like `1e400`, is written wrong with `number out of range`, where Rust let both through. Changes the report of every policy that writes such a number.

### Fixed

- A `for` line that starts with `some` and has a second item passes when one item of the first list passes, as in `ergo.rego` 0.6.1 and spec 0.7 ([for.pass](../../spec/semantics.md#for)), where it failed when another item's alias held a value the sentence couldn't read. With `approvers` holding `[{"username": "ada"}, {"state": "APPROVED"}]` and `commits` one commit, `for: some approvers as approver, every commits as commit` with `approver.state is "APPROVED"` passes, where 0.4.0 failed it as `absent` with `item 1 of approvers: approver.state is missing`. The same goes for a second item with `some`, `first of` or `last of … sorted by …`, and for one whose `whose` reads the first item's alias. An item that is an object, where what a sentence or a later line reads through its alias, like `approver.state`, is missing, `null` or of the wrong type, never counts as passing, even when nothing is checked for it because the second list is empty with `, if any,` or its `whose` leaves nothing, and every sentence reads the second item's alias: with `approvers` holding `[{"username": "ada"}]`, `commits` holding `[]`, `every commits, if any, as commit` and `commit.author is approver.u`, the check still fails as `absent` with `item 1 of approvers: approver.u is missing`. An item that isn't an object is judged as before, so when nothing is checked for it, it passes, and `["str", {"username": "b"}]` now passes through `"str"`. When no item passes, the check fails as before.

- A `for` line with a list that's empty with `, if any,`, or whose `whose` leaves nothing, still runs the sentences that don't read that list's alias, as in `ergo.rego` 0.6.1 and spec 0.7 ([for.if_any](../../spec/semantics.md#for)), where it ran none of them. With `approvers` holding `[{"u": "g", "state": "REJECTED"}]` and `commits` holding `[]`, `for: some approvers as ap, every commits, if any, as c` with `ap.state is "APPROVED"` fails as `value` with `item 1 of approvers: ap.state is "REJECTED"`, where 0.4.0 passed it. The same goes for a `for` line that starts with `every`. With the empty list first, `for: every commits, if any, as c, some approvers as ap` fails as `value` with `item 1 of approvers: state is "REJECTED"`, as `for: some approvers as ap` does, and approvers `[]` fail as `value` with `approvers is []`, where 0.4.0 passed both. With one item, `for: every xs, if any, as m` with `z is 1` fails as `value` with `z is 3` when `z` holds `3` and `xs` holds `[]`, where 0.4.0 passed it. A sentence that reads the second item's alias, like `c.author is ap.u`, has nothing to check and is left out. An item of the first list that isn't an object now fails a sentence that reads it as `not_an_object`, so approvers `["str"]` fail where 0.4.0 passed them.

- A root of the wrong type on the left of a compare, like `z` in `z is at least 1` under `every xs, if any, as m` with `z` holding `"s"`, fails the check as `unusable` with `z is "s", which isn't a number` on an empty list too, as in `ergo.rego` 0.6.1 and spec 0.7 ([for.roots](../../spec/semantics.md#for)), where it passed. The same goes for `is at most`, `is more than`, `is less than`, `is not`, `does not equal`, `is … within`, a text compare like `starts with`, a time compare when the value isn't a time at all, and a root on the left in a `whose`, like `count of xs whose $params.q is at least v is 0` ([tally.whose](../../spec/semantics.md#counts-and-sums)). With items, the root is named once with no item in front, like a root on the right: `z is at least m.v` says `z is "s", which isn't a number` where it said it for each item, and `z is at least $params.q` with no `q`, or a `null` one, says `z is "s", which isn't a number; $params.q is missing` (or `is null`) where it said only `$params.q is missing` (or `is null`). With params that aren't an object, like `3`, `z is at least 1` on an empty list was already `unusable`, and its message changes from `for every xs, if any, as m: z is at least 1 is false` to `z is "s", which isn't a number`.

- When `every`, `some`, `count of … whose` or a `for` line's sentence reads a name that walks a list, its `inputs` entry is the one a plain check of the same path has, as in `ergo.rego` 0.7.0 and spec 0.7 ([walk.inputs](../../spec/semantics.md#every-and-some)). With the subject `t` from `every teams` holding `[{"name": "ann", "rows": [{"v": "ann"}]}, {"name": "bob", "rows": [{"v": "bob"}]}]`, `every rows.v is in name` lists `t[].name` holding `["ann", "bob"]` at `/teams/0/0/name` and `/teams/0/1/name`, where it listed `t.name` holding `null`. The same goes for a part on a list subject, a list in the middle of a name, like `os[].name`, and a part that holds a list, which keeps its `part` tag. An alias of a `for` line that holds a list is listed the same way in the `inputs` of `failed_assertions`: `every rows.v is in d.name` with `d` holding `[{"name": "ann"}, {}]` lists `d[].name` holding `["ann", null]`, where it listed `d.name` holding `null`, as `$params.w is in d.name` already did. `for: every rows as r` with `r.v is in name` on that subject already passed, and now lists `t[].name`. Changes the report of checks that read such a name.

- A part whose own path walks a list, like `pn` from `c.names` with `c` a list, read by `every` or in a `whose`, is named from the subject in messages, as in `ergo.rego`: `every rows.v is in pn` with `c` holding `[{"x": 1}, {"names": ["bob"]}]` says `item 1 of c: names is missing`, where it said `item 1 of "$outer".c: names is missing`.

- A `followed by` piece read from `$input` on an input that is a list says `$input is [...], which isn't an object` after `is`, `starts with` and the other phrases too, as in `ergo.rego` 0.7.0 and spec 0.7 ([compare.join](../../spec/semantics.md#compare)), where only `contains` did. After `contains` and `does not contain`, an `unusable` row names the left side only when it isn't a list of text, and names a piece that can't be read before it, as `ergo.rego` does: `tags contains $input.o.a.b followed by ""` with `tags` holding `["a"]` and `$input.o.a` holding `1` says `$input.o.a is 1, which isn't an object`, where it said `tags is ["a"], which isn't a number, and $input.o.a is 1, which isn't an object`, and `p contains "a" followed by v` with `p` holding `5` says `p is 5, which isn't a list`, where it said `"a" followed by v is "ax", which isn't a number`. Changes the message of such rows.

- A list on the right of `is in`, `matches` and the other list phrases, read from a part, a parent, a parent's part or a part of a subject that is a list, is walked on a `for` line, in a sentence, in the line's own `whose` and in the `whose` of a `count of`, as in `ergo.rego` 0.7.0 and spec 0.7 ([for.roots](../../spec/semantics.md#for)), where it failed as `unusable`. A `count of` or `sum of` inside a `whose` reads its path as it does on its own ([tally.whose](../../spec/semantics.md#counts-and-sums)) and is read once before any item, so a problem it has fails the row on an empty list too, and a `count of` in a `for` sentence whose path has a list in the middle, like `count of pl.z is 2`, passes. A `for` line's `inputs` list the walked name, like `pos[].name`.

- A name read from outside the item that walks a list is named once, with no item in front, in an `every`, a `whose` and a `for` line, as in `ergo.rego` 0.7.0 and spec 0.7 ([message.items](../../spec/semantics.md#messages)), where it was read as `pos is [...], which isn't an object` or repeated under each item. A `for` line says an item's own problem after a root that can't be read, even when it fails no worse than the root, and `and N more` counts each problem once.
- A root that a check walks as a list, and that holds an item it can't read or values it can't use, fails the check on an empty list too, or when a `whose` leaves no item, as in `ergo.rego` 0.7.0 and spec 0.7 ([tally.walk](../../spec/semantics.md#counts-and-sums), [for.roots](../../spec/semantics.md#for)), where the check passed. That goes for a part, a parent, a parent's part, an alias of an earlier `for` line, a field of the subject written with a dot, `$params` and `$input`. With the part `pos` holding `[{"name": "bob"}, {}]` and `rows` `[]`, `count of rows whose v is in pos.name is 0` fails as `absent` with `item 2 of pos: name is missing`, where it passed. Rust also passed such a check for `$params` or `$input` names of more than one kind under `count of`, `sum of` and a `for` line's count, where `ergo.rego` failed it.

- A check that doesn't go through a list item by item fails as `not_an_object` with `$input is [...], which isn't an object` when the input is a list and its `named by` key can't be read, as in `ergo.rego` 0.7.0 and spec 0.7 ([path.not_an_object](../../spec/semantics.md#reading-a-path)). With no `k` in the params, `k is $input.m named by $params.k` and `k is $input named by $params.k` failed as `absent` with `$params.k is missing`, and as `null` or `unusable` with a `null` or a number, where only `contains` did this, and `k is m named by $input.k` failed as `unusable` with `k equals m named by $input.k is false`. `ts is after m named by $input.k` and `m named by $input.k exists` said `... is false`. On a list input, `ts is after $input.ts` and `ts is after $input.m named by $params.k` with a text key, which were `not_an_object` with `ts is after $input.ts is false`, now say `$input is [...], which isn't an object`, and so does the option `b: k is m named by $input.k` of an `any_of` with a text key, where it said `b: the check is false`. A one-line `every` or `some`, a `for` line, a `count of` or `sum of`, a child subject's checks and the `whose` of a `from` line don't change. Changes the report of such checks.

- The `$refs` of `$applies`, `$min_subjects`, `$unique_ids` and `$unique_ancestor_ids` point at the item of the params where the read stopped when the params are a list, as in `ergo.rego` and spec 0.7 ([location.read](../../spec/semantics.md#where-a-value-was-read)). With params `[[1]]`, `from: things whose x is in $params[0].v` gives `$applies` the ref `$params[0].v` at `$params:/0`, where it said `$params:`. A check already did this. Changes the report of such checks.

- A `for` line's row lists an `every` or `some` that walks a `$params` list, like `$params.q[]` for `every $params.q is 1`, as in `ergo.rego` and spec 0.7 ([for.inputs](../../spec/semantics.md#for)), where it left it out. Changes the report of such checks.

- A piece of a `followed by` from `$params` or `$input` after `is` or another comparison, like `$params.x.y` in `w is v followed by $params.x.y`, is in the check's `$refs`, as in `ergo.rego` and spec 0.7 ([compare.join](../../spec/semantics.md#compare)). After `contains` it already was. Changes the report of such checks.

- A check's `$refs` list every path from `$params` or `$input` it reads, wherever it is in the sentence, as in `ergo.rego` and spec 0.7 ([value.refs](../../spec/semantics.md#values)): on either side of `is`, `is at least` or another comparison, after `count of` or `sum of`, the list an `every` or `some` walks, in a `whose`, on a `for` line and in an `any_of` option. With params `{"n": 2, "q": [1]}`, `n is at least $params.n` lists `$params.n` holding `2` at `$params:/n`, and `every $params.q is 1` on a `for` line lists `$params.q`, where they had no `$refs`. A path that is missing or `null` is listed with `null`. A path that goes through a list, like `$params.objs.x` after `every`, `some`, `count of` or `sum of`, or on a `for` line, is listed once with what the walk read, as after `is in`: with params `{"objs": [{"x": "y"}]}`, `every $params.objs.x is "x"` lists `$params.objs[].x` holding `["y"]` at `$params:/objs/0/x`. Each option of an `any_of` lists its paths as it reads them, so `v is $params.objs.x` in one option and `v is in $params.objs.x` in another give an entry each. The `$applies` entry keeps the `$refs` it had. Changes the report of such checks.

- An `every` or a `some` whose list is missing, `null` or of the wrong type names a parent's part or a grandparent's part that its `whose` or `that` reads and that can't be read before the list, as a part of the subject already was and as in `ergo.rego` 0.7.0 and spec 0.7 ([walk.flaws](../../spec/semantics.md#every-and-some)). With the parent's part `art.cov` `null` and no `ys`, `every ys whose n is at least art.cov.z, if any, exists` says `art.cov is null; ys is missing`, where it said `ys is missing`. A child subject's check was treated as if it were a `for` line because it holds its parents' names. In an `any_of` option a part is still named only when it is in the same state as the list, as in `ergo.rego`, and otherwise the list is named. Changes the report of such checks.

## 0.4.0

### New

- `ergo_policy_engine::SPEC` is public. It is the version of the spec the engine implements, the text a policy's `ergo_spec` and a report's `ergo` use, so a program that builds policies for the engine can write the version from it.

### Changed

- A `from` line with more than one name needs `every` to read a list, and `every` works on a child subject, as in `ergo.rego` 0.6.0 and spec 0.6. A line that ends at text, a number or true or false gives that value as a subject, the subjects of a line must be of one type, `every` reads one list per name, a name it reads as a list must be one in every item, `every deployment` is written wrong, and a list before `named by each of` says to use a child subject. A failure for mixed types, or for a name that is a list in some items only, lists the items it names in `failed_items`, and a child subject of such a line is still read under each parent. Reports change as [spec/CHANGELOG.md](../../spec/CHANGELOG.md) says.
- Names resolve where spec 0.6 says, as in `ergo.rego` 0.6.0: a bare name on the right of the phrase after `every` or `some` reads the subject's field, `whose` and `that` read the value the path ends at, `pr.author` reads the subject's field inside a relative clause, and the right side of a `some` or `every` condition in a `from` line reads the candidate. Reports change for policies that write these, see [spec/CHANGELOG.md](../../spec/CHANGELOG.md). This version follows spec 0.6, so a policy says `ergo_spec: v0.6`.
- As spec 0.6 also says: `pr named by k` and `pr[0]` are allowed inside a relative clause; a `whose` that compares a field with itself says `write pr.x`; `distinct` no longer makes a bare name on the right written wrong; a `sum of` whose `whose`, or the right side of its `that`, reads a name of the value it adds is written wrong; a `named by` on the right of `every` or `some` reads the subject's key whatever the path starts at, `$params` and `$input` included; `named by pr.k` takes the key from the subject inside a relative clause, after any path; a root name in a `whose` or on the right of `every` or `some` is read once, up front, so a problem with it fails the row even on an empty list; a `whose` that compares a field with itself gives no advice when the subject's name needs double quotes; and messages name a value past the list after its item and a colon, list every item a `count of` or `sum of` couldn't read, say a root name no item can use once, and a root name's problem inside a relative clause once with no item, and an item of its own list once, like `item 2 of $params.envs is null, which isn't an object`, name a `named by` key that can't be read, and write the item's path in full when a name on the right is spelled the same.
- As spec 0.6 and `ergo.rego` 0.6.0 say, `contains` and `does not contain` read one value and never walk a list on their right side, the list after `named by each of` never walks a list, a message names text, a number or a list that stops the read of its keys, and a right side that walks a list names the value where the read stopped when another item holds a list there. `tags contains $input.k followed by ""` on an input that is a list fails as `not_an_object`, as in `ergo.rego`, where it read each item of the input and passed. `$refs` list such a path, and the keys of `named by each of`, as written with the value `null`, as in `ergo.rego`. Reports change as [spec/CHANGELOG.md](../../spec/CHANGELOG.md) says.
- As spec 0.6 and `ergo.rego` 0.6.0 say, `every`, `some`, `count of`, `sum of`, a `for` item without a position and the right side of the phrases that take a list read each item of a list a path starts at, whether it is the subject, a part, a `for` alias or `$input`, and so does a second `for` item that starts at an alias holding a list. A check that also reads the subject's own field outside those still fails as `not_an_object`, once. A path from `$input` whose first step is a key or a `named by` fails as `not_an_object` on an input that is a list, where it failed as `unusable`, and says `$input is [...], which isn't an object`. A `for` item that isn't an object is named by its value, where it said `is null`. A check that can't use a param or a `named by` key no longer says the list it reads isn't an object, and a root name inside a `whose` that isn't a list, or that is missing or `null` in an item of the subject, is said once, with no item.
- A path that meets `null` partway along fails as `null`, where it failed as `absent`, and the message names the step that is `null`, as in `ergo.rego` and spec 0.6: `c.z is 1` with `c` `null` says `c is null`, and `pl.z is 1` with the part `pl` `null` says `pl is null`. The same goes for `$input`, `$params`, a parent's field, a `for` alias and a position on a `null` subject, alias or `$input`. A key read from a field right after the `null` still decides. A `whose` condition on a `from` line reads the same way, so its `$applies` row fails as `null`, while a `from` line that walks through the `null`, like `every prs.c.z`, still fails `$min_subjects` as `absent`. A key read from a field after the `null` is named too, after the step, like `s is null; p is 3, which isn't text`.
- A requirement on a child subject checks the ids of every ancestor of its subject too, on `$unique_ancestor_ids` rows, as in `ergo.rego` 0.6.0 and spec 0.6. Reports of every requirement on a child subject change, see [spec/CHANGELOG.md](../../spec/CHANGELOG.md).
- A name under a `for` line that doesn't depend on the item, a field of the subject or of a part, `$params` or `$input` with or without a path, or an alias of an earlier line, is read once, before any item, as in `ergo.rego` and spec 0.6 ([for.roots](../../spec/semantics.md#for)). When a compare or `is in` phrase reads it as a value, a problem with it fails the check on an empty list too, with or without `, if any,`, and the message names it once with no item in front, whatever its cause, then the empty list if it is one, then what each item says on its own, `z is missing; item 1 of xs: m.v is 1`. A `$params` or `$input` read alone is such a name too, and `failed_items` lists every item that failed, also when a name is said once. A root in a `whose` on the `for` line no longer hides what an item says on its own, whichever clause comes first: `every xs whose k is in pr.z and whose v is 1 as m` with `pr.z` holding `"s"` says `pr.z is "s", which isn't a list; item 2 of xs: v is "x", which isn't a number`, where it said only `pr.z is "s", which isn't a list`. A list on a later line that doesn't depend on the item is said before the items' problems. A `named by` key read from the item under `null` params says what missing params say. In a `count of` or `sum of`, a `$params` or `$input` name that is missing or `null` is named before the others, like `$params.l is missing; pr.l is missing` for `count of xs whose w is in pr.l and whose v is in $params.l is 0`, where it said `pr.l is missing; $params.l is missing`. The report no longer depends on the order the `whose` clauses are written in. Reports change for policies that write these, see [spec/CHANGELOG.md](../../spec/CHANGELOG.md).
- Under a `for` line, `is`, `count of`, `sum of` and a `named by` key read a root once, before any item, as in `ergo.rego` and spec 0.6 ([for.roots](../../spec/semantics.md#for)). A root that is missing, `null` or of the wrong type fails the check on an empty list too, and is named once with no item in front: `z is 1` with `z` holding `"s"` says `z is "s", which isn't a number`, `count of z is 1` says `z is "s", which isn't a list or an object`, and `m.t named by z is 1` with `z` holding `3` says `z is 3, which isn't text`, where it said it for each item. A key the row can't read is named before what each item says on its own. An object that `count of` or `sum of` reads fails on an empty list too, with `z is {"a": 1}, which isn't a list`, with or without a `whose`, as it does with items. A `count of` or `sum of` root is said once with items, where it was said for each item: `count of z is at least m.v` with `z` holding `"s"` says `z is "s", which isn't a list or an object`. A sentence that reads two roots isn't said again after them, and a root named before an item's own problem counts towards the cause, so `zz is 3, which isn't text; item 1 of ws: w[0] named by zz is missing` fails as `unusable`, not `absent`. A name that depends on the item and can't be read, like `i.t` holding `"s"` in `every items as i, every $params.l whose v is at least i.t as x`, makes the cause `unusable` where a missing or `null` item of `$params.l` gave `absent` or `null`, with the same message. The names of one sentence are said worst cause first and then by name. Reports change for policies that write these.
- A ref on the right of `is in`, `is not in`, `contains`, `contains all of` and the other phrases that take a list or patterns is listed in the row's `inputs` after the field, as in `ergo.rego` 0.6.0 and spec 0.6 ([path.right_inputs](../../spec/semantics.md#what-a-row-shows)), and a violation lists a ref its row lists already once. The rows of `every`, `some` and `count of` list such a ref from `$input` where they list the right side of `is at least`, but not one from `$params`, and a `for` line's own row lists one from either. A ref with `named by` after these phrases is listed in those rows as it is after `is at least`, like `$input.m named by k` and `k` in `every xs.n is in $input.m named by k`, where it was left out, or listed in full in a `whose` where `ergo.rego` lists `$input.m`. Changes the report of every such check.

### Fixed

- The `checks` block of the report matches `ergo.rego` in three places. A `$refs` entry for a path that reads through a list of params, like `$params[0].v`, points at where the read stopped, `$params:/0`, where it pointed at `$params:`. A check written wrong because it has a field no check has, like `zz` or a `for` next to an `any_of`, keeps the words it was written with in its `expression`, `is one of $params.z`, and has no `$refs`, where it printed `is in` and listed the refs. A failed assertion of a `for` check lists the alias before the path through it, `ok` and then `ok.fs[].k`, where it listed the path first.
- The `$applies` check has `$refs` for each `$params` or `$input` path the conditions of a `from` line read, like `$params.i` in `things whose x.y named by $params.i does not exist`, as `ergo.rego` and spec 0.6 say, where it had none.
- A `count of` or `sum of` whose path runs into an item that isn't an object says so, like `item 1 of xs: m is "s", which isn't an object`, as `ergo.rego` does, where it said `m.v is null, which isn't a number`.
- A root name that a `whose`, or the phrase after `every` or `some`, reads as a list and that isn't one, like `$params.q` or `pr.z` in `count of xs whose v is in pr.z is 0`, fails as `unusable` and names itself, like `pr.z is "s", which isn't a list`, on an empty list too, as `ergo.rego` does, where the check passed. On a `for` item the message no longer puts an item in front, like `item 1 of xs: pr.z is "s", which isn't a list`. Every root name in a relative clause that fails is named, whatever its cause, in the order the sentence reads them and in front of what the items say, as in `ergo.rego`, where it named the first one with the row's cause, and a check's own row that fails as `absent` or `null` names a missing or `null` side read from the subject too, like `c.z is missing, and d is null`. A list in the middle of a subject's field on the right of `every` or `some`, like `c.z` with `c` a list, fails before any item and with no item in front, where it passed on an empty list. A walk whose ref step can't be read names its path and then each root its phrase can't read, like `xs named by $params.k is missing; q is missing`, where it named only the path. A root of the wrong type for any other phrase, like `pr.z` after `is at least`, fails the same way on an empty list too, with no item in front, as `ergo.rego` does. A root in a sentence under a `for` line is named once, with no item, and a root that reads the alias of the first item in the second item fails on an empty list too, like `item 1 of ys: m.q is "s", which isn't a list`, where it blamed `item 1 of xs`. A `count of` names a missing or `null` `$params` or `$input` root first, sorted, as `ergo.rego` does.
- A part that holds a list, like `pl` in `m.v is in pl.z` under `every xs as m` with `has: {pl: c}` and `c` holding `[{"z": 1}]`, fails the `for` check as `unusable` with `pl is [{"z": 1}], which isn't an object`, as `ergo.rego` and spec 0.6 say, where it failed as `value` with `[]` and passed with `[{"z": 1}]`. `count of xs whose v is in pl.z is 0` is read the same way. When the params aren't an object, a `for` line that picks tied items fails as `ambiguous`, not `unusable`, and a tie under a `whose` that reads the first item's name is named instead of `for ... is false`.
- `require: some` on a child subject needs a passing subject under each parent, as spec 0.6 and `ergo.rego` 0.6.0 say. Failing subjects under a parent that has a passing one are not violations and not counted in `causes`.
